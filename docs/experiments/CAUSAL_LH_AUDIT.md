# 미래 정보 없이 왼손 역할 proxy 쌍을 만들 수 있나 — causal 왼손 자료 감사 (#1750) — 사전 등록

작성 2026-10-15. 학습 없음, 모델 없음. **통계를 돌리기 전에 고정한다.** 아스트라 리뷰(a5ebf5bb, BLOCKER/HIGH 없음, MEDIUM 2·LOW 2)를 반영한 뒤 한 번만 실행한다.

## 왜 하나

코드 조건 학습의 출발점은 "PiJAMA에는 코드 라벨이 없으니 왼손을 화성 조건으로 쓴다"는 자가 라벨이다. 그런데 PiJAMA에는 손 정보가 없다. 손을 나누는 규칙이 미래 음을 보거나 같은 음을 조건과 타깃에 함께 쓰면, 모델은 정답을 조건으로 미리 보는 학습을 하게 된다. 아스트라가 #1736 리뷰(HIGH H1)와 #1749 재리뷰에서 학습 전에 이것부터 확인하자고 했다.

## 질문

세 가지 역할 proxy 규칙으로 다음을 확인한다.

1. 실시간 결정 시각(타깃 onset − 선행 시간)까지 관측할 수 있는 정보만으로 조건을 만들 수 있나?
2. 흔히 쓰는 오프라인 추출(타깃 onset 시점에 울리는 화성)은 미래 정보를 얼마나 쓰나?
3. 그렇게 만든 조건은 얼마나 자주 비어 있지 않나? 다양성은 어떤가? 곡별·연주자별로는 어떻게 퍼져 있나?

## 판정 범위 (아스트라 합의)

- **이번 판정은 "명세대로 미래 정보 없이 역할 proxy 쌍을 만들 수 있는가"까지만이다**
- 판정하지 않는 것: 화성 정답, 손 정확도, 티그랑 스타일, 음악성, 학습 효과
  - 수작업 정답이 없으므로 손 정확도에 수치를 붙이지 않는다
- 세 규칙은 "손"의 정답이 아니라 **역할 proxy**다. 조건 쪽 음을 "왼손 같은 화성 역할", 타깃 쪽 음을 "모델이 배울 선율 역할"로 나눌 뿐이다
- **PC가 겹치는 것은 누출로 세지 않는다.** 왼손 C3와 선율 C5가 같은 PC인 것은 자연스럽다. 누출은 같은 음표(ID)이거나, 결정 시각 뒤의 정보일 때만이다

## 세 가지 시각 (따로 보고한다)

- **역할 확정 시각** `available_at`: 위 표
- **타깃 onset**
- **결정 시각** `d = 타깃 onset − L`. L은 두 가지다
  - `L = 0`: 선행 시간 없이 규칙 자체의 확정 지연만 적용
  - `L = 468.75 ms`: 128 BPM의 1박. **주판정은 이쪽이다**
- **이 d는 "음별 이상적 결정 시각" 진단이다. 현재 런타임의 블록 snapshot 시각이 아니다**(아스트라 리뷰 M2)
  - 현재 producer(`rt_producer.py`)는 블록 시작 `now = t0 + k·937.5`에 `now + 1406.25`까지를 확정한다. 그래서 한 블록 안의 음들은 모두 블록 시작 시점의 관측으로 만들어진다
  - 예: t0 = 0, k = 1, 타깃 onset 2200 ms. 블록 snapshot은 937.5 ms지만 이 감사의 d는 1731.25 ms다. 1200 ms에 친 조건 음을 이 감사는 "사용 가능"으로 세지만, 그 블록을 시작할 때는 아직 관측되지 않았다
  - 그래서 이번 결과는 **"음마다 1박 앞에서 결정한다면" 미래 정보 없이 쌍을 만들 수 있는가**까지만 말한다. 현재 런타임 방식의 쌍 자격으로 주장하지 않는다(runtime-matched 미검증)
  - 학습에 들어가기 전에 블록별 snapshot 계약(위상, t0, 최초 prebuffer 포함)을 고정하고 따로 확인한다

## 조건 정의

| 조건 | 정의 | 떼기(off) 정보 |
|---|---|---|
| **주 조건 `sounding`** | 조건 역할이고, `available_at ≤ d`, `on ≤ d`, d까지 떼지 않은 음 | d 이전에 뗀 것만 반영한다. d 뒤의 떼기는 아직 관측하지 않은 것으로 본다 |
| **보조 조건 `recent`** (이번에 실행 전 등록) | 조건 역할이고, `available_at ≤ d`, `d − 937.5 ms ≤ on ≤ d`인 음. 937.5 ms는 런타임 블록 하나(2박)다 | 전혀 쓰지 않는다 |
| 오프라인 지름길 `offline` | 조건 역할이고 타깃 onset에 울리는 음. `available_at`을 무시한다 | 타깃 onset까지의 떼기를 쓴다 |

- **보조 조건을 지금 넣는 이유:** 컴핑음은 짧다. 그래서 1박 전 시점에는 이미 떨어져 있어 `sounding`이 비기 쉽다. 결과를 본 뒤 이 조건을 더하면 사후 완화가 된다. 그래서 실행 전에 등록하고, **두 조건을 모두 보고하고 각각 판정한다.** 결과를 보고 한쪽을 고르지 않는다
- **`recent`를 "지금 울리는 코드"로 해석하지 않는다.** 최근에 시작한 조건 역할 음의 묶음일 뿐이다
- **내보내는 조건의 형식:** 관측 전 떼기는 `off = ∞`로 둔다(`prefix_view` 형식). 실제 off 값을 조건에 싣지 않는다
  - 이번 감사는 **ID·PC 수준의 인과 감사**다. 원자료 CSV에는 개수와 PC 집합만 나간다. P2b의 off 노출 검사는 prefix로 만든 `sounding` 목록만 본다. `recent`를 포함한 실제 조건 음표 payload의 검증은 자료 구현 때 따로 한다
- 오프라인 지름길은 미래 정보를 얼마나 쓰는지 재는 데만 쓴다. 자료로 쓰지 않는다

## 집계 — 각각 독립으로, 분모와 함께

| 기호 | 세는 것 | 분모 |
|---|---|---|

| K4 | (오프라인만) d에 울리고 있던 조건 음 중 (d, 타깃 onset] 사이에 떼어 오프라인이 뺀 음. d 뒤의 떼기 정보를 쓴 것이다 | 타깃 수 |
| 참고 | 타깃과 음높이가 같고 onset 차이가 1 ms 미만인 조건 음(전사 중복) | 조건 항목 수 |

- 누출이 하나라도 있는 타깃 수도 따로 센다(분모: 타깃 수)
- PC 겹침은 세지 않는다

## 검사와 판정 (실행 전 고정)

| 검사 | 내용 | 통과 |
|---|---|---|
| P0 자료 | 189곡 모두 SHA1 일치, 파싱 성공, 음 수가 manifest `all_notes`와 같음 | 전부 |
| P1 누출 | 온라인 두 조건 × 두 L, **전체 타깃**에서 K1, K2, K3 | 모두 0 |
| P2a replay | 같은 규칙을 이벤트 순서대로 다시 계산하는 **독립 구현**(`replay`)과 일괄 계산의 조건 ID 집합을 **전체 타깃**에서 비교 | 불일치 0 |
| P2b prefix | 곡·규칙마다 고르게 뽑은 타깃 64개 × 두 L에서, d까지의 음만 남기고 규칙을 다시 적용해도 조건이 같은지 | 불일치 0, 내보낸 조건에 실제 off 노출 0 |
| P2c 미래 교체 | 같은 표본에서 d 뒤를 다음 곡의 첫 30초로 바꿔도(d + 1 µs부터 시작) 과거 조건이 같은지 | 불일치 0 |

- **구성 가능** = P0, P1, P2a, P2b, P2c 모두 통과(규칙별)
- **비퇴화** = `L = 1박`에서 조건이 비어 있지 않은 타깃 수 ÷ 타깃 수(전체 곡 합산)가 1/10 이상(규칙·조건별)
  - **원래 개수로 판정한다.** 보고 파일의 반올림 비율은 표시용이다(아스트라 리뷰 M1: 2499/25000 = 0.09996이 0.1로 반올림되어 통과하던 것을 고침)
  - 0.10은 품질 기준이 아니다. "조건이 거의 항상 비어 있어서 사실상 무조건 자료"인 경우만 거르는 공학 하한이다. 누출 0을 조건 삭제로 달성하는 것을 막기 위한 것이다. 학습 충분성이나 음악성 기준도 아니다
  - 합산 비율이 통과해도 특정 연주자까지 쓸 수 있다고 말하지 않는다. 곡별·연주자별 분포를 함께 제시한다
- 판정 문구는 규칙 × 조건마다 다음 셋 중 하나다
  - **causal 쌍 구성 가능**: 구성 가능이고 비퇴화
  - **구성 가능하나 조건이 거의 항상 비어 있음**: 구성 가능이지만 비퇴화 미달
  - **구성 실패**: 검사 하나라도 미달
- A Fable 층은 같은 검사 수치와 통계만 보고한다. 자격 판정(구성 가능·비퇴화)은 주대상만 한다

## 함께 보고하는 것 (판정에 쓰지 않는 기술 통계)

- **coverage:** 규칙 × 두 조건 × 두 L의 비어 있지 않은 비율과 평균 크기. 오프라인 지름길의 비율도 같이 적는다
- **남은 타깃:** 타깃 수, 전체 음 대비 비율, 제외 원인별 수
- **PC 다양성:** 서로 다른 PC 집합 수, 엔트로피(bit), 상위 5개 비중, 집합 크기 분포
- **시간표:** 조건 음의 역할 확정 지연(`available_at − on`), 조건 나이(`d − available_at`, `d − on`), d가 0보다 앞인 타깃 수
- **분포:** 곡별 비율(최소·p10·중앙·p90·최대, 0인 곡 수), 연주자별, live/studio별
- **오프라인 지름길:** 조건 항목 중 미래 onset 비중, 역할 미확정 비중, 미래 떼기로 빠진 음(K4), 온라인 조건과의 Jaccard, "오프라인은 있는데 온라인은 빈" 타깃 수
- **원자료:** 타깃별 행(`L = 1박`의 조건 크기·PC 집합·오프라인 누출 수 + `L = 0`의 sounding 크기)을 repo 밖 `/Users/ohhalim/git_box/lh_audit/targets_lead1beat.csv.gz`에 둔다. 보고 파일에 sha256을 적는다

## 검사기 자체의 검증 (실행 전에 마침)

- **fixture:** 같은 PC, 동시각 중복음, 굴린 화음, 손 교차, 무반주 선율, 지속음, 짧은 컴핑음(`tests/test_lh_role_proxy.py`)
- **경계 fixture(아스트라 Q3):** 50 ms·300 ms 창 끝의 직전·동일·직후, 창 끝에 시작하는 음, off = d(뗀 것)와 off > d(울리는 것). 일괄 함수와 replay를 함께 확인한다
- 표본 64개 + 전체 replay는 개발 감사 수준이다. 전 구간 인과성의 증명은 아니다
- **replay 대조:** 고정 fixture와 무작위 음에서 일괄 계산과 같음. prefix·미래 교체는 무작위 음으로 확인
- **양성 대조:** 묶음 창이 닫히기 전, 창 시작 시각에 역할을 확정하는 "새는 규칙"을 일부러 만들었다. replay 검사와 미래 교체 검사가 모두 잡았다(`tests/test_lh_audit_stats.py`)
- **이번에 더한 변형 시험 7개 중 6개 검출**(b7acd672의 변형 3개는 그때 모두 검출). 놓친 1개는 미래 교체 검사가 원래 역할을 섞어 쓰게 한 변형이다. 그런데 d 시점에 쓰이는 음의 역할은 어느 쪽이든 같아서 결과가 같은 등가 변형이었다. 결함이 아니므로 위 양성 대조로 대신했다
- **통계 스크립트의 후보 줄이기:** 곡의 최장 음 길이와 recent 창 중 큰 값 + 1 ms 안에서 시작한 조건 음만 등록 함수에 넘긴다. 그 밖의 음은 결과에 들어갈 수 없다. 전체 음을 쓰는 replay가 모든 타깃에서 이를 다시 확인한다(창을 잘못 줄이는 변형은 검출됨)
