## 질문 (하나)
**이 특정 공개 체크포인트가 지금 BebopNet(N1/N2)보다 사용자 목표에 맞는가.** 목표는 코드에 맞고, 릭이 들어가고, 연결이 자연스러운 비밥 솔로다.

- 학습 데이터, epoch, 표현이 모두 다르다. 그래서 "명시 코드 조건 구조가 더 낫다" 같은 아키텍처 인과 주장은 하지 않는다
- 품질 판정은 사용자 청취다. 자동 지표는 진단만 한다

  - HSE 포크와 `model.py`·`layers.py`가 같다(git blob 일치 확인)
  - 8마디 체크포인트를 고른 이유: N1/N2와 같은 길이다. 데이터를 보기 전에 정했다
- **MINGUS**: 현재 구현(원 저장소와 HSE runner)은 생성할 때 WJazzD 원본(XML 약 90 MB + CSV 약 20 MB)으로 어휘와 코드 사전을 다시 만든다. 추론에 원본 전체가 본질적으로 필요한 것은 아니고, 구현이 어휘 재생성에 의존하는 것이다
  - HF 모델 카드 파일 목록에는 token-ID 사전이나 metadata 파일이 없다. `*_state.pt`는 학습 재개용 체크포인트로 설명돼 있고, 내용은 받지 않아 모른다
  - 사전을 임의로 재구성하거나 ID 순서를 추정하지 않는다
  - **현재 blocked.** 데이터 다운로드가 승인되면 같은 계약으로 별도 실행한다
- **기준**: N1(BebopNet 기본), N2(BebopNet 화성 탐색). 이미 사용자에게 올린 파일 그대로다

## 실행 계약 (T1-a)
- **진행:** Gm7–C7–Fmaj7–Fmaj7 × 2(8마디), 128 BPM, 같은 guide 컴핑(C3–B3), 같은 피아노 렌더
- **CMT 입력:**
  - 16분음표 격자, 마디당 16프레임. 프레임마다 그 순간 코드의 12차원 크로마를 넣는다. 마지막 프레임 다음 칸(129번째)은 진행을 이어서 Gm7로 둔다
  - 시작 마디: HSE 기본값인 `tonic_held`(첫 프레임 G4 onset, 나머지 15프레임 sustain)
  - 샘플링: 체크포인트 hparams의 `topk: 5`(pitch). rhythm은 원 코드대로 top-3
  - 출력 시간은 CMT 고정 격자(120 BPM 상당)이므로 128 BPM으로 비례 변환한다
- **처리:** 원 출력(raw)과 처리본을 따로 저장한다. 처리본은 아래 세 가지만 바꾼다
  - 128 BPM 시간 변환
  - velocity 90 고정(N1/N2와 같다. BebopNet도 출력 velocity가 전부 90이었다)
  - 2:1 스윙(`lick_bank.swing`). CMT 출력은 스트레이트 16분음표고, BebopNet은 자체 스윙 출력이다. 스윙은 렌더 처리이지 모델 출력이 아니라고 표시한다
  - 음 재선택, 충돌 정리, 마스크, 옥타브 이동은 하지 않는다. 음역이 피아노 오른손에서 벗어나도 그대로 둔다
- **seed:** 1–4를 생성한다. 청취에 올리는 것은 seed 1·2로 미리 고정한다. 좋은 샘플을 고르지 않는다. 실패, 무음, 오류도 그대로 보고한다

## 코드 반응 진단 (T1-c, 보고만)
- 같은 seed로 진행 두 개를 넣는다
  - P = Gm7–C7–Fmaj7–Fmaj7
  - Q = Gm7b5–C7–Fm7–Fm7. 근음은 그대로 두고 품질만 바꾼 진행이다
- P와 Q가 다른 음(Gm7의 D ↔ Gm7b5의 Db, Fmaj7의 A·E ↔ Fm7의 Ab·Eb)만 센다. 출력 Y_P와 Y_Q 각각이 자기 조건 쪽 음을 더 많이 쓰는지 2×2 표로 본다
- 출력이 달라졌는지만 보는 비율은 성공 기준으로 쓰지 않는다

## 청취 (T1-d)
- 익명 쌍대 선호: N1, N2, CMT seed 1, CMT seed 2를 무작위 글자로 섞어 올린다. 매핑은 페이지에서 접어 둔다
- 사용자에게 받을 것: 전체 선호, 그리고 화성·릭·연결감 메모를 따로
- 실제 비밥 피아니스트의 오른손을 같은 피아노로 렌더한 기준 클립 하나를 함께 둔다(이미 있는 RH_Barry). 음색이나 렌더에 대한 불만을 모델 문제와 분리하기 위해서다
- 올리기 전에 모든 클립을 마디별 음 단위로 덤프해 읽는다(음 이름, 코드 도수, 컴핑과 실제 울리는 음정, 길이)

## 결과 (`scripts/t1_cmt_generate.py`, CMT `paper/8bars`, epoch 정보는 report.json)

### 사전 등록 설정(`tonic_held`)은 긴 음 위주
- 8마디에 음이 12–33개였다(seed 1–4, P·Q). BebopNet N1/N2는 47·57개다
- 리듬 출력과 음높이 출력은 서로 맞았다(onset 프레임과 음 index 일치). 디코딩 오류가 아니다
- 음 위치를 보면 온음표·2분음표가 대부분이고 A4·G4 반복이 많다
- **원인 후보:** 시작 마디가 온음표 하나라서 모델이 그 리듬을 따라갔을 수 있다. 이번 seed에서 관측한 것이지, 텍스처 잠금을 보편적으로 증명한 것은 아니다
- **시작 조건이 BebopNet과 크게 달랐다.** BebopNet은 8분음표 헤드 16마디를 받았다. 사전 등록 때 이 차이를 보지 못했다

### 사후 변형(`head`, 사전 등록 아님으로 표시)
- 시작 마디를 BebopNet이 받은 헤드의 첫 마디(Gm7 위 8분음표 G–A–Bb–C–D–C–Bb–A)로 바꿨다. 나머지 계약은 같다
- 음 39–54개로 BebopNet과 비슷해졌다
- 이것은 "시작 텍스처를 가깝게 맞춘 사후 탐색"이지 조건을 동등하게 만든 것이 아니다. 문맥 길이(1마디 대 16마디)와 내용이 여전히 다르다
- 그래서 이 비교는 각 공개 체크포인트를 지원하는 입력으로 쓴 실사용 비교일 뿐이다. 구조나 모델 자체의 우열에 대한 인과 주장은 하지 않는다
- 음 단위 덤프(seed 1·2, 처리본):
  - seed 1: 스케일 밖 음 2(둘 다 해결), 단9도 충돌 1, 0.1초 미만 음 0, 같은 음 연속 7. 순차 진행과 코드톤이 대부분이고 음역이 D4–D5로 좁다. 반음 접근 같은 비밥 어휘는 드물다
  - seed 2: 판정 스케일 밖 음 5, 그중 다음 음으로 해결 안 됨 3. 단9도 충돌 3, 0.1초 미만 음 7
    - 덤프의 "스케일 밖"은 `harmony_bias.SCALE` 기준이다. 이 스케일은 회피음을 뺀 것이다. 그래서 C7 위 F(11음)는 믹솔리디안 안의 음인데도 회피음이라 "밖"으로 세어졌다. Fmaj7 위 Eb(b7)은 실제로 스케일 밖이다
    - 컴핑과의 충돌, 그리고 해결 여부는 스케일 소속과 따로 판정한다. 마지막 음처럼 뒤에 음이 없으면 unknown이다
    - 0.1초 미만 음 7개는 16분음표에 스윙을 넣은 렌더 처리에서 생겼다. 오류로 보고 자동으로 늘리지 않는다(#1669 전례)
  - 단9도 충돌 대부분은 **Fmaj7에서 솔로 F 아래 컴핑 E3** 패턴이다. BebopNet N1/N2와 같다. 컴핑 쪽 원인 후보라는 근거가 하나 늘었다(같은 솔로 + 컴핑만 바꾼 A/B 전까지 확정 아님)

### 코드 반응 2×2 (T1-c, seed 1–4, 생성된 2–8마디만)
계산: 생성된 2–8마디 중, P와 Q의 코드가 다른 마디(Gm7/Gm7b5, Fmaj7/Fm7)에서 시작하는 음만 센다. 그 마디 코드의 구별 음인지 본다. 두 진행이 같은 C7 마디는 세지 않는다. 원자료는 `t1_cmt_2x2.json`이다.

- P음 = D(Gm7), A·E(Fmaj7). Q음 = Db(Gm7b5), Ab·Eb(Fm7)
- 8조건 모두 양방향으로 자기 조건 쪽 구별 음을 더 썼다. 다만 tonic_held seed 2(2/0 대 0/2)처럼 증거량이 작은 셀이 있다
- 결론은 "이 두 진행, 이 8조건에서 방향성을 관측했다"까지다. 화성 준수의 일반화는 아니다
- P와 Q는 두 품질(m7→m7b5, maj7→m7)을 동시에 바꾼다. 하나씩 분리하려면 후속 단일 품질 개입이 필요하다
- 출력 품질 주장이 아니다. "코드 품질이 바뀌면 그 코드의 구별 음으로 바뀐다"는 반응만 확인한 것이다
- 현 13.4M Music Transformer는 코드가 달라도 같은 출력이 10–37% 나왔다. 단, 측정 방식이 달라서 수치를 직접 비교하지 않는다
