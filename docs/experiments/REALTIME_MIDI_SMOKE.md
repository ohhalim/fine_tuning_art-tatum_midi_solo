# 실제 시계·가상 MIDI 독립 캡처 smoke (#1747) — 사전 등록

가상 시각에서 MLX 생성과 송출 계약을 연결해 확인했다(#1743). 재타격 정책(#1745)과 연주 가능한 음 정책(#1747 1부)도 고정했다. 이 단위는 처음으로 **실제 시계**로 MIDI를 내보내고, **별도 프로세스가 그것을 캡처**해서 기대한 이벤트열과 비교한다. 실물 DAW나 신스 동작, 음악성, 코드 반응은 주장하지 않는다.

## 질문

1. 생성(producer)과 송출 시계를 분리해 가상 MIDI 포트로 내보내면, 독립 캡처가 기대 이벤트열(`midi_out`)을 빠짐없이 순서대로 받는가?
2. 예약 시각, 실제 송출 시각, 캡처 시각은 각각 얼마나 차이 나는가?
3. producer가 중간에 죽어도 음이 남지 않는가?

## 구성 (세 프로세스)

| 프로세스 | venv | 하는 일 |
|---|---|---|
| producer `scripts/rt_producer.py` | t3_aria(MLX) | #1743 루프를 실제 시계로 돌린다. 블록 시작 시각(W + k·B)까지 기다렸다가 `fill_block` → 확정 음을 JSON 줄로 stdout에 낸다 |
| 송출기 `scripts/rt_sender.py` | main | 가상 MIDI 출력 포트를 만든다. stdin을 읽는 스레드와 시계 루프를 분리한다. 음악 시각을 단조 시계로 바꿔 `Scheduler`를 tick하고, 새 `midi_out` 항목을 한 번씩만 포트로 보낸다 |
| 캡처기 `scripts/rt_capture.py` | main | 그 포트를 입력으로 열어 도착한 메시지와 시각을 기록한다 |

- 묶음 실행은 `scripts/rt_smoke_run.py`가 한다. producer의 stdout을 송출기의 stdin으로 잇는다
- **시계:** 세 프로세스 모두 `time.monotonic_ns()`를 쓴다. macOS에서 이 값은 시스템 전체 단조 시계(mach_absolute_time)라 프로세스끼리 비교할 수 있다. 확인용으로, 송출 → 캡처 차이가 음수로 크게 나오면 시계 불일치로 표시한다
- **시작:** producer는 cold 사전 버퍼(첫 블록의 확정 지평 + 한 블록 추측)를 만든다. 그 뒤 `start`(음악 기준 시각 t0, 벽시계 기준 W = 지금 + 1초)를 보낸다. 첫 블록의 확정 음은 W 전에 보낸다. 송출기는 캡처기가 포트를 열었다는 신호를 받은 뒤에만 송출한다
- **블록:** 128 BPM 반 마디(937.5 ms), 확정 지평 H = now + B + 1박, 추측 한 블록, 블록당 최대 64토큰. 형식 마스크와 #1726 샘플러를 쓰고, `<D>`·`<E>`는 막는다. 4마디마다 되돌리기로 코드 입력을 흉내 낸다(제어 토큰 없음)
- 확정 음은 `playable()`을 거쳐 예약한다. 버린 음(세기 0)과 늘린 음(길이 0)의 수를 기록한다
- **종료 경로:** 송출기는 `end`를 받든, stdin이 끊기든(EOF), 오류가 나든 `finally`에서 `Scheduler.stop()`을 부른다. 대기를 취소하고 소유 음높이에 off를 보낸 뒤 포트를 닫는다

**재리뷰 반영 (아스트라 #1749 재리뷰 MEDIUM):** 정리 단계의 best-effort flush가 남은 off뿐 아니라 아직 안 보낸 note-on까지 보냈다. 같은 tick에서 on60 성공 → on64 실패 → on67 미시도 상태로 정리하면 `[on67, off60, off64, off67]`이 나갔다. 정지 뒤에 새 음이 시작된 것이다. 이제 정리 단계는 안 보낸 note-on을 보내지 않고 `cancelled_unsent_on`에 기록하며, off만 보낸다. 이 경우 `clean_stop = false`이고, 분석의 예상↔송출 비교(A1a)에 실패·취소 수를 함께 적는다. 3음 회귀를 더했다(전체 47개).

**두 번째 재리뷰 반영 (아스트라 #1749 재리뷰 MEDIUM, 0032eb11):** main 루프가 큐를 비운 뒤 종료 확인보다 tick을 먼저 불렀다. 그래서 end 없는 EOF나 깨진 입력 줄 뒤에도 마감이 온 note-on이 나가고 `clean_stop = true`로 남을 수 있었다. 옛 순서로 재현하면 `[on60, off60]`, `clean_stop: true`다. 이제 `Sender.process`가 받은 메시지를 모두 처리한 뒤, 비정상 종료면 tick 없이 끝낸다. 정상 end는 예약된 음을 끝까지 내보낸다. main은 이 함수만 부른다.

- **검증 근거:** 가짜 시계·가짜 포트로 main과 같은 경로(reader → queue → drain → process → cleanup)를 도는 회귀 4개를 더했다. 전체 51개 통과(아스트라도 고정 커밋으로 51개 직접 실행). **실제 시계 본실행은 다시 돌리지 않았다**
- **과거 B 원자료의 한계:** 송출기가 EOF를 받은 시각을 기록하지 않았다. 그래서 B에서 EOF 이후에 note-on이 나갔는지는 판별할 수 없다. B의 "음이 남지 않았다"는 결론은 그대로지만, "정지 뒤 새 음이 시작되지 않았다"는 이번 원자료로 말할 수 없다
