# 관측 왼손 문맥: 블록별 전체 prefill 마감 측정 (사전 등록)

작성 2026-10-18 10:4x KST. 이슈 #1791. 측정만 합니다. 청취·학습·새 자료 없음. 음악 품질과 무관합니다.

## 1. 왜

- Aria 실시간 경로는 생성 → 가상 MIDI 송출 → 독립 캡처까지 확인됐습니다(#1743, #1747). 빠진 것은 **키보드 입력**입니다
- #1773 계약은 관측한 사람 왼손을 오른손 문맥의 과거 위치에 끼워 넣습니다. 그러면 기존 KV가 무효가 되어, 블록마다 **전체 prefill**을 해야 합니다(계약 문서 "KV" 행)
- 블록 계약(#1770)상 새 입력을 반영한 블록은 시작 s_k에서 마감 s_k + 1박(128 BPM 468.75 ms) 안에 확정·예약해야 합니다. 전체 prefill + 그 블록 토큰 생성이 이 안에 드는지 잰 적이 없습니다

## 2. 질문 (하나)

#1773의 b 문맥(오른손 이력 + 관측 왼손)을 블록마다 전체 prefill하고 그 블록 토큰을 생성할 때, MLX에서 1박(468.75 ms) 안에 끝나는 요청은 얼마나 되는가?

## 3. 측정 (실행 전 고정)

- 모델: Aria medium `t3_aria/ckpt/model-gen.safetensors`, `aria.inference.model_mlx.TransformerLM`, float32, KV 캐시(#1743과 같은 로드 방식). M1 Max
- 토큰: dev 곡 export(`lh_request_export_run3/requests/NNN.json.gz`)의 실제 Aria 토큰열. 가장 긴 곡을 쓰고, 그보다 긴 길이는 두 번째로 긴 곡을 이어 붙입니다(계산 비용은 내용과 거의 무관하다고 보고, 한 번 다른 곡 토큰으로 같은 길이를 재서 확인합니다)
- 길이 격자 L: 128, 256, 512, 1024, 1536, 2048, 2560, 3072, 3584, 4000
- 길이마다: 준비 1회(버림) + 측정 5회. 1회 = 위치 0부터 L토큰 전체 prefill(마지막 logits까지 `mx.eval`) → 이어서 48토큰을 한 개씩 decode(KV 사용, 매 토큰 `mx.eval`)
- 기록: prefill ms, decode 토큰별 ms(첫 토큰 따로), 열 압력(길이마다 전후), RSS
- 내용 확인: L = 2048에서 다른 곡 토큰으로 prefill 5회를 따로 재서 중앙값 차이를 적습니다

## 4. 대입 (측정 뒤, 규칙은 지금 고정)

- dev 4곡 1,314 요청(`lh_context_run1/arms`, status ok)의 b 문맥 길이 L_b = `label_start.b`와 블록 생성 토큰 수 n = `win_labels + boundary_labels`
- 예측 시간 = prefill(L_b) + n × decode 중앙값(첫 토큰은 따로 더함). prefill(L_b)는 격자 중앙값의 선형 보간
- (리뷰 교정) 목적은 "블록 토큰 n개를 생성해 예약"입니다. 전체 prefill의 마지막 logits가 이미 첫 토큰을 예측하므로 추가 forward는 **n − 1회**입니다. v1은 n회를 더했습니다(7.2 참고)
- 보고: 예측 시간 중앙값·p90·최대, 468.75 ms 안 비율. 같은 값을 a 문맥 길이로도 냅니다(왼손이 늘린 몫을 보려고)
- 이것은 **예측**입니다. 실제 실시간 루프에서 잰 끝-끝 지연이 아닙니다. 샘플링·문법 마스크·송출 비용은 빠져 있습니다

### 7.2 대입 (예측)

아스트라 리뷰(msg_ff82232b47e4) M1로 계산을 고쳤습니다. v1 값은 `report.json`의 `prediction_v1`에 그대로 둡니다.

| 계산 | b 문맥 1박 안 | 중앙값 | p90 | 최대 |
|---|---|---|---|---|
| v1(추가 forward n회, 잘못) | 426/1314 (32.4%) | 739.0 | 1375.1 | 1877.9 |
| **v2(n − 1회, decode 격자 전체 중앙값 첫 11.76·이후 11.90 ms)** | **439/1314 (33.4%)** | 727.1 | 1363.2 | 1866.0 |
| 민감도(n − 1회, decode를 문맥 길이별로 보간) | 452/1314 (34.4%) | 724.0 | 1400.7 | 1960.5 |

- a 문맥(오른손만)에 같은 전체 prefill 계산을 하면 v2 34.1%, 중앙값 716 ms입니다. 왼손이 늘린 몫은 작습니다. 문제는 왼손 토큰 수가 아니라 **전체 문맥을 매번 다시 계산하는 것**입니다. 참고로 지금 KV 경로(#1743)는 전체 prefill 없이 블록 재생성만 해서 0.08–0.24초였습니다
- 블록 토큰 15개(중앙값)일 때 1박 안에 들려면 문맥이 약 1,070토큰 이하여야 합니다(근사). b 문맥이 1,024토큰 이하인 요청은 31.4%입니다
- 블록 토큰이 많은 요청은 이 근사의 decode 예산만으로도 1박을 넘습니다. 다만 decode는 문맥 길이에 따라 10.4–14.0 ms로 달라지고 격자 중앙값 하나로 근사한 값이라, "어떤 방식이든 넘친다"거나 모델의 피할 수 없는 한계·토큰 상한의 근거로 쓰지 않습니다(리뷰 M2)
- 측정 격자보다 짧은 문맥: b 49개, a 58개 요청이 128토큰 미만(b 최소 2토큰)이라 128토큰 격자값으로 맞췄습니다. 그 구간은 재지 않았습니다
- p90은 요청 길이 분포에 대입한 예측 시간의 p90이지, 실시간 지터의 p90이 아닙니다. 왼손 문맥이 생성에 실제로 도움이 되는지도 아직 검증하지 않았습니다
- 출처 기록(리뷰 LOW): 입력 arms 4개 파일 sha256과 요청 수(1,314, 다르면 중단), 체크포인트 sha256, aria 저장소 커밋, float32, 기기 정보를 `report.json` `provenance`에 남겼습니다

## 8. 읽기

- 사전 등록 5절 기준으로 **"긴 문맥에서 넘침"**입니다. #1773 계약 그대로 블록마다 전체 prefill하는 방식은 지금 문맥 길이(crop 상한 약 4,000토큰)로는 대부분의 블록에서 1박 마감을 지키지 못한다고 예측됩니다
- 말하지 않는 것: 실시간 키보드 입력이 불가능하다. 이것은 격자 곡선으로 낸 예측이고, 샘플링·마스크·송출 비용은 빠졌습니다
- 설계 선택지(결정 아님, 아스트라와 정함)
  1. 문맥 상한을 약 1,000토큰으로 줄인다(crop 계약 #1758 변경). 문맥이 짧아지면 음악적 일관성에 영향이 있을 수 있음
  2. KV를 살리는 왼손 삽입: 이미 계산한 앞부분은 두고, 새로 들어온 왼손 음이 끼는 위치부터만 다시 계산한다. 다만 #1773의 7.5초 관측 창이 블록마다 밀리면서 오래된 왼손 음이 빠지면 앞쪽이 바뀌어 KV가 깨집니다. 창 대신 "crop 이후 전부 유지"로 바꾸는 계약 변경이 함께 필요
  3. 마감 완화(D = 2박): 스케줄 대기가 길어짐(#1771 B·D안의 반대 방향)
  4. 블록 토큰이 많은 경우의 처리(토큰 상한이나 추측 생성분 재사용 규칙). 이 근사 예산상 넘치는 블록이 있다는 것까지이며, 원인·필요성은 따로 확인해야 함
- 아스트라 결정: 선택지 1(문맥 축소)·3(2박 지연)·4(밀도 상한)는 문맥·반응·사용자가 원한 긴 릭을 깎는 제품 tradeoff라 비용 숫자만으로 고르지 않고 기본값을 바꾸지 않습니다. 다음 단위(#1793)는 선택지 2를 지금 계약 그대로 감사합니다
