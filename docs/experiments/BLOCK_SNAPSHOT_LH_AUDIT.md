# 런타임 블록 관측 시각에서도 왼손 역할 쌍을 미래 정보 없이 만들 수 있나 (#1754) — 사전 등록

작성 2026-10-15. 학습 없음, 모델 없음. **통계를 돌리기 전에 고정한다.** 아스트라가 사용량 한도에 걸려 있던 약 1시간 동안 Claude가 준비했다. 아스트라 설계 리뷰(@77843002)를 받아 M1과 Q1–Q4를 실행 전에 반영했다(84fdae25, 아래 "설계 리뷰"). 실제 자료 통계는 그 뒤 한 번만 돌린다.

## 왜 하나

#1750(PR #1751)은 "음마다 1박 앞에서 결정한다면" 세 규칙 모두 미래 정보 없이 쌍을 만들 수 있다고 판정했다. 아스트라 리뷰 M2대로, 그것은 **음별 이상적 결정 시각 진단**이다. 현재 런타임은 블록 시작에 한 번 관측하고 그 블록의 음을 모두 만든다. 그래서 한 블록 안의 늦은 음일수록 실제 관측은 1박보다 훨씬 이르다. 학습 자료를 만들기 전에 이 계약을 고정하고, 그 기준에서도 쌍이 만들어지는지 따로 확인한다.

## 블록 관측 계약 — `scripts/block_contract.py`

음악 시각(ms) 기준이다. 128 BPM에서 블록 B = 937.5 ms(반 마디), 1박 = 468.75 ms다(`aria_mlx_stream_loop.py`).

| 블록 | 관측 시각 s | 확정하는 onset 구간 | onset − s |
|---|---|---|---|
| 0 (cold prebuffer) | 늦어도 `t0 − 1000`(상한) | `[t0, t0 + B + 1박)` | 1000–2406.25 ms 이상 |
| k ≥ 1 | `t0 + k·B` | `[t0 + k·B + 1박, t0 + (k+1)·B + 1박)` | 468.75 – 1406.25 ms(오른쪽 끝 미포함) |
| onset < t0 | — | primer. 생성하지 않는다 | — |

- 근거 코드: `rt_producer.py`의 `h0 = t0 + BLOCK + BEAT`, `now = t0 + k * BLOCK`, `h = now + BLOCK + BEAT`. `stream_contract.commit_until`은 onset < horizon인 음만 확정한다
- 블록 0은 재생 시작 1초 전(`LEAD_S`)보다 먼저 만들어진다. `t0 − 1000`은 실제 cold 관측 시각이 아니라 **가능한 가장 늦은 시각(상한)**이다. prebuffer 자체의 실행 시간만큼 실제 관측은 더 이르다
  - 위상 t0가 최대 703.125 ms라서 cold 관측 시각은 모두 0보다 앞이다. 원 MIDI onset이 0 이상이므로 cold 타깃의 조건은 항상 빈다. 더 앞당겨도 같다(아스트라 Q2). 스크립트가 이 가정을 assert로 건다
  - 실제 primer history가 있는 초기화나 cold 계산 시간 보장은 이 감사에서 뺀다. 이후 자료에서는 cold를 별도 초기 조건으로 정해야 한다
- **이 계약이 요구하는 되돌리기 규칙(제안, 아직 구현 안 됨):** 블록 시작 s_k마다 그때까지의 관측으로 모델이 받을 **조건 표현 전체**를 다시 계산한다. 미확정 토큰을 생성할 때 쓴 표현(s_(k−1)의 것)과 다르면 그 토큰을 버리고 s_k에서 다시 생성한다(`must_regenerate()`)
  - 비교 대상은 입력 이벤트가 아니라 표현이다. `recent` 창이 만료되면 새 note-on·note-off·역할 이벤트가 없어도 조건이 바뀐다. 아스트라 M1의 예: g3 음 on 500/off 600, snapshot 937.5 → 1875에서 `recent`가 {음0}에서 빈 집합으로 바뀐다. 상대 나이나 시간 특징을 입력에 넣으면 그 변화도 비교에 들어간다. 두 경우 모두 fixture로 고정했다
  - 지금 producer는 다음 블록을 미리 생성해 두고, 정해진 코드 블록에서만 되돌린다. 이 규칙이 없으면 확정음의 관측이 한 블록 더 오래될 수 있다
  - 이 규칙이 있으면 모든 확정음의 조건은 자기 블록 시작 시점의 표현이다. `snapshot()`이 돌려주는 값이 그것이다
  - 토큰만 버리면 충분한지, KV 캐시를 더 앞까지 무효화해야 하는지는 조건 주입 방식에 따라 달라진다. 주입을 만들 때 따로 검증한다. 여기서는 보장하지 않는다

## 결정 시각 묶음 `runtime_block`

| 이름 | 결정 시각 d | 쓰임 |
|---|---|---|
| `block_p0` – `block_p3` | 위 계약의 관측 시각. t0 = 0, 234.375, 468.75, 703.125 ms(블록의 1/4 간격 위상) | **판정** |
| `lead_worst` | onset − 1406.25 ms. warm 블록(k ≥ 1) 최대 간격에 해당하는 고정 지연 진단 | 기술 통계만 |

- 곡 안에서 블록 격자가 어디서 시작할지는 정해져 있지 않다. 그래서 위상 4개를 모두 본다
- onset < t0인 타깃은 그 결정에서 빼고 수를 따로 센다(primer)
- 위상마다 cold(블록 0) 타깃 수와 그중 조건이 비어 있지 않은 수를 따로 세고, warm 비율을 따로 적는다(아스트라 Q2)
- `lead_worst`는 관측이 오래됐다는 뜻일 뿐, 어느 위상의 비어 있지 않은 비율의 최악값이나 하한도 아니다. 조건은 d에 대해 단조롭지 않다. 예: g3 음 on 500/off 700, 타깃 2000이면 d_worst 593.75에서는 sounding = {0}이고, 위상 0의 실제 snapshot 937.5에서는 빈 집합이다. cold 블록에는 이 warm 기준을 적용하지 않는다(아스트라 Q4)
- 비교 기준으로 #1750의 음별 1박 결과(`causal_lh_audit/report.json`)를 함께 적는다. 다시 계산하지 않는다
