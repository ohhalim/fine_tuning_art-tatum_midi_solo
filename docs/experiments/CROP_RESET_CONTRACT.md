## 질문 (하나)

블록 요청 문맥이 실시간 KV 용량(4096)을 넘을 때, 요청 시작에서 확정 이력을 잘라 다시 prefill할 수 있나? 그때 다음 네 가지가 지켜져야 한다.
- 남긴 토큰의 절대 시각이 원래와 같다
- 위치별 조건 provenance가 원래와 같다
- 미래 suffix가 자르는 위치를 바꾸지 못한다
- 모든 위치가 용량 아래에 있다

이 조건을 지키는 계약을 고정할 수 있는지 묻는다.

## 계약 — `scripts/crop_contract.py`

| 항목 | 정의 |
|---|---|
| 자르는 위치 | `<T>` 바로 뒤에서만 자른다. Aria abs onset은 segment 기준이므로, `<T>` 뒤에서 자르면 남긴 토큰을 하나도 바꾸지 않는다. 음 경계에서 자르는 것도 segment 원점을 따로 보존하면 원리상 가능하지만, 이번에는 그 복잡성을 뺀다 |
| 판단 | `needs_crop(확정 길이) = 확정 길이 + 2·CAP + 3 > CAPACITY`(예약분 131). 요청 시작에서, 생성 전에 판단한다. 1회차의 `+ 2·CAP`는 틀렸다(아래 "이탈 1") |
| crop 경로 | 미확정 토큰을 버리고(되돌리기와 같다) reset 뒤 다시 생성한다. 학습 재연에서도 같다 |
| 자를 `<T>` 고르기 | ① 헤더 + 남길 길이 ≤ KEEP_TARGET(2048)인 가장 이른 `<T>`(목표 아래에서 이력을 가장 많이 남긴다) ② 없으면 안전 상한을 만족하는 가장 늦은 `<T>`(목표는 놓치지만 안전하다) ③ 그것도 없으면 `CapacityFailure`. 음을 자르거나 시계를 초기화하지 않는다 |
| 시간 | `base_ms`는 누적값이다. `base_ms += 제거한 <T> 수 × 5000`이고, 자른 `<T>` 자신도 센다. 절대 시각 = `base_ms + local_segment × 5000 + onset`. s_k, t0, 블록 k, horizon은 세션 시계를 쓰고, 확정 판정은 `h − base_ms`와 비교한다. 스케줄된 note-off는 scheduler 소유라 움직이지 않는다 |
| 헤더 | 새로 만든 `[prefix, <S>]`다. 옛 헤더와 primer는 다시 붙이지 않는다. 다시 붙이면 제거한 시간대가 되살아난다 |
| 조건 | input 위치 q는 label q+1을 확정한 요청의 payload를 갖는다. crop 뒤에는 위치마다 다음과 같다 |

crop 뒤 위치별 조건:
- prefix 위치(label `<S>`)는 cold다
- `<S>` 위치는 첫 유지 토큰을 예측한다. 그래서 그 토큰을 확정한 요청의 조건을 갖는다. 자르기 전 cut `<T>` 위치가 갖던 값과 같다
- 유지 위치는 과거 provenance를 그대로 유지한다
- p0와 continuation은 현재 요청의 조건을 갖는다. 유지 이력이 비면 `<S>` 위치가 p0다

- **판단식 근거(이탈 1 뒤, 귀납):**
  - fill_block 한 호출은 최대 CAP개를 샘플한다. 투기 생성은 coverage가 h_spec에 처음 닿을 때 멈추는데, 요청 k의 h_spec은 요청 k+1의 h다
  - 그래서 다음 h를 넘는 원소는 음 하나(3토큰) 또는 `<T>` 하나뿐이다
  - 따라서 호출 시작 때 미확정 토큰은 최대 CAP(직전 호출이 샘플한 수) + 3(그 앞 호출에서 넘어온 원소)이다. 되돌리기나 crop은 이 수를 줄이기만 한다
  - 호출 안에서 CAP개를 더 샘플해도, feed 위치는 `확정 + (CAP + 3) + CAP − 1`보다 작다
  - 그러므로 `확정 + 2·CAP + 3 ≤ CAPACITY`면 안전하다. 딱 맞는 하한은 +2이고, +3은 한 칸 여유다
  - 이 근거는 지금의 문법(3토큰 음), horizon, fill_block에서만 성립한다. 문법·종료·재시도가 바뀌면 상한을 다시 본다. forward 가드(위치 < 4096)는 유지한다
  - 실시간에는 미확정 토큰 수를 알 수 있다. 하지만 학습 재연에서 그 수는 정답 미래 토큰 수다. 그래서 판단에 넣지 않는다(아스트라 5번)
- `choose_cut`은 사전조건을 검사한다. keep_target + 예약분 ≤ 용량, 헤더 + 예약분 ≤ 용량이 아니면 거절한다(아스트라 LOW)
- **KEEP_TARGET 2048은 고정 engineering setting이다.** reset이 반복되는 횟수를 줄이려는 hysteresis이고, 성능 최적화를 주장하지 않는다. 실제 full-prefill 지연은 이번에 입증하지 않는다
- window + boundary가 64를 넘는 요청(#1756 3회차 107개)은 crop과 별개인 budget 제한이다. loader에서 조용히 자르지 않는다

## 이탈 1 — 판단식 2·CAP가 틀렸다 (아스트라 #1759 리뷰 H1)

- **1회차의 오류:** 판단식 `확정 + 2·CAP > 4096`은 "직전 호출이 남긴 미확정 토큰 ≤ CAP"라는 전제를 썼다. 이 전제가 거짓이었다
  - 조건이 바뀌지 않으면 되돌리기가 없다. 그러면 그 앞 호출의 경계 음이 남은 채로 다음 호출이 CAP를 더 샘플할 수 있다
  - 아스트라의 재현: 확정 3968 + 미확정 67(경계 음 3 + 같은 onset 64)에서, 다음 호출이 64개를 더 샘플하면 최대 feed 위치가 4097이다. Claude가 실제 fill_block으로 같은 값을 재현했다
  - 실제 forward 가드가 ValueError로 막기는 하지만, 그러면 연주가 멈춘다
- **1회차 결과의 한계:** R1–R4 = 0과 crop 235회는 틀린 판단식으로 얻은 값이다. R4는 같은 `needs_crop`을 다시 쓴 "설정 상한 충족"이라, 실제 feed 안전을 보지 못했다. 1회차 시험 11개도 CAP를 생성 중단 조건으로 쓰지 않아 이 경로를 놓쳤다
- **수정:**
  - 예약분을 2·CAP + 3으로 바꿨다(근거는 위 "판단식 근거")
  - `choose_cut`에 사전조건 검사를 넣었다
  - 실제 fill_block을 쓰는 시험 두 개를 더해 시험은 13개다
    - 반례 회귀: 자르지 않는 가장 큰 확정 길이에서 최대 feed가 4094이고, 한 칸 늘리면 crop한다
    - 연속 호출 퍼징: 300개 세션, 3,000개 넘는 호출. 매 호출 시작 때 미확정 ≤ CAP + 3이고, 모든 feed 위치가 용량 아래인지 본다
  - 변형으로 확인했다. 예약분 2·CAP와 2·CAP + 1은 반례 회귀에서 실패하고(feed ≥ 4096), 딱 맞는 2·CAP + 2는 통과한다
- 2회차 점검은 아래에 적는다
