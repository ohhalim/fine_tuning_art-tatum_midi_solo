# T4a: Aria가 넣어 준 코드 품질에 반응하는가 — 무마스크 짝 프로브 (사전 등록)

작성 2026-10-08. 아스트라 #190·#202 설계. 새 학습 없음. `musical_quality_verified: false`.

## 질문 (하나)
같은 연주 맥락 끝에 근음·음역·시각·세기가 같고 **품질만 다른** 코드(maj7 대 m7)를 넣었을 때, 이어지는 짧은 생성이 그 코드의 구별 음(3·7음) 쪽으로 반응하는가. 그리고 그 생성의 배치 1 블록 준비 시간은 얼마인가.

- 코드 반응만 본다. 음악 품질, 티그랑 스타일, 실시간 성공은 주장하지 않는다
- 사용자 기준 곡이 아직 없으므로 새 스타일 주장을 하지 않는다

## 맥락 (history, 생성 전 고정)
- 기존 프라이머 4개를 층으로 쓴다: P2(Joy Spring), P3(Bud-Like), TA(What The Waves Brought), TB(The Legend Of The Moon)
- Aria가 디코드한 프라이머 MIDI(`out/*_prompt_decoded.mid`) 그대로 쓴다. 결과를 보고 다시 고르지 않는다

## 사람 코드 입력 (시간 계약)
- **근음:** 프라이머 마지막 1초의 최저음 pitch class(생성 전 고정). P2 B, P3 G, TA C, TB G
- **시각:** 프라이머 마지막 onset + 0.20초에 친다. 길이 0.9375초(128 BPM 반마디)
- **보이싱:** 근음 C2–B2 1개 + 3음·7음 C3–B3. velocity 60
- **P = maj7(3음 +4, 7음 +11), Q = m7(3음 +3, 7음 +10).** 근음, 음역, 시각, 세기, 음 수가 같고 3·7음만 반음 다르다
- 코드는 미래 정보가 아니다. 모델은 코드 onset까지 들은 뒤 그 뒤를 이어 친다. 실제 연주에서는 이 반응이 지연만큼 늦어진다. 그 지연은 아래에서 따로 잰다

## 생성
- 공식 sampler(`sample_batch`), 배치 1, temp 0.98, **min_p 0(이 실험의 조건. 전역 기본값 아님)**, 마스크 없음, 반복 패널티 없음, force_end 끔
- 생성 토큰 48개(약 16음). seed 1–4, `torch.manual_seed`
- 4 맥락 × 2 품질 × 4 seed = 32개, 전부 보고한다

## 측정
- **평가 대상:** 생성 음 중 onset이 [코드 시각, 코드 시각 + 0.9375초)인 음. 코드 음 자체는 입력이라 제외한다
- **2×2:** 생성 음 중 P 구별 음(근음 +4, +11 pitch class) 수와 Q 구별 음(+3, +10) 수를 조건별로 센다. seed가 같은 P와 Q가 짝이다. 대상 음 수, 비율을 함께 적는다
  - 창 안 생성 음이 2개 미만이면 "판단 불가"로 적는다
- **블록 준비 시간(배치 1):** 토큰화 + prefill + 48토큰 decode + detokenize의 전체 wall time. 첫 실행(cold)은 따로 적는다
  - 48토큰이 0.9375초 창을 다 채우는지도 적는다(마지막 생성 onset ≥ 창 끝)
  - 소수 표본의 최댓값은 경험적 값이지 마감 보장이 아니다
- 저장: manifest(체크포인트·패치·입력 해시·seed·조건), 원 토큰, 입력 MIDI, 출력 MIDI

## 판정 (결과 전 고정)
- 보고: 맥락별·seed별 2×2 표, 양방향(Y_P에서 P음 > Q음, Y_Q에서 Q음 > P음)이 몇 쌍에서 나타나는지
- 이 결과는 "이 맥락·이 코드에서 방향성을 관측했다"까지다. 화성 준수의 일반화나 협연 가능 판정이 아니다
- 방향이 안 나오면 "이 조건에서 코드 반응 미관측"으로 기록하고, 마스크나 조건 방식 변경을 바로 해법으로 등록하지 않는다

## 해석 (사전 등록 범위)
- **이 맥락·이 코드에서 약하고 들쭉날쭉한 방향성을 관측했다.** 합산으로는 넣은 코드의 구별 음을 더 썼지만, 같은 seed 짝 16개 중 양방향은 6개다
- T1의 CMT(8조건 모두 양방향)와 직접 비교하지 않는다. CMT는 7마디 내내 코드가 명시 입력이었고, 이번은 코드 하나와 1초 창이다
- **시간:** 블록 준비 약 0.67–0.75초는 반마디(0.9375초)보다 짧다. 하지만 사람이 코드를 친 뒤 계산을 시작하면, 그 반마디의 앞 0.7초는 이미 지나간다. 지금 런타임 예산(블록 시작 전 약 419 ms)보다도 길다. 다음 블록을 미리 만들거나 KV 캐시를 블록 사이에 재사용하지 않으면, 실시간으로 코드에 반응하기 어렵다(추정, 측정 아님)
- 이것은 음악 품질, 티그랑 스타일, 협연 가능을 판정한 것이 아니다. 마스크나 조건 방식 변경을 해법으로 등록하지 않는다

## 사후 진단: 새 선율 반응인가, 입력 코드 재타격인가 (아스트라 #203, 새 생성 없음)
원자료 `t4a/decompose.json`, 스크립트 `scripts/aria_t4a_decompose.py`. 사전 등록 판정(양방향 6/16)은 바꾸지 않는다. 아래는 사후 진단이며, 품질이나 화성 준수 지표가 아니다.

### 창 안 생성 음 분해 (32개 합산)
| 조건 | 창 음 | 코드 음 재타격 | 같은 pc 다른 옥타브 | 그 밖 | 코드 최고음 위 | P음(재타격 / 그 밖 / 그중 최고음 위) | Q음(재타격 / 그 밖 / 그중 최고음 위) |
|---|---|---|---|---|---|---|---|
| Y_P (maj7 입력) | 140 | 14 | 38 | 88 | 77 | 8 / 22 / 17 | 0 / 9 / 2 |
| Y_Q (m7 입력) | 136 | 16 | 27 | 93 | 83 | 0 / 11 / 4 | 10 / 13 / 11 |

- 앞의 2×2는 양손의 모든 음을 셌다. 그래서 입력 코드 음을 그대로 다시 친 것도 "반응"으로 잡혔다. Y_P의 P음 30개 중 8개, Y_Q의 Q음 23개 중 10개가 입력 코드 음의 정확한 재타격이다
- **재타격을 빼면:** Y_P는 P음 22 대 Q음 9로 방향이 남는다. **Y_Q는 Q음 13 대 P음 11로 거의 사라진다**
- **코드 최고음 위의 새 음만 보면:** Y_P P음 17 대 Q음 2, Y_Q P음 4 대 Q음 11. 방향은 있지만 개수가 적다. "코드 최고음 위"는 오른손 라벨이 아니다

- d(전체) 양수 13/16. d(재타격 제외) 양수 8/16, 0 5, 음수 3
- 맥락마다 다르다. P2(비밥 Joy Spring, 근음 B)에서 가장 일관되고, TB에서는 재타격을 빼면 거의 남지 않는다

### 해석
- **반응의 상당 부분이 입력 코드 음의 재타격이었다.** 재타격을 빼면 m7 쪽 반응은 거의 사라지고 maj7 쪽만 남는다. 솔로 선율이 코드를 따른다는 근거는 약하다
- 최고음 위 새 음에서는 양쪽 방향이 보인다. 다만 표본이 작아서(17/2, 4/11) 결론이 아니다

## 시간 계약 (정정)
- **입력에 미래 정보가 있었다.** 코드 음의 끝 시각(t_c + 0.9375초)이 입력에 들어 있었다. Aria는 음마다 길이 토큰을 쓴다. 그래서 실제로 건반을 누르는 순간에는 모르는 값이다. 처음 문서의 "모델은 코드 onset까지 들은 뒤"는 과장이었다
  - 맥락 쪽도 마찬가지다. 코드 시각에 아직 울리고 있는 맥락 음이 TA 8개, TB 6개다. 맥락 음의 끝이 코드 시각보다 최대 TB 1.98초, P2 0.60초, TA 0.57초 뒤다
- **실시간에서 토큰화할 수 있는 시점**은 두 가지다
  - (가) 키업을 기다린다: 코드를 뗀 뒤에야 길이를 안다. 그동안 반응할 수 없다
  - (나) 키다운 순간에 길이를 외부 규칙으로 정한다: 예를 들어 "반마디 동안 누른다고 가정". 설계 선택이고 아직 정하지 않았다
- **(나)를 가정한 타임라인 (이 실험 실측 기준)**
  - t_c: 키다운
  - t_c + 약 0.01초: 토큰화
  - t_c + 약 0.67초: 생성 완료(배치 1, 매번 prefill. warm 샘플링 중앙값 0.662초, 전체 중앙값 0.674초, 최대 0.747초)
  - 그 뒤: 예약 재생
  - 그 반마디(0.9375초)의 앞 약 0.67초는 이미 지났다. "누르자마자 반응"은 이 조건에서 성립하지 않는다. 다음 반마디에 반영하는 방식이면 반응 지연이 0.94초 이상이다
- **런타임 예산 정정**
  - 앞에서 쓴 "약 419 ms"는 `RUNTIME_N2.md` 설정의 값이다: `start_budget_bars` 0.5 × 반마디 0.9375초 − fetch margin 50 ms(`run_continuous_jazz.py`의 `start_not_before`)
  - 라이브 프리셋(`fl_live.py`)은 `--start-budget-bars 0.9`라서 같은 식으로 약 0.79초다
  - 어느 예산이든 미리 생성(lookahead)하는 시간이지, 누르는 순간의 반응 지연이 아니다. KV 캐시를 블록 사이에 재사용했을 때의 효과는 측정하지 않았다
- **기록 정정**
  - "입력 보존"은 pitch와 onset만 비교했다. end와 velocity는 비교하지 않았다
  - "창 채움"은 마지막 생성 음의 onset이 창 끝을 넘었는지다. 블록 길이 계약과는 별개다
  - cold 0.724초는 모델 로딩 뒤 첫 생성이다. 로딩 시간은 포함하지 않는다
