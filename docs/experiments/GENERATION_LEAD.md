# 생성 선행 3마디 → 1마디 (늦은 fetch) — 사전 등록

작성 2026-09-29. 이슈 #1526. `style_verified: false` · `musical_quality_verified: false` · 가상 CoreMIDI 포트

**이 절은 측정 전에 작성했다.** 구현은 측정 전에 끝냈다.

## 문제 (#1525에서 관측)
연주자 입력이 출력에 반영되기까지 **4마디**(128 BPM 약 7.5초)가 걸린다.
- 스케줄러는 마디 k의 다운비트에 마디 k+1 블록을 가져간다(consumed watermark = k+1)
- producer 선행 한도는 2다(콜드 스타트 때 0·1마디를 둘 다 미리 만들려고 넣은 값)
- 그래서 마디 k의 다운비트에 마디 k+3 생성이 시작되고, 입력 스냅샷도 그때 찍힌다
- 리포트의 `input_to_bar_start_ms`는 6.1–8.4초였다. jam_bot 목표(반주 100 ms, 멜로디 조건 800 ms)와 거리가 멀다

## 변경 (opt-in으로 구현, 기준 통과 시 기본값)
- `OneBarMidiScheduler(fetch_margin_ms=M)`: 마디 b를 **다운비트(b) − M**에 가져간다. None이면 기존 동작이다
- `BarBlockProducer(steady_lead_bars=1)`: 첫 fetch 전(워밍업)에는 선행 2로 0·1마디를 만들고, 그 뒤로는 선행 1이다
- `run_continuous_jazz.py --fetch-margin-ms M`(0–500). 리포트에 `fetch_margin_ms`를 기록한다
- 기대
  - 마디 b 생성은 마디 b−1을 가져가는 순간(다운비트(b−1) − M)에 시작된다. 생성 예산은 약 1마디 − M이다(현재 p95는 마디의 최대 29%, #1523)
  - 마디 r에 도착한 입력은 마디 r+2에 반영된다(도착→연주 시작 1–2마디)

## 측정 (M = 50 ms)
- (a) 반영 지연: `run_live_select_probe.py`, #1525와 같은 조건(쌍 S, 128 BPM, 16마디, seed 42/43/44, 실행 후 12/20/28초 PC 1/0/1)
- (b) 실시간성: Tatum 완성 · 멜다우 #1497 × 128 / 240 BPM × seed 42/43/44 = 12회(`run_tempo_sweep.py`, 코드 primer 2 sub-block)
- (c) 마디 동일성: (b)의 128 BPM 실행과 (a)의 연주 마디를 같은 seed의 기존 실행(선행 3마디)과 비교한다. 입력 음이 없으면 생성은 시점과 무관하다(seed가 마디 번호로 정해짐)

## 판정 (모두 충족하면 `--fetch-margin-ms 50`을 기본값으로 한다)
1. (a) 세 실행 모두에서 보낸 PC 3개가 전부 기록된다. 다운비트 50 ms 이내에 도착한 경우가 아니면 적용 지연(적용 마디 − 도착 마디)이 **2 이하**다
2. (b) 12회 모두 fallback 0, 오류 0, 데드라인 미스 0
3. (c) 연주된 마디가 기존 실행과 **전부 동일**하다(스왑 세션은 해당 어댑터 단독 실행과 비교)

미달하면 opt-in으로만 남기고 원인을 기록한다.

## 결과 — 기준 1–3 모두 충족, **`--fetch-margin-ms 50`을 기본값으로 한다**
원시값: `docs/experiments/generation_lead/`(`probe_seed{42,43,44}.json`, `sweep_report.json`). 원본: `outputs/gen_lead/`.

### 기준 1 — 반영 지연
| seed | 보낸 PC | 기록 | (도착 마디 → 적용 마디, 지연) | 마디별 어댑터 |
|---|---|---|---|---|
| 42 | 3 | **3** | (4→6, **2**), (8→10, **2**), (13→15, **2**) | TTTTTT MMMM TTTTT M |
| 43 | 3 | 3 | 같음 | 같음 |
| 44 | 3 | 3 | 같음 | 같음 |

- 기존 방식(#1525)은 지연 4마디였고 세 번째 PC가 적용되지 않았다
- 입력 도착 → 그 입력을 처음 반영한 마디 시작: **2.3–3.7초**(128 BPM)였다. 기존은 6.1–8.4초였다

### 기준 2 — 실시간성 (12회)
| 모델 | BPM | fallback | 미스 | 생성 p95 ms (seed별) | 마디 ms |
|---|---|---|---|---|---|
| Tatum 완성 | 128 | 0 | 0 | 473 / 458 / 462 | 1,875 |
| Tatum 완성 | 240 | 0 | 0 | 244 / 258 / 277 | 1,000 |
| 멜다우 #1497 | 128 | 0 | 0 | 317 / 396 / 320 | 1,875 |
| 멜다우 #1497 | 240 | 0 | 0 | 241 / 192 / 186 | 1,000 |

생성 예산이 약 3마디에서 약 1마디로 줄었지만, p95는 여전히 마디의 28% 이하다.

### 기준 3 — 마디 동일성
- probe 48마디가 단독 실행과 같다
- sweep 192마디가 선행 3마디 방식의 같은 seed 실행(#1523)과 같다
- 합계 **240/240 동일**하다. 생성 시점만 바뀌고 내용은 바뀌지 않았다

### 판정과 한계
- `run_continuous_jazz.py --fetch-margin-ms`의 기본값을 **50**으로 했다. `--fetch-margin-ms off`로 이전 방식(선행 2, 다운비트 fetch)을 쓸 수 있다
- 남은 지연은 구조상 **최소 1마디 + α**다. 마디 b는 마디 b−1을 가져가는 순간에 생성을 시작하기 때문이다. jam_bot의 반주 100 ms 목표와는 여전히 차원이 다르다. 더 줄이려면 마디보다 작은 단위(sub-block 단위 fetch)나 생성 시작을 늦추는 예측 예산이 필요하다(다음 후보)
- 가상 포트, CPU에서 쟀다. 실물 키보드와 DAW는 쓰지 않았다
