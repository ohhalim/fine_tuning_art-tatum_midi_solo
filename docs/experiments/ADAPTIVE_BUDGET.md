# 적응형 생성 시작 예산 — 사전 등록

작성 2026-09-29. 이슈 #1536. `style_verified: false` · `musical_quality_verified: false` · 가상 CoreMIDI 포트, 합성 부하

**이 절은 측정 전에 작성했다.** 구현은 측정 전에 끝냈다.

## 문제 (#1534)
고정 시작 예산 0.5블록에는 장단점이 있다.
- 부하가 없을 때: 입력 반영이 0.9초로 짧다
- 성능 코어를 모두 쓰는 부하에서: 생성이 2.5–3배 느려져 예산을 넘고, fallback이 블록의 16–28%다
- 예산을 끄면 fallback이 0–3%로 줄지만, 평소 지연이 약 0.5블록 늘어난다

## 변경 (opt-in으로 구현, 기준 통과 시 기본값)
- `run_session(adaptive_start_safety=s)` / `--adaptive-start-safety s|off`
- 블록 b의 예산 = max(β × 블록, s × 최근 4블록 생성 시간 최대)이고, 1블록을 넘지 않는다
- 시작 시각 = fetch(b) − 예산
- 평소에는 s × 최근 최대(약 1.5 × 300 ms)가 β × 블록(469 ms)보다 작아서 고정 예산과 같다. 부하로 생성이 느려지면 그만큼 일찍 시작한다

## 측정 (s = 1.5, 반 마디 블록, β = 0.5)
- (a) 무부하 지연: `run_live_select_probe.py`, #1532와 같은 조건(쌍 S, 128 BPM, 16마디, seed 3, PC 5개). 기준은 #1532 probe(평균 890 ms)다
- (b) 부하 N = 8(`yes` 8개): Tatum 완성 × 128 / 240 BPM × seed 3. 기준은 #1534의 예산 off(fallback 합 3, 미스 0)다
- (c) 동일성: (a)의 반 마디 96개를 단독 실행과 비교한다

## 판정 (모두 충족하면 `--adaptive-start-safety 1.5`를 런타임 기본값으로 한다. 프리셋도 따른다)
1. (a) PC 15/15 적용, `latency_ms` 평균 ≤ 1,040 ms(#1532 + 150 ms)
2. (b) 6회 fallback 블록 합 ≤ 3이고 미스 합 0
3. (c) 96/96 동일

---

## 결과 — 기준 1·3 충족, **기준 2 미달 → opt-in으로만 합침(기본값 변경 없음)**
원시값: `docs/experiments/adaptive_budget/`.

| 기준 | 결과 |
|---|---|
| 1. 무부하: PC 15/15, 평균 ≤ 1,040 ms | 15/15, 평균 **942 ms**(#1532 890), 최대 1,432 ✓ |
| 2. N = 8: fallback 합 ≤ 3, 미스 0 | fallback **8**, 미스 **1** ✗ |
| 3. 동일성 | 96/96 ✓ |

N = 8 부하에서 세 설정을 비교하면 다음과 같다(Tatum 완성, 6회 합).

| 설정 | fallback 블록 합 (192블록 중) | 미스 합 |
|---|---|---|
| 고정 예산 0.5 (#1534) | 42 | 15 |
| **적응형 s = 1.5** | **8** | 1 |
| 예산 off (#1534) | 3 | 0 |

- 적응형은 고정 예산보다 fallback을 81% 줄였지만 예산 off에는 못 미쳤다
- 무부하 지연은 거의 그대로다. 한 번(seed 43) 예산이 넓어져 적용이 한 블록 늦었다(1,432 ms)
- 해석 후보(검증 안 함): 부하에서는 생성 시간이 튄다. 최근 4블록 최대의 1.5배로는 다음 블록의 튐을 다 덮지 못한다
- 조치
  - `--adaptive-start-safety`는 opt-in으로 둔다(기본 off)
  - 무거운 부하 지침은 #1534와 같다(`--start-budget-bars off`)
  - 다른 s 값으로 다시 돌려 기준을 맞추는 것은 하지 않는다. 결과를 보고 값을 고르는 것이 되기 때문이다
