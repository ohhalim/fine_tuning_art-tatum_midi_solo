# 학습 부족인가, 추론 입력 불일치인가 — 자연 문맥 vs 코드 프라이머 진단 (계획)

작성 2026-10-02. 이슈 #1597. 계획 문서다. 측정 전에 판정 규칙을 고정하고, 독립 리뷰를 받은 뒤 실행한다. **이 진단 결과는 새 학습의 자동 승인 근거가 아니다.** 새 학습은 별도 이슈·사전 등록·리뷰를 거친다.

## 배경
- 런타임 출력은 앞에서 친 음정 패턴을 다시 쓰지 않는다(VR 0. 실제 Tatum 0.014, 멜다우 0.054, #1575). FL 청취에서도 "무작위적"이었다
- 그런데 기존 학습은 이미 연속 구간을 썼다(`music_transformer/dataset/e_piano.py` 95–108: `x = data[:max_seq]`, `tgt = data[1:]`)
  - 모델은 "자연스러운 앞 문맥 → 다음 토큰"을 이미 배웠다. 그러니 같은 방식으로 다시 학습하는 것을 "연속성을 처음 가르친다"고 부를 수 없다
- 반면 런타임 입력은 학습 때와 다르다
  - 반 마디마다 처음부터 다시 생성한다(블록 리셋)
  - primer는 코드 가이드 음 몇 개뿐이다(코드 프라이머)
  - 이력 모드에서도 이력 뒤에 코드 진술을 끼워 넣는다
- 그래서 원인 후보가 둘이다
  - (가) 모델이 연속성을 충분히 배우지 못했다(학습 부족)
  - (나) 배운 것은 있는데 런타임 입력이 학습 분포와 달라서 쓰지 못한다(추론 입력 불일치)

## 질문 (하나)
같은 처음 보는 곡의 같은 이어지는 구간에 대해, 자연 문맥 조건과 런타임식 조건(코드 프라이머·블록 리셋)이 실제 이어지는 구절의 가능도와 자유 생성의 패턴 재등장을 다르게 만드는가.

## 데이터 (곡 단위 분할 보존, 누출 금지)
| 모델 | 진단용(파이프라인·탐색) | 평가용 |
|---|---|---|
| Tatum 완성 | val12(모델 선택에 쓰여 노출됨) | fresh12(학습·선택에 안 씀). **최종 평가에 이미 한 번 쓴 재사용 셋**이라 완전히 새로운 시험 셋이 아니다 |
| 공통 base | 위와 같은 곡(base는 Tatum을 보지 않음) | 위와 같음 |
| 멜다우 완성 | 없음 | 재사용 holdout 2곡. 기술 통계로만 보고하고 판정에 쓰지 않음 |

- 곡 목록과 파일 해시를 결과에 기록한다. 학습 manifest와의 교집합이 0인지 확인한다
- 위치: 곡마다 앞 문맥 256토큰 이상이 있는 지점에서 결정적으로 고른다(곡당 최대 8곳, 겹치지 않게)
- 이어지는 구간(target): 그 지점 뒤 실제 음악 2초 분량의 토큰

### target 경계와 상태 규칙 (사전 리뷰, 구현·회귀 테스트 먼저)
같은 raw 토큰이라도 조건마다 앞쪽 상태가 다르면, 가능도 차이가 화성이나 문맥이 아니라 토큰 문법 상태 차이를 재게 된다. 그래서 다음을 고정한다.
- target 시작점은 후보 지점에서 앞으로 찾아 **울리고 있는 음이 하나도 없는 note_on 직전**으로 정한다. 그래야 target 안에 앞 문맥에서 시작한 음의 note_off(짝 없는 off)가 없다
- target 앞에 **명시적 velocity 토큰**을 하나 둔다. 원래 그 지점에서 유효했던 값이다. velocity 상태를 primer에서 물려받지 않게 하기 위해서다. 이 토큰은 모든 조건에 똑같이 들어가고 NLL 계산에서는 뺀다
- 경계의 time shift: primer 마지막 이벤트와 target 첫 이벤트 사이 간격은 모든 조건에서 0으로 둔다. target은 첫 note_on부터 시작한다
- target 끝은 2초 안에서 시작한 음이 모두 닫히는 지점까지로 자른다. 2초를 넘겨 울리는 음은 2초 시점에서 끝낸다(재인코딩)
- 회귀 테스트(구현 전 작성)
  - target에 짝 없는 off가 없다
  - 경계에서 울리는 음이 없다
  - 첫 토큰이 velocity다
  - 조건별 primer + target을 이었을 때 grammar 위반(중복 on, 짝 없는 off)이 없다

## 조건 (target은 모두 같음)
| 조건 | primer | 의미 |
|---|---|---|
| N | 실제 앞 문맥 256토큰 | 학습 분포와 같다 |
| Ns | 실제 앞 문맥의 마지막 len(C)토큰(사례마다 C와 같은 길이) | 블록 리셋과 같은 짧은 문맥. C와 길이를 맞춘 대조 |
| C | 코드 가이드(사례마다 실제 인코딩 길이, 보통 48 미만) | 지금 런타임(블록 리셋 + 코드 프라이머) |
| NC | 실제 앞 문맥 + 추정 코드 가이드(이력 모드 순서) | 코드 진술 삽입 |
| NX | 실제 앞 문맥 + **무관한 코드** 가이드(같은 토큰 길이) | 삽입으로 위치가 밀리는 효과 대조 |
| M | 다른 곡의 앞 문맥 256토큰 | 앞 문맥이 그 곡이라서 도움이 되는지 확인 |

- 길이 맞춤: Ns와 C, NC와 NX는 사례마다 실제 토큰 수가 같은지 검사한다. 다르면 기록하고 그 비교에서 뺀다
- NC vs N에는 위치 증가가 섞인다. 코드 내용 효과는 NC vs NX로만 말한다. 삽입 자체의 교란은 NX vs N으로 본다

- 코드 가이드는 처음 보는 곡에 코드 라벨이 없다. 그래서 target 구간 음들의 pitch class로 템플릿을 맞춘 **추정 코드**를 쓴다
  - 추정이 틀리면 오히려 C/NC를 해칠 수 있다. 그래서 이 추정이 C에 유리하다거나 결론이 보수적이라는 보장은 **없다**
  - 추정 규칙은 `live_chords.recognize`의 템플릿을 쓴다
  - 코드를 추정할 수 있는 위치만 골라 같은 짝 위치에서 C/NC/NX/Ns를 비교한다. 제외율을 보고한다
- 우선순위: 앞 문맥 효과(M vs N)와 삽입 효과(NC/NX vs N)를 먼저 본다. C vs Ns는 추정 코드 의존이 커서 보조로 본다
- 무관한 코드: 추정 코드와 공통음이 가장 적은 템플릿 코드다(결정적 선택)

## 측정
1. **target 가능도(teacher forcing):** target 토큰당 평균 NLL
   - 앞 문맥 효과: NLL(M) − NLL(N). 양수면 그 곡의 앞 문맥이 이어지는 구절 예측을 돕는다
   - 삽입 교란: NLL(NX) − NLL(N)
   - 코드 내용: NLL(NC) − NLL(NX)
   - 짧은 문맥: NLL(Ns) − NLL(N)
   - 코드 프라이머 대 같은 길이의 자연 문맥: NLL(C) − NLL(Ns)(보조)
2. **자유 생성(free rollout):** 각 조건에서 target 길이만큼 생성한다
   - 실제 앞 8초 윗선율 대비 VR/XR/IR(#1575 지표, 창별 윗선율)
   - 실제 이어지는 구간의 같은 지표를 기준으로 함께 적는다
   - 동기 지표 하나만 최대화하지 않는다. 코드톤(추정 코드), 음 수, 검증 통과율도 함께 적는다
- 집계: 곡별 평균을 먼저 낸다. 곡 단위 bootstrap 95% CI를 쓴다. 위치를 독립 n으로 세지 않는다

## 판정 규칙 (평가용 fresh12, Tatum과 base 각각, 실행 전 고정)
두 가설(학습 부족, 추론 입력 불일치)은 서로를 배제하지 않는다. 이 진단은 **추론 입력 불일치의 근거가 있는지**만 판정한다.
- **추론 입력 불일치 지지:** 다음을 모두 충족(곡 단위 bootstrap 95% CI)
  1. 앞 문맥 효과: NLL(M) − NLL(N) > 0
  2. 짧은 문맥 또는 삽입 교란이 크다: NLL(Ns) − NLL(N) > 0 또는 NLL(NX) − NLL(N) > 0
  3. 자유 생성: 곡별 평균 VR이 N에서 Ns보다 높다(차이 CI > 0)
  - 다음 단계: 런타임에 실제 연주 이력을 학습 분포에 가깝게 넣는 방법을 먼저 설계한다(별도 이슈)
- **앞 문맥 효과 미확인:** 1의 CI가 0을 포함하면 이렇게 기록한다. **학습 부족을 지지한다는 뜻이 아니다**
- **학습 부족 여부는 이 진단에서 판정하지 않는다.** 필요하면 별도 검정으로 설계한다
- 어느 결과도 새 학습의 자동 승인 근거로 쓰지 않는다. 새 학습은 별도 이슈와 사전 등록, 리뷰를 거친다
- 진단용(val12)에서는 파이프라인과 분포만 확인한다. 판정은 평가용에서만 한다. 이 단위에서 조건이나 기준을 다시 탐색하지 않는다

## 예산과 범위
- 로컬 CPU만 쓴다. 새 데이터·새 학습·외부 업로드·유료 자원은 쓰지 않는다. 기존 체크포인트는 읽기만 한다
- 평가용 기준: 모델 2개 × 12곡 × 최대 8위치 × 조건 6개(N, Ns, C, NC, NX, M)
  - 조건 6개 가능도 계산 최대 1,152회
  - 자유 생성은 조건 3개(N, Ns, C)에서 위치당 seed 2개, 최대 1,152회
- 품질·스타일 주장은 하지 않는다(`musical_quality_verified: false`)

### 해석 (확인 안 됨, 다음 단위 설계용)
- 가능도로 보면 모델은 그 곡의 앞 문맥을 쓰고, 지금 런타임 입력(짧은 문맥, 코드 진술 삽입)은 이어지는 구절 예측을 나쁘게 한다
- 그런데 학습 분포와 같은 자연 문맥을 줘도 자유 생성은 앞 구절을 다시 쓰지 않는다
  - IR이 실제의 약 1/7이고, VR은 0이다
- 그래서 입력만 학습 분포에 맞춰서는 "무작위적"이라는 청취 문제가 풀리지 않을 가능성이 크다. 생성(샘플링) 단계나 모델 쪽 원인을 따로 진단해야 한다
- 이 결과는 새 학습의 자동 승인 근거가 아니다
