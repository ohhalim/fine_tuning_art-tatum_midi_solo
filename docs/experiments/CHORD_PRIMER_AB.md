# 코드 진행에 반응하는 생성 — 최소 구현과 A/B

작성 2026-09-22. 브랜치 `exp/chord-primer` (로컬 전용, push 안 함).
`musical_quality_verified: false` — 청취 리뷰 없음.

## 0. 먼저 가설을 검증했다 (그리고 틀렸다)

`RESUME_HANDOFF.md` 는 다음 작업으로 "`control_prefix_tokens` 에 코드 심볼을
더하는 형태" 를 제안했다. **가설이었고, 확인해 보니 성립하지 않는다.**

vocab 에 Stage B 코드 토큰이 있고(`TOKEN_STAGE_B_CHORD_ROOT_*`), checkpoint
임베딩도 547 행이라 ID 가 범위 안에 있다. 둘 다 "학습됐다" 를 뜻하지 않는다.
토큰화된 학습셋을 직접 세면 끝난다.

| 데이터셋 | 용도 | 최대 토큰 ID | 제어 토큰 등장 |
|---|---|---|---|
| `jazz_full` (2,777곡) | armB 사전학습 = 우리 베이스 | 377 | **0** |
| `roles/lead/tokenized` | armD LoRA 적응 = 우리 checkpoint | 388 | **0** |
| `roles_aug12` | Arm E (D1 에서 기각된 증강 팔) | 395 | 864 |

**우리 checkpoint 는 제어 토큰을 하나도 본 적이 없다.** 코드 토큰뿐 아니라
`ROLE_LEAD`·`TEMPO_*`·`BAR`·`COND_SEP` 전부다. 미학습 임베딩 행을 prefix 에
넣고 "conditioning 구현" 이라고 부르는 것은 근거 없는 주장이 된다.

### 덤으로 드러난 기존 결함

현재 런타임의 `build_primer(control_format="control_v1")` 는 매 primer 앞에
그 미학습 토큰 4개를 붙이고 있다. **이번 범위에서 고치지 않았다** (기본 경로
보존 지시). 별도 과제로 남긴다.

## 1. 선택한 경로 — 학습된 음표 vocabulary 의 chord primer

후보 둘 중 하나만 고르라는 지시에 따라:

| 후보 | 판단 |
|---|---|
| chord-aware constrained decoding / 약한 chord bias | 규칙 제어다. 모델이 반응하는 게 아니라 내가 거르는 것이고, "모든 음 강제 chord tone" 위험이 구조적으로 존재한다 |
| **기존 음표 vocabulary 의 chord primer** | **선택.** 학습된 토큰만 쓰고, 필터가 없으므로 비화성음·해결이 원리적으로 막히지 않는다 |

기존 자산 `inference/app/conditioning.build_request_conditioning_midi` 를
재사용한다(저음역 화성 가이드 MIDI). 호환성 확인:

```
chord primer 토큰 44개  ID 범위 38..370  제어 토큰 0개  (학습셋 최대 388)
```

**이것은 학습 기반 conditioning 이 아니다.** 모델은 코드 심볼을 모른다.
화성을 아는 음표를 깔아 주고 이어서 치게 하는 것이다. 보고서에서 이 둘을
섞지 않는다.

## 2. A/B 설계

같은 checkpoint·같은 seed·8마디. **primer 뒤의 코드 진행만 바꾼다.**

팔: `none`(가이드 없음) · `ii_V_I` · `minor` · `blues` · `shuffled`(ii_V_I 를
섞은 순서). seed 42/100/200 3회.

채점은 **생성된 음을 고정하고 잣대만 옮긴다.** 필터가 아니라 측정이다.

- `own` — 자기 진행 기준 chord-tone 비율
- `cross` — 다른 진행들 기준 (평균)
- `tritone` — **자기 진행을 6반음 전조한 것 기준.** 깨끗한 대조다

### 1/3 을 합격선으로 쓰지 않는다

코드음 4개 / 12 pitch class = 1/3 은 **음높이가 독립·균등일 때만** 성립한다.
재즈 솔로는 조성 안에 있고 음을 반복하며 음계도에 기댄다. 1/3 을 넘었다고
화성 반응의 증거가 아니고, 밑돌았다고 실패의 증거가 아니다. 참고선일 뿐이다.

## 3. 결과 (3 seed 평균)

| 팔 | valid 마디 | own | crossΔ | tritone | **triΔ** |
|---|---|---|---|---|---|
| none | **0~1/8** | – | – | – | – |
| ii_V_I | 7~8/8 | 0.549 | +0.175 | 0.186 | **+0.364** |
| minor | 6~7/8 | 0.473 | +0.130 | 0.238 | **+0.235** |
| blues | 7~8/8 | 0.500 | +0.045 | 0.252 | **+0.249** |
| shuffled | 7~8/8 | 0.495 | +0.078 | 0.188 | **+0.308** |

- **트라이톤 대조 triΔ: 평균 +0.289, 12/12 전부 양수, 범위 +0.164~+0.457**
- cross 대조 crossΔ: 실제 진행 평균 +0.117 vs shuffled +0.078 — **구별 안 됨**
- 생성 지연 p50 317~486ms (마디 1875ms), 다양성 pitch class 11~12/12

## 4. 판단 — 두 층으로 나눈다

**확인된 것**: chord primer 가 출력의 음높이 분포를 primer 화성 쪽으로
움직인다. 트라이톤 대조에서 12/12 일관되게 나왔고, 팔 사이에 다른 것은
primer 뿐이다.

**확인되지 않은 것**: 마디별로 코드 변화를 따라가는지. shuffled 대조가
실제 진행과 구별되지 않았다(+0.078 vs +0.117, 범위 겹침). 트라이톤 대조는
**"조성 안에 있다"와 "진행을 따라간다"를 구분하지 못한다** — 한 조성에
머무르기만 해도 트라이톤보다는 잘 맞는다.

즉 **"코드를 준 만큼 음이 달라진다" 까지가 근거 있는 주장이고,
"코드 진행을 따라 솔로한다" 는 아직 아니다.**

**음악적 품질은 주장하지 않는다.** 청취 리뷰 없음.

### 대조군 해석 주의

`none` 팔이 0~1/8 로 무너진 것은 "화성이 없어서" 가 아닐 수 있다. 이 팔의
primer 는 `[60]` 단일 음이라 **런타임 기본 경로(고정 conditioning MIDI)가
아니다.** "primer 가 빈약하면 생성이 무너진다" 와 "화성이 필요하다" 가
섞여 있다. 기본 경로와의 비교는 하지 않았다.

# 후속 — 교란 제거와 마디별 진행 추종 (2026-09-22)

`scripts/run_chord_ablation.py`. 첫 A/B 의 두 문제를 처리한다.

## 8. 미학습 prefix 주장의 검증 — 앞선 근거는 불충분했다

§0 에서 **데이터 count 만으로** "checkpoint 가 제어 토큰을 본 적 없다" 고 썼다.
그건 학습 이력의 확정 근거가 못 된다. loader 와 recipe 를 확인해 사슬을 채웠다.

| 확인 대상 | 결과 |
|---|---|
| armB 출처 | `jazz_full` 로 **처음부터** 학습. 선행 checkpoint 없음 (`run_d0_experiment.sh`) |
| loader 의 prefix 처리 | `crop_control_v1_sequence` 는 prefix 를 **데이터에서 읽는다**. 합성하지 않는다. COND_SEP 가 없으면 제어 처리 없이 랜덤 크롭 |
| vocab resize | armB·armD 둘 다 (547, 512). 둘 사이 resize 없음 |
| LoRA 가 임베딩을 갱신했나 | **아니다.** armB↔armD `embedding.weight` 최대 절대차 **0.00e+00** |

∴ 제어 토큰 임베딩 행은 armB 초기화 상태다. **다만 이건 가중치 논증이고,
출력이 달라지는지는 ablation 이 답한다.**

## 9. 2×2 ablation — prefix 효과를 분리한다

(chord primer | 기존 conditioning MIDI) × (prefix 있음 | 없음).
generation budget 과 seed 를 4팔에 동일하게 맞췄다. **`[60]` 팔은 없앴다** —
무화성 기준선은 실제 기본 경로다.

8마디 × seed 42/100/200:

| 팔 | primer 토큰 | valid | 노트 | chord-tone own | 생성 p50 |
|---|---|---|---|---|---|
| default_prefix | 48 | 24/24 | 117 | 0.164 | 86ms |
| default_noprefix | 48 | 24/24 | 74 | 0.137 | 84ms |
| chord_prefix | 15 | 21/24 | 228 | 0.545 | 414ms |
| chord_noprefix | 11 | 22/24 | 216 | 0.610 | 264ms |

**prefix 효과: 분명하지 않다.** default 에서는 있는 쪽이 약간 높고(0.164 vs
0.137) chord 에서는 없는 쪽이 약간 높다(0.610 vs 0.545). 방향이 반대고 폭이
작다. §8 의 가중치 증거와 일치한다.

**이것은 prefix 가 해롭다는 증거가 아니다.** 효과가 안 보인다는 것뿐이고,
런타임 기본값을 바꿀 근거로는 부족하다. **기본 경로를 건드리지 않았다.**

### 아직 남은 교란 — 내 앞선 주장을 정정한다

스크립트가 "primer 길이가 팔 간에 동일" 이라고 출력하고 있었다. **틀렸다.**
default 48 vs chord 11~15 다. 화성 가이드가 그냥 더 짧고, 예산은 자르기만 하며
채우지 않는다. 출력과 docstring 을 고쳤다.

따라서 **chord 대 default 비교는 화성과 primer 길이·내용을 여전히 섞는다.**
한 kind 안의 두 prefix 팔 비교만 깨끗하다.

## 10. 마디별 진행 추종 — 같은 코드 multiset, 다른 순서

조성을 고정하려고 같은 multiset 을 순서만 바꿔 쓴다.

```
진행    Dm7  G7   Cmaj7 Am7
순열    Cmaj7 Am7  Dm7  G7      (모든 마디 쌍의 공유 코드음 1/4)
```

전체곡 조성 적합성은 두 잣대에서 **구성상 동일하다.** 마디-코드 정렬만 다르다.
진행으로 생성한 뒤, 각 마디를 실제 코드와 순열이 그 자리에 놓은 코드로 **짝지어**
채점한다.

24마디 중 19마디 채점 (5마디는 무효/빈 마디):

| 부분집합 | 마디 | 노트 | 단순 평균Δ | **노트가중Δ** | true vs perm | 양수 |
|---|---|---|---|---|---|---|
| 전체 | 19 | 216 | +0.292 | +0.218 | 0.556 / 0.338 | 13/19 |
| **노트 ≥ 8** | **14** | **201** | +0.176 | **+0.199** | **0.542 / 0.343** | **9/14** |
| 노트 < 8 | 5 | 15 | +0.617 | +0.467 | 0.733 / 0.267 | 4/5 |

노트 수 분포: 1,2,3,4,5,8,8,9,9,10,11,12,12,13,19,21,21,23,25

**노트 ≥ 8 행을 읽어야 한다.** 3음짜리 마디의 비율은 거의 전부 표집 노이즈이고
(1음이면 0.0 또는 1.0), 그 마디들이 단순 평균을 끌어당긴다.

### 한계 — 과장하지 않는다

- **표본 독립이 아니다.** 한 실행 안의 마디들은 같은 primer 정책과 같은 모델

- **공유 코드음.** 이 설계는 쌍마다 1/4 로 낮췄지만, 다이아토닉 7화음은 원래
  많이 겹친다. 겹칠수록 이 검정의 분리력이 떨어진다.
- 14마디 · 201노트는 작다. 3 seed × 8마디 세트 하나다.

```
seed 8개  평균 +0.099  표준편차 0.173  SE 0.061  t=1.62 (df=7)
평균/표준편차 = 0.57  → 분산이 평균보다 크다
양수 5/8  (동전던지기 기대 4/8)
```

## 15. 판정 — 마디별 진행 추종은 확인되지 않았다

**seed 간 분산이 평균보다 크고 3/8 seed 가 음수다. 0 과 구별되지 않는다.**

앞선 3 seed 결과(+0.199, 9/14)가 암시적으로 보인 이유가 분명하다. **그 3 seed
가 우연히 전부 음수가 아닌 쪽이었다**(+0.342, +0.174, +0.019). seed 5개를
더하자 음수 3개가 들어왔다. 작은 표본이 오해를 만든 교과서적 사례이고,
내가 그걸 "암시적" 이라고 읽은 것이 과했다.

`t=1.62` 는 참고용이다. seed 는 근사적으로만 독립 단위이고 n=8 이다.
유의성을 주장하려는 것이 아니라 **주장할 수 없음**을 보이려는 수치다.

### 이것이 뒤집지 않는 것

chord primer 가 출력 음높이를 움직인다는 결과는 그대로다. 근거가 다르다 —
트라이톤 대조와 2×2 ablation 의 chord 대 default 차이(0.545~0.610 vs
0.137~0.164)는 **전체 음높이 분포**에 대한 것이고, 여기서 무너진 것은
**마디-코드 정렬**이다.

즉 현재 상태를 한 줄로: **조성은 따라가고 코드 변화는 따라가지 않는다.**

## 16. 다음 한 단계

**마디 안에서 화성을 갱신한다.** 지금은 마디 시작에 코드를 한 번 깔고 생성이
마디 전체를 자유롭게 채운다. 생성 길이가 마디 하나인데 primer 는 그 마디
앞에만 있으니, 모델이 마디 중간에 코드를 "다시 볼" 방법이 없다. 마디를 더 짧은
블록(예: 2박)으로 쪼개 각 블록마다 화성을 다시 제시하면 정렬이 강해질지
측정할 수 있다. 새 학습은 필요 없다.

이게 실패하면 다음은 학습 쪽이다(코드 토큰을 실제로 학습시키는 것). 그건
GPU 비용과 승인이 필요한 별개 작업이다.

## 17. 결과 — blocks=1 만 실패였다

## 18. 왜 blocks=1 이 실패했는지 설명된다

primer 는 마디 앞에만 있고 생성은 마디 전체를 채운다. 모델이 **마디 중간에
코드를 다시 볼 방법이 없었다.** 정렬이 안 되는 것이 오히려 당연하다.
§15 의 음수 결과는 모델의 한계가 아니라 **내가 화성을 제시하는 간격의 문제**
였다.

## 19. 분리되지 않은 교란 — 정직하게

blocks 를 바꾸면 **두 가지가 함께 변한다.**

1. 화성을 다시 제시하는 빈도 (의도한 변수)
2. 호출당 생성 길이 (마디 → 반마디 → 1박)

짧은 생성이 그냥 국소적으로 더 일관될 수도 있다. **둘을 분리하지 않았다.**
분리하려면 블록은 짧게 유지하면서 화성만 다운비트에서 한 번 제시하는 팔이
필요하다(= 블록 2,3,4 는 무화성 primer). 다음 후보다.

## 20. 실시간 비용

blocks 를 늘리면 마디당 생성 호출이 그만큼 늘어난다. blocks=4 면 마디당 4회다.
`docs/phase1/LATENCY_BUDGET.md` 기준 마디 예산이 1875ms 이므로 호출당 예산이
약 470ms 로 줄어든다. 측정된 생성 p50 은 블록 길이에 따라 다르지만, **연속
런타임에 붙이기 전에 블록 단위 지연을 따로 재야 한다.** 이번에는 재지 않았고
런타임에 연결하지 않았다.

∴ §19 에서 분리하지 못했던 교란의 답: **정렬 이득은 화성을 다시 제시하는

### 부수 관찰 — 일관성과 효과 크기는 다르다

blocks=2-다운비트만은 blocks=1 과 효과 크기가 같은데 sd 는 0.173 → 0.090 으로
낮고 양수가 5/8 → 7/8 이다. 마디·노트가 늘어 추정이 안정된 것이고
**효과가 커진 것이 아니다.** t 가 1.62 → 3.08 로 오른 것도 그 때문이다.
t 를 효과 크기로 읽으면 안 된다.

| blocks | 블록당 예산 | 블록 p50 | 블록 max | 여유 | 마디합 p50 | 마디합 max | 마디 초과 |

**마디 합계는 거의 늘지 않는다** (340 → 361 → 505ms). 블록이 짧으면 블록당

블록마다 별도의 디스패치 마감이 있다. 마디 예산 1875ms 를 블록 수로 나눈 값이

blocks=4 는 마디 합계로는 여유가 있어 보이지만 **블록 단위로 보면 이미 초과
사례가 있다.** 마디 합계만 보면 이 위험을 놓친다.

## 28. 권고 — blocks=2

측정 조건 한계: 부하 없는 단독 실행이고 CPU 경로다. DAW·신스가 함께 도는
상태에서는 재측정해야 한다. 32마디 단발이다.

# 후속 6 — blocks=2 를 연속 런타임에 opt-in 연결 (2026-09-22)

§29 를 실행했다. `--chord-primer --chord-blocks-per-bar 2`.

## 30. 스케줄러는 고치지 않았다

스케줄러는 여전히 **마디당 블록 하나**를 소비한다. 분할은 producer 콜백
안에서 일어나고, 두 하위 블록을 한 마디 분량으로 합쳐 하나의
`ScheduledMidiBlock` 으로 낸다. `OneBarMidiScheduler` 와
`BarBlockProducer` 의 계약이 그대로다.

하위 블록 하나가 검증에 실패하면 **그 블록만 버리고 마디는 살린다.** 반 마디를
잃는 것이 한 마디를 다 잃는 것보다 낫다. 모든 하위 블록이 실패할 때만 마디가
실패해 fallback 으로 간다.

입력 반영은 **다운비트 하위 블록에만** 한다. 두 번째 블록이 같은 입력을 다시
쓰면 이미 소비한 맥락을 중복 조건으로 넣는 셈이다.

## 31. 실측 — 세 경로 (8마디, seed 42, 독립 캡처)

| 경로 | 완주 | model | 오류 | 생성 p50 | **생성 max** | 캡처 | 손실 | 데드라인 미스 |
|---|---|---|---|---|---|---|---|---|
| 기본 (플래그 없음) | ✅ | 8/8 | 0 | 93ms | 258ms | 44/44 | 0 | 0 |
| `--chord-primer` | ✅ | 8/8 | 0 | 368ms | **1106ms** | 214/214 | 0 | 0 |
| `--chord-primer --chord-blocks-per-bar 2` | ✅ | 8/8 | 0 | 436ms | **640ms** | 266/266 | 0 | 0 |

`생성 p50/max` 는 **마디 전체**(하위 블록 합계)다. blocks=2 에서 p50 은 조금
오르지만 **최대가 1106ms → 640ms 로 내려간다.** §27 의 오프라인 측정과 같은
방향이고, 실시간에서는 최악값이 더 중요하다.

노트도 214 → 266 으로 늘었다. 데이터 손실·데드라인 미스는 세 경로 모두 0 이다.
