# 생성 시작 예산 — 입력 반영 지연 추가 단축 (사전 등록)

작성 2026-09-29. 이슈 #1530. `style_verified: false` · `musical_quality_verified: false` · 가상 CoreMIDI 포트

**이 절은 측정 전에 작성했다.** 구현은 측정 전에 끝냈다.

## 문제
늦은 fetch(#1526) 뒤에도 마디 b+1의 생성은 마디 b를 가져간 직후(다운비트(b) − 50 ms)에 시작된다. 입력 도착에서 그 입력을 반영한 마디 시작까지는 **1–2마디**다. 그런데 생성에는 마디의 30% 이하만 쓴다(#1523, #1526).

## 변경 (opt-in으로 구현, 기준 통과 시 기본값)
- `BarBlockProducer(start_not_before_ns=f)`: 정상 상태 마디(2번째 이후)의 생성 시작을 시각 f(b)까지 미룬다. 워밍업 0·1마디는 미루지 않는다
- `run_continuous_jazz.py --start-budget-bars β`(0.1–0.95, 늦은 fetch 필요)
  - f(b) = 다운비트(b) − fetch 여유 − β × 마디
  - 리포트에 `start_budget_bars`를 기록한다
- 기대: 도착→반영 지연이 **β + 여유 ~ 1 + β + 여유**마디가 된다. β = 0.5면 128 BPM에서 약 1.0–2.9초다(현재 약 1.9–3.8초)

## 측정 (β = 0.5)
- (a) 지연: `run_live_select_probe.py`
  - 쌍 S, 128 BPM, 16마디, seed 42/43/44
  - 도착 위상이 흩어지도록 실행 후 11.0 / 15.4 / 19.9 / 24.1 / 28.2초에 PC 1/0/1/0/1을 보낸다
  - **기준 arm(β 없음, 현재 기본)과 β = 0.5 arm을 같은 전송 계획으로** 각 3회 잰다
  - 지표 `latency_ms` = 적용 마디 다운비트 − 도착 시각
- (b) 실시간성: Tatum 완성 · 멜다우 #1497 × 128 / 240 BPM × seed 3 = 12회, β = 0.5
- (c) 마디 동일성: (b) 실행과 #1526 sweep(같은 모델·템포·seed)의 연주 마디를 비교한다

## 판정 (모두 충족하면 `--start-budget-bars 0.5`를 기본값으로 한다)
1. β arm에서 보낸 PC가 전부 적용된다. 단, 마지막 생성이 시작된 뒤 도착한 PC는 제외하고 그 수를 보고한다
2. β arm의 모든 `latency_ms` ≤ (1 + β) × 마디 + 150 ms(= 2,962 ms)이고, 평균이 기준 arm보다 **0.3마디(562 ms) 이상** 짧다
3. (b) 12회 모두 fallback 0, 오류 0, 미스 0
4. (c) 연주 마디가 전부 동일하다

미달하면 opt-in으로만 남기고 원인을 기록한다.

## 1차 결과 — 기준 1·2·4 충족, **기준 3 미달 → 기본값으로 바꾸지 않음(opt-in)**
원시값: `docs/experiments/start_budget/`(`probe_{base,beta05}_seed*.json`, `sweep_report.json`).

### 기준 1·2 — 지연 (PC 5개 × 3회, 같은 전송 계획)
| arm | 적용 | latency_ms 평균 | 최소 | 최대 |
|---|---|---|---|---|
| 기준(늦은 fetch만) | 15/15 | 2,676 | 1,892 | 3,746 |
| **β = 0.5** | **15/15** | **1,832** | 1,271 | **2,410** (기준 ≤ 2,962) |

- 평균 차이 **−844 ms**(0.45마디). 기준 −562 ms를 넘는다 ✓
- 세 seed 모두 도착 위상에 따라 1마디 뒤(6→7, 13→14) 또는 2마디 뒤에 적용됐다. 기준 arm은 모두 2마디 뒤였다

### 기준 3 — 실시간성 (12회): 미달
- fallback은 12회 모두 0이다
- **Tatum 128 BPM seed 42(미스 3, 최대 지각 23.9 ms)와 seed 43(미스 2, 43.6 ms)에서 데드라인 미스가 났다.** 나머지 10회는 0이다
- 미스 5건 모두 `producer_busy: false`였다. **생성이 돌지 않을 때** 난 멈춤이다
- 같은 시간대 **기준 arm probe(β 없음) seed 42에서도 미스 2건(36.2 ms, producer_busy false)**이 났다
- 해석(판정 아님): β가 원인이라는 근거는 없다. RUNTIME_STALL_CAUSE에서 본 드문 비생성 멈춤(GC, OS 선점 후보)과 같은 부류로 보인다. 그래도 사전 기준은 "미스 0"이었으므로 미달로 기록한다

### 기준 4 — 마디 동일성
sweep 192마디(vs #1526 sweep)와 probe 96마디(vs 단독 실행)가 **288/288 동일**하다 ✓

### 조치
- `--start-budget-bars`는 opt-in으로 합친다. 기본값은 바꾸지 않는다
- β가 미스를 늘리는지는 새 질문이다. 아래 후속 실험으로 따로 등록해 잰다

## 후속 — β가 데드라인 미스를 늘리는가 (사전 등록, 실행 전)
- 조건: Tatum 완성, 128 BPM, 16마디, 코드 primer. arm A(β 없음)와 arm B(β = 0.5)를 **seed 42–47에서 교대로** 실행한다(A42, B42, A43, …, 12회). 시간대 차이를 상쇄하기 위해서다
- 기록: 실행별 미스 수, 각 미스의 `producer_busy`, fallback
- **판정(모두 충족하면 `--start-budget-bars 0.5`를 기본값으로 한다)**
  1. 12회 모두 fallback 0
  2. B의 미스 합 ≤ A의 미스 합
  3. B에서 `producer_busy: true`인 미스가 0이다(β로 옮긴 생성 구간이 이벤트와 겹쳐 생기는 미스가 없어야 한다)
- 미달하면 opt-in으로 남긴다. 이 후속은 1회만 실행한다
