## 2. 사전 등록 (실행 전 커밋)

질문: ReaLJam의 실시간 생성 한 번(`generate_live`)이 이 Mac(M1 Max, 32 GB)에서 몇 ms 걸리는가. 우리 템포에서 16분음표마다 새로 고칠 수 있는가.

방법 (`scripts/realjam_live_bench.py`)

- 브라우저 동작을 흉내 냅니다. 매 프레임 `generate_live`를 부르고, 돌려받은 코드 토큰을 세션 목록의 해당 프레임부터 덮어씁니다
- 입력 멜로디: C 장조 음계에서 1~4프레임 길이 음, 쉼표 15%, 시드 0. 음악 품질과 무관한 부하용 입력입니다
- 세션 320프레임(80박). 무음 8박(32프레임). 256프레임을 넘는 마지막 구간에서 문맥 자르기도 지나갑니다
- 모델: GAPT, ReaLchords. 온도 1.0
- 설정(lookahead:commit 프레임): 16:16(화면 기본값 4박:4박), 8:4(2박:1박)
- 백엔드: PyTorch CPU(torch.compile 기본값), MLX, ONNX CPU
- 첫 호출의 오프라인 모델(인트로 코드 채우기)은 한 번만 일어나므로 따로 기록합니다. 나머지 호출에서 처음 3번을 워밍업으로 뺍니다
- 지표: 호출당 시간의 중앙값, p95, 최대

판정 기준

- 우리 128 BPM에서 16분음표는 117.2 ms입니다. ReaLJam 기본 80 BPM에서는 187.5 ms입니다
- **p95 < 117.2 ms**이면 "128 BPM에서 매 16분음표 갱신 가능"으로 적습니다
- 117.2 ≤ p95 < 187.5 ms이면 "80 BPM에서만 매 프레임 갱신 가능"으로 적습니다
- 그 이상이면 "매 프레임 갱신 불가. 갱신 간격 = p95"로 적습니다
- 백엔드끼리 순위를 매기지 않습니다. 기준을 넘는 백엔드가 있는지만 봅니다
- (실행 후 주석) 위 세 문구 중 "갱신 가능"·"갱신 간격 = p95"는 p95 하나로 말할 수 없는 표현이었습니다. 임계값은 그대로 두고, 결과 표현은 3.1에서 교정했습니다

하지 않는 것

- 음악 품질 판단. 사용자 직접 연주 소감은 따로 적습니다
- 브라우저·네트워크 지연 측정. 이번에는 모델 호출 시간만 잽니다

### 3.1 사전 등록 판정

- **p95 < 117.2 ms(128 BPM 16분음표)를 만족한 설정은 없습니다**
- **MLX + 8:4(2박 앞, 1박 확정)는 p95 < 187.5 ms(80 BPM 16분음표) 기준만 충족**합니다(GAPT p95 175.4, ReaLchords p95 173.3)
- PyTorch CPU와 ONNX CPU는 모든 설정에서 p95 ≥ 187.5 ms입니다

**표현 교정 (아스트라 원 JSON 재검산, 2026-10-16 22시)**

- 처음에는 MLX 8:4를 "80 BPM에서만 매 프레임 갱신 가능"으로 적었습니다. 같은 설정에서도 187.5 ms를 넘은 호출이 GAPT 7/289(최대 208.7 ms), ReaLchords 6/289(최대 204.3 ms) 있습니다. **"매 프레임 갱신 가능" 보장은 철회합니다.** 맞는 표현은 "호출 지연 p95 기준만 충족, 실제 시계·브라우저·입출력은 미측정"입니다
- 117.2 ms를 넘은 호출은 GAPT 92/289, ReaLchords 139/289입니다
- 사전 등록 문서에 "그 이상이면 갱신 간격 = p95로 적는다"고 썼지만, **p95는 실제 갱신 간격이 아닙니다.** 브라우저의 다음 요청 시점은 조건부입니다. `frontend/play_from_midi_input.js`(263–269행)는 응답을 받았을 때 아직 같은 프레임이면 한 프레임(`1000 / fps` ms) 뒤에 `setTimeout`으로 다시 요청하고, 프레임이 이미 넘어갔으면 바로 요청합니다. 그래서 실제 갱신 간격은 호출 지연과 프레임 위상에 따라 달라집니다. 이 표의 호출 벤치 숫자는 서버 호출 지연으로는 유효하지만 브라우저 갱신 간격으로 쓰지 않습니다. 판정 열은 p95가 기준을 넘었는지만 적도록 바꿨습니다
- 이 측정은 **코드를 생성하는 모델(GAPT, ReaLchords)**의 지연입니다. 같은 구조의 약 2,000만 파라미터 멜로디 모델(`rl_melody_gail_4_datasets`) 지연은 재지 않았습니다

### 3.2 관찰 (판정에 쓰지 않음)

- MLX는 같은 조건에서 PyTorch CPU보다 중앙값이 약 3–4배 빠릅니다. ONNX CPU는 PyTorch CPU와 비슷하거나 약간 빠릅니다
- **MLX는 세션 뒤쪽이 더 빠릅니다.** 문맥이 최대 길이(256프레임)에 닿은 뒤인 마지막 64회 p95가 GAPT 8:4에서 80.6 ms, ReaLchords 8:4에서 96.0 ms로 117.2 ms 아래입니다. 앞쪽 호출에서는 입력 길이가 매번 달라 MLX가 그래프를 새로 만드는 비용이 생기는 것으로 추정합니다(미확인). 사전 등록 지표는 전체 p95라 판정은 바꾸지 않습니다. 확인하려면 "문맥 길이 고정 후 p95"를 따로 등록해 재야 합니다
- 설정을 16:16에서 8:4로 바꾸면 호출이 빨라집니다. 다만 이 변경은 lookahead와 commit을 동시에 바꾼 것이라, lookahead만의 효과로 단정하지 않습니다. 한 번에 다시 계산하는 확정 구간 토큰이 줄어드는 것(`commit_frames` 교사 강제)이 원인 후보입니다
- 공식 코드는 매 호출 INFO 로그로 토큰 텐서 전체를 출력합니다. 이 비용도 측정값에 들어 있습니다. 실제 서버도 같은 로그를 내므로 그대로 두었습니다. 로그를 끄면 얼마나 빨라지는지는 재지 않았습니다

### 3.3 우리 프로젝트에 주는 시사점 [판단]

- 이 크기의 코드 생성 모델은 이 Mac에서 MLX를 써도 일부 호출이 128 BPM 16분음표 예산(117.2 ms)을 넘었고 p95 기준에 못 미쳤습니다(8:4에서 GAPT 92/289, ReaLchords 139/289 초과). 우리 블록 계약(반 마디 937.5 ms마다 요청)과 같은 간격이라면 호출 시간으로는 여유가 있습니다. 실제 시계·입출력을 붙인 측정은 아닙니다
- ReaLJam의 lookahead·commit은 지연과 반응성을 맞바꾸는 손잡이입니다. 짧게 잡을수록 빨리 반응하지만 호출 부담과 실패 위험이 커집니다. #1766 F4(블록 계약을 t_f·k와 lookahead·commit 축으로 다시 쓰기)의 실측 근거로 씁니다
- **기존 Aria MLX 측정과 비교 (정정):** 처음에는 "Aria는 가중치가 30배 이상 커서 같은 방식은 어렵다"고 적었습니다. 모델 크기만 보고 추론한 문장이라 근거가 약했습니다. #1743(`ARIA_MLX_STREAM_LOOP.md`)에서 이미 잰 값은 이렇습니다
  - 코드 입력을 흉내 내 미확정을 버리고 확정 지평까지 다시 만드는 데 0.08–0.24 s(n=5, 다시 만든 토큰 10–37개)
  - 추측 포함 블록 전체: 중앙값 0.133 s, 최대 0.398 s(n=42)
  - ReaLJam MLX 호출 p95 173–320 ms와 비슷한 크기입니다
  - 두 측정은 토큰 수, 문맥 길이, 표본 수, 무엇을 다시 계산하는지가 달라서 직접 비교는 못 합니다. Aria의 0.236 s 최대값으로는 매 16분음표(117 ms) 재생성을 보장할 수 없습니다. 반 마디 블록 + 1박 확정 지평 설계에서는 여유가 있습니다(#1743 결론과 같음)
