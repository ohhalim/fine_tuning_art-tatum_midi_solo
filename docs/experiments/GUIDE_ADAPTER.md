# guide 형식 비밥 어댑터 (A, 사전 등록)

작성 2026-10-03. 이슈 #1631. 선행: `HARMONY_CONTRACT.md`. U2에서 bebop의 Δshuf가 base 절반 미만이라 go가 나왔다(경계). 아스트라와 합의한 A 병행 조건을 따른다. 판정 규칙은 학습 전에 고정했다. `musical_quality_verified: false`.

## 가설
학습할 때 각 솔로 창 앞에 그 창의 화성 guide(계약 형식)를 두면, 모델이 guide 내용에 더 크게 반응한다(Δshuf가 커진다). 이것은 가설 실험이다. 통과해도 자유 생성에서 화성이 맞는다는 증명은 아니다.

## 데이터 (`scripts/build_guide_dataset.py` → `data/bebop_guide`)
- `data/bebop_rh`와 곡, split, 파일 이름이 같다(train 189 / val 28 / test 18)
- 곡마다 0.9375초 창을 이어 붙인 스트림 `[guide][솔로 창][guide][솔로 창]…`
  - 솔로: 전체 음의 50 ms 최고음 중 G3 이상(`bebop_rh`와 같은 규칙)
  - guide: 그 창의 accompaniment proxy. pc가 2개 미만이면 이전 guide를 이어 쓴다. 첫 guide가 나오기 전 창에는 guide가 없다
- 런타임과의 대응
  - history 없음: primer = `[guide]` → 스트림 시작과 같다
  - history 있음: `[과거][guide]` → 스트림 중간과 같다
- 한계
  - 손 분리가 아니다. 오른손 내성이 섞여 있다
  - guide가 과거 솔로 뒤에 시간상 0.85창만큼 끼어든다. 실제 연주에는 없는 시간이다
  - loss는 guide 토큰에도 걸린다(trainer에 타깃 마스크가 없다)

## 학습 (bebop 어댑터와 같은 레시피, 데이터 형식만 다르다)
- `run_mehldau_update_budget_diag.py --checkpoint outputs/tvm/common_base/checkpoint_epoch8.pt --data-dir data/bebop_guide --mode budget --budget-seconds 6000 --planned-epochs 43 --batch-size 4 --gradient-accumulation 4 --lr 3e-4 --label-smoothing 0.1 --seed 42 --device mps --lora-targets out_proj,qkv`
- 약 516 update. 마지막 스냅샷을 쓴다. val로 고르지 않는다
- 출력: `outputs/bebop_guide/{run,export}`. 기존 체크포인트는 건드리지 않는다
- 컴퓨트 상한: 6000초. 넘으면 중단하고 기록한다. 재시도는 한 번만 한다(같은 설정)

## 주평가 (학습 전 고정, 봉인 대상 아님)
- U2와 같은 스크립트·창·조건(val 28곡, 491창). 모델: base, bebop, **guide**
- **통과:** guide 어댑터가 둘 다 충족
  1. Δshuf CI 하한 > 0.024(bebop Δshuf CI 상한). bebop보다 분명히 크다는 뜻이다
  2. Δshuf 평균 ≥ 0.07(base 0.035의 2배)
- 보고만
  - NLL true(같은 val 창)
  - Δabs
  - 곡 macro, Δshuf > 0인 곡 수
- 미달이면 기록하고 끝낸다. 형식이나 하이퍼파라미터 sweep은 하지 않는다

## 봉인 (U3가 끝날 때까지)
- guide 어댑터의 자유 생성 평가, 청취, 런타임 통합은 하지 않는다
- 이 평가들은 U3 대조 반응표로 지표 타당성을 확인한 뒤에 별도로 등록한다
- U3 대조가 실패하면 A 산출물은 탐색용으로만 남긴다

## 노출 이력

- val과 test는 화음 적합 지표 탐색에서 이미 봤다
- 그래서 이번 결과는 모두 **탐색**으로 표시한다

## 생성 평가 (봉인 해제 후 등록: U3 결과 3f4008f9 이후, 학습 결과를 보기 전)
- U3 판정에 따라 rel_js(합산 분포)만 게이트로 쓴다. fit과 clash는 집단 수준 보고로만 쓴다
- 스크립트: `scripts/guide_gen_eval.py`
- 데이터: val 491창
- 생성 조건: 각 창의 true guide만 primer로 준다(history 없는 런타임 계약). 0.9375초, T 1.0, top-k 32, top-p 0.95, grammar mask, seed 2개
- 솔로: 생성 결과의 G3 이상 최고음 선율
- 비교: bebop, guide 어댑터, 실제(같은 창의 실제 솔로)
- 보고만
  - 같은 생성을 donor 화성으로 잰 fit. guide 화성을 따르는지 보는 값이다
  - 빈 창 수
- **통과:** guide 어댑터가 모두 충족
  1. rel_js < bebop
  2. rel_js ≤ 0.10. 실제 val은 .048, 화성 교환 대조는 .088이다
  3. fit ≥ bebop + 0.03(집단 수준)
  4. 초당 음 수가 실제 창의 0.67–1.5배
- 미달이면 기록한다. sweep은 하지 않는다. 통과해도 런타임 통합과 청취는 별도 단위다. "듣기 좋다"는 주장은 하지 않는다

원시값은 `outputs/bebop_guide/{run,export,eval_nll,eval_gen}/`(git 미추적). 사전 등록(cb3d91d8)과 생성 평가 등록(76226150)은 학습 결과를 보기 전에 push했다.

- 사전 규칙대로 형식과 하이퍼파라미터 sweep은 하지 않는다

**가장 중요한 관찰(탐색, 원인 확정 아님)**
- **같은 화성 출처(실제 accompaniment proxy guide)를 주면 기존 bebop 모델은 이미 실제 비밥에 가깝다**
  - rel_js .049(실제 .048), fit .321(실제 .335)
  - 준 화성을 따른다. 받은 guide로 재면 fit .321, 다른 곡 화성으로 재면 .228이다
  - 실제보다 큰 것은 반음 충돌뿐이다(.225 vs .169)
- 그래서 "모델이 화성을 못 따른다"는 설명은 약해졌다. 아스트라가 지적했듯이 "반주 조건을 본 적 없음"은 너무 강한 주장이었다
- 사용자가 들은 틀린 음은 **런타임이 주는 화성 입력 쪽**에서 왔을 가능성이 있다. 근거는 둘이다
  1. guide 보이싱 결함(G7에 3음이 없고, m7b5가 m7과 같다)
  2. 학습 때와 다른 guide 형식(항상 4 pc, 고정 음역)
  - 컴핑 음과 솔로의 반음 충돌도 후보다
- 다음 단위에서 확인한다: 같은 모델과 같은 코드 진행에서 런타임 guide(기존) vs 계약 guide(결함 수정)를 비교하고, 같은 코드 pc 기준으로 상대 비교한다

## 결과 노출 후 교정 (아스트라 공동 리뷰 3, 2026-10-03)
리뷰는 결과가 나오기 전에 작성됐다. Claude가 받아 반영한 시점은 결과를 본 뒤다. 그래서 아래는 **결과 노출 후 교정**이다. 원래 판정(주평가·생성 평가 모두 미달)은 그대로다. 교정을 반영해도 결론은 같다.
- **H1(등록 모순):** 생성 평가 판정 3(fit ≥ bebop + .03)은 U3에서 fit이 게이트 자격을 잃었는데도 다시 게이트로 넣은 것이다. 교정본에서는 fit을 보고로만 쓴다. 교정본으로 봐도 판정 1(rel_js < bebop)이 ❌라 미달은 같다
- **H2:** .10은 근거 없는 분포 상한이다. harmony_swap(.088)도 이 기준을 통과한다. rel_js는 order_shuffle에 반응하지 않고, partial_shift에서는 오히려 좋아진다. 그래서 **릭의 일관성이나 막 친 음을 판정할 수 없다.** 통과해도 추천하거나 품질을 승격하는 근거로 쓰지 않는다
- **M1(U2 donor 교란):** shuffled donor의 pc 수와 guide 토큰 길이를 맞추지 않았다(2 pc = 6토큰, 4 pc = 10토큰). 같은 pc 수의 다른 곡 donor로 다시 분석했다(`outputs/harmony_contract/u2_matched/`, 사후 분석). 제외된 창은 0개다
  | 모델 | Δshuf 원래 | **Δshuf matched [95% CI]** | Δshuf > 0인 곡 |
  |---|---|---|---|
  | base | .035 | **.021 [.010, .033]** | 22/28 |
  | bebop | .017 | **.014 [.006, .020]** | 21/28 |
  | tatum | .034 | **.021 [.011, .032]** | 21/28 |
  | mehldau | .024 | **.021 [.010, .032]** | 19/28 |
  | guide | .017 | **.016 [.005, .027]** | 21/28 |
  - 원래 차이의 일부는 길이 교란이었다. 그래도 모든 모델이 CI > 0이다
  - 원래 U2의 go(.017 vs .0175)는 탐색할 동기였을 뿐이다. 무반응이나 학습 부족을 진단한 것이 아니다
- **M2(paired 모델 차, guide − bebop, 곡 bootstrap)**
  - Δshuf: **.000 [−.009, .009]**
  - true NLL: −.129 [−.153, −.106]
  - shuffled NLL: −.129 [−.153, −.105]
  - true와 shuffled가 똑같이 좋아졌다. guide 학습은 **형식에 대한 적응**이었고 화성 내용에 대한 반응은 늘리지 않았다
- **M3(생성 평가의 한계):** 이번 생성 평가에는 다음 기록이 없다
  - raw 문법·시간 유효성, underfill
  - 저음 guide를 다시 출력하거나 G3 컷으로 뺀 음 수
  - trim량, 창·seed별 원시 토큰
  - [guide][RH] 스트림으로 학습한 모델은 생성 중에 다음 guide로 넘어갈 수 있다. 그 음이 필터로 빠져 솔로만 평가됐을 수 있다. 다음 평가부터 원시 출력을 보존하고 이 항목들을 기록한다
- **문서 표현 제한**
  - "history 없음 = 스트림 시작"은 곡마다 한 번뿐이다. 학습 crop 대부분은 중간 문맥이다
  - 연속 0.9375초 분할과 carry 30.6%는 U2 평가 창의 분포(2초부터 4초 간격, proxy ≥ 2 pc만)와 다르다
  - guide 음역이 최대 59(B3)라 솔로 컷(G3 = 55)과 겹친다. 역할이 혼동될 위험이 있다
  - 이번 A는 "이 스트림 레시피의 탐색 결과"로만 한정한다. target-only loss나 표본 경계 마스킹은 다음 별도 가설로 둔다
