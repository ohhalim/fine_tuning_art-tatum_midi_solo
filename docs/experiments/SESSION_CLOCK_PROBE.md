# probe 입력을 세션 시계 기준으로 — 사전 등록

작성 2026-09-29. 이슈 #1569. 가상 CoreMIDI 포트

**이 절은 측정 전에 작성했다.** 구현은 측정 전에 끝냈다.

## 문제
- `run_live_select_probe.py`는 입력을 **실행 시작 뒤 N초**에 보냈다. 세션 시계(0번 마디 다운비트)는 모델 로딩이 끝난 뒤 정해진다
- 그래서 로딩 시간 차이만큼 입력이 블록 경계와 스냅샷 시각에 닿는 위치가 실행마다 달라졌다
- 그 결과 입력이 있는 실행끼리의 비교가 성립하지 않았다(#1553 후속 reserve_v2, #1567 기준 1)

## 변경
- 런타임 `--announce-clock`: 연주 전에 `SESSION_CLOCK_START_NS <0번 마디 다운비트의 perf_counter_ns>`를 출력한다
  - macOS에서 `perf_counter_ns`는 프로세스 사이에 같은 시계다(자식 프로세스 값이 부모의 앞뒤 측정 사이에 들어오는 것을 확인했다)
- probe `--session-relative`: 시각을 세션 시계 기준 초로 해석한다. 자식 출력에서 기준값을 읽고, 그 시각에 맞춰 보낸다(2 ms 전까지 sleep, 이후 spin)

## 측정
- 반 마디 블록, 쌍 S(`--adapter-control program`), 128 BPM, 16마디
- 스냅샷 시각(블록 k 생성 시작 ≈ k × 937.5 − 519 ms)과 입력 창 4초의 경계에서 떨어진 시각을 골랐다
  - PC 1: 7.450 s
  - PC 0: 11.200 s
  - 음 C5 E5 G5 B5 D6: 13.075 s부터 0.1875 s 간격
- 실행 순서: seed 42, 42, 43, 43

## 판정 (모두 충족하면 합친다)
1. 도착 정확도: 런타임이 기록한 PC 도착 시각(`received_ms_from_start`)과 의도한 시각의 차이가 4회 모두 ±10 ms 이내다
2. 결정성: 같은 seed 두 실행이 연주 마디 16/16, 입력이 든 블록 목록과 입력 메시지 수, PC의 소비 블록까지 모두 같다(두 쌍 모두)
3. 4회 모두 fallback 0(미스는 보고만 한다)

## 1차 결과 — 기준 1·3 충족, **기준 2 미달**(원인 확인)
원시값: `docs/experiments/session_clock/summary_v1.json`.
- 기준 1 도착 정확도: PC 도착 오차가 0.17–3.06 ms다(4회) ✓
- 스냅샷 구조
  - 입력이 든 블록과 메시지 수가 네 실행 모두 같다: 9–14번 블록 각 1개, 15/16/17/18/19번 블록 6/11/10/10/8개
  - PC 소비 블록도 네 실행 모두 [9, 13]으로 같다
- 기준 2 결정성: 연주 마디가 seed 42 쌍 14/16, seed 43 쌍 13/16이다 ✗. 달라진 마디는 **입력 음이 든 마디(7–9)뿐**이다
- 기준 3: fallback 0, 미스 0(4회)
- **원인(오프라인으로 확인):** primer의 시간 토큰은 10 ms 단위다. 음 간격 187.5 ms는 반올림 경계(18.75 단계)에 정확히 걸린다. 그래서 음 하나의 도착이 0.5 ms만 흔들려도 primer 토큰이 달라졌다. 코드 결함이 아니라 내 측정 설계(입력 시각 선택) 문제다

## 재측정 (사전 등록, 실행 전, 1회)
- 변경: 모든 입력 이벤트 사이 간격을 **10 ms의 정수배**로 둔다. 음은 13.070 s부터 0.190 s 간격, note_off는 +0.250 s다. 그러면 반올림 경계까지 ±5 ms 여유가 있어 측정된 지터(≤ 3 ms)를 흡수한다
- 조건과 판정은 위와 같다(도착 ±10 ms, 같은 seed 쌍의 연주 마디 16/16과 입력 블록·소비 블록 동일, fallback 0)

## 재측정 결과 — 기준 1·2 미달(한 실행의 전달 지연)
원시값: `docs/experiments/session_clock/summary_v2.json`.
- seed 43 쌍: PC 도착 오차 ≤ 0.36 ms, **연주 마디 16/16 동일**, 입력 블록·소비 블록 동일. 입력을 10 ms 격자에 맞추면 입력이 있는 실행도 결정적으로 재현됐다
- seed 42 쌍: run1의 두 번째 PC가 **16.66 ms** 늦게 도착했다(기준 ±10 ms 초과). 연주 마디는 13/16(입력 마디만 다름)
- 측정 중 부하 평균은 약 4.4–5.7이었다(외부 프로그램)
- 판정: 사전 기준 미달이므로 이 형태로는 합치지 않는다
- 한계: 음 이벤트의 도착 시각은 기록되지 않아서 seed 42 쌍의 입력 마디가 달라진 원인을 확정할 수 없었다

## v3 (사전 등록, 실행 전, 1회) — 도구 정확도와 전달 지연을 분리
- 추가(동작 변화 없음)
  - 런타임 리포트 `input_log`: 입력 버퍼가 가진 모든 메시지(최대 512개)의 세션 기준 도착 시각
  - probe `arrival_error_ms`: 보낸 메시지마다 "런타임 도착 − 의도 시각"
- 조건: v2와 같다(10 ms 격자 입력). seed 42, 42, 43, 43, 44, 44
- **판정(모두 충족하면 합친다)**
  1. 도구 정확도: probe가 기록한 보낸 시각(`sent.at_s`)이 의도 시각의 ±1 ms 이내다(전 실행, 전 메시지)
  2. 전달 지연은 보고만 한다: `arrival_error_ms` 분포
  3. 결정성: 두 실행의 모든 메시지 도착 오차가 ≤ 4 ms인 쌍은 연주 마디가 16/16 같다. 그런 쌍이 3쌍 중 2쌍 이상이어야 한다. 아니면 판정 불가로 기록한다
  4. fallback 0

## v3 결과 — 결정성 충족, **도구 정확도 미달**
원시값: `docs/experiments/session_clock/summary_v3.json`.
- 기준 3 결정성: 세 쌍 모두 연주 마디 **16/16 동일**하다. 판정 대상 쌍(모든 도착 오차 ≤ 4 ms)은 seed 43·44의 2쌍이다 ✓
- 기준 1 도구 정확도: seed 42 두 실행에서 probe가 보낸 시각이 **5.2 ms, 3.2 ms** 늦었다(±1 ms 기준) ✗. 나머지 4회는 ≤ 0.8 ms였다
- 기준 4: fallback 0. 미스 1(run1)은 보고만 한다
- 도착 오차가 보낸 시각 오차와 거의 같다. 지연은 전달 경로가 아니라 **probe 프로세스 안**(1 ms sleep이 목표 2 ms 전을 넘겨 깨어남)에서 생겼다. 측정 중 부하 평균은 약 5.5였다
- 판정: 미달이므로 이 형태로는 합치지 않는다

## v4 (사전 등록, 실행 전, 1회) — probe 전송 타이밍 보강
- 변경
  - probe 전송 스레드에 런타임 스케줄러와 같은 QoS(user-interactive)를 적용한다. 결과는 `sender_qos`에 기록한다
  - spin을 목표 10 ms 전부터 시작한다
- 조건과 판정은 v3와 같다(기준 1 ±1 ms, 기준 3 판정 대상 쌍 16/16, 기준 4 fallback 0)

## v4 결과 — 미달. **반복을 멈추고 도구 코드는 합치지 않는다**
원시값: `docs/experiments/session_clock/summary_v4.json`. 측정 중 부하 평균은 4.5–6.5였다(외부 브라우저 렌더러가 CPU를 계속 씀).
- 기준 1 도구 정확도: 보낸 시각 오차 최대가 9.6 / 0.2 / 0.4 / 1.8 / 10.5 / 2.1 ms다(QoS 적용 확인) ✗
- 기준 3 결정성: 판정 대상 쌍(도착 ≤ 4 ms)은 seed 43 한 쌍뿐이다(16/16) → 2쌍 미만이므로 **판정 불가**. 참고로 seed 44 쌍(대상 아님)도 16/16, seed 42 쌍은 12/16이었다
- 기준 4: seed 42 run1에서 fallback 1, 미스 5 ✗

## 종합 (v1–v4)
- 세션 시계 기준 전송은 실행 간 입력 위치 차이를 수백 ms(모델 로딩 차이)에서 **대부분 ≤ 3 ms, 부하 중 최대 약 10 ms**로 줄였다
- 입력 시각을 10 ms 격자에 맞추고 두 실행의 도착 오차가 모두 ≤ 4 ms이면, 입력이 있어도 연주가 **완전히 재현**됐다(판정 대상 쌍 3/3: v3 2쌍, v4 1쌍)
- 사전 등록한 합칠 조건은 v2·v3·v4에서 모두 미달이었다. 원인은 부하 중 Python 송신 스레드의 깨어남 지연이다(QoS로도 해결되지 않음). 결과를 보고 기준을 바꾸지 않으려고 **도구 코드(`--announce-clock`, `--session-relative`, `input_log`)는 합치지 않는다**. 코드는 브랜치 `feat/issue-1569-session-clock-probe`에 남긴다
- 입력이 있는 실험의 비교는 여전히 성립하지 않는다(#1567과 같은 결론). 다음 선택지(각각 한 질문)
  1. 부하 없는 머신에서 v4 조건을 다시 잰다
  2. 송신을 Python 밖(CoreMIDI 타임스탬프 예약 전송 등)으로 옮긴다
  3. 입력 실험을 재현성에 기대지 않는 통계 설계(seed를 늘리고 짝지은 비교)로 바꾼다
