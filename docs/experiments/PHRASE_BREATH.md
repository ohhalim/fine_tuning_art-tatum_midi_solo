## 근거
- #1620: 비밥 런타임의 맨 위 선율은 프레이즈 중앙값 26음, 쉼 4.5%였다. 데이터는 16음, 7.6%다
  - 블루스 seed 42는 쉼 3.3%, 프레이즈 중앙값 98음으로 거의 쉬지 않았다
- 사용자: 솔로가 "릭"처럼 들리기를 원한다. 너무 빠르지 않게
- 합의
  - 쉼 유도만 **단독**으로 대조한다
  - 코드톤 착지는 바꾸지 않는다. 착지는 나중에 별도 arm으로 본다
  - 둘을 한꺼번에 바꾸면 무엇 때문에 달라졌는지 가를 수 없다

## 변경 (opt-in, 기본값 끔)
- `--phrase-breath N`(`--solo-line` 필요)
  - 맨 위 선율이 0.3초 넘는 쉼 없이 N음을 치면, 마지막 음이 끝난 뒤 0.4초 안에 시작하는 음을 뺀다
  - 음은 빼기만 한다. 옮기거나 새로 만들지 않는다
  - 상태는 반마디 블록을 넘어 이어진다. 기준은 생성 순서다. 채택 여부는 반영하지 않는다(한계)
- **N = 24로 고정한다.** 데이터 프레이즈 중앙값 16의 1.5배다. 0.4초도 고정값이다. 결과를 보고 다시 고르지 않는다

## 실행
- `--preset bebop --solo-line`, 진행 3개(ii–V–I C 16마디 128 / F 블루스 12마디 120 / C 단조 16마디 128) × seed 42·43
- 팔 두 개를 같은 seed로 교대 실행한다
  - **A:** 쉼 유도 없음. 새로 돌리고, #1620 실행은 재사용하지 않는다
  - **B:** `--phrase-breath 24`
- 측정은 `--comp` 없이 한다. 지표는 송신 이벤트의 예정 시간축 기준이다(#1623)

## 판정 (실행 전 고정, B 6회 합산)
- **통과:** B가 모두 충족
  1. 프레이즈 중앙값 ≤ 24. 장치가 실제로 작동하는지 보는 확인이다
  2. 쉼 시간 비율이 A보다 크다. 그리고 데이터의 0.5배(3.78%) 이상이다
  3. 초당 음 수가 데이터의 0.67–1.5배(2.49–5.57)다
  4. 솔로 코드톤 비율 ≥ A − 0.03
  5. `rendered_invalid` 0. 생성 최대 시간 ≤ A 최대 × 1.1
- 대체 패턴과 deadline miss는 보고만 한다. 쉼 유도는 생성이 끝난 뒤 음을 빼는 것뿐이라 생성 시간을 바꾸지 않는다(5번으로 확인). 실시간 견고성은 #1624에서 따로 본다
- 보고만
  - 블루스 프레이즈 중앙값
  - 뺀 음의 비율
  - 프레이즈 끝 코드톤. 실제 데이터에는 코드 표기가 없어 같은 조건의 기준값을 만들 수 없다. 그래서 A–B 비교로만 쓴다
- 통과하면 FL 문서에 `--phrase-breath 24`를 선택지로 적는다. 청취용 피아노 렌더를 페이지에 올린다. 미달이면 기록만 하고 N을 다시 고르지 않는다

- **판정: 통과.** 다섯 기준을 모두 충족했다
- 해석상 주의
  - **쉼이 데이터보다 많아졌다**(12.5% vs 7.6%, 1.65배). 사전 기준은 하한만 두었으므로 판정에는 영향이 없다. 실제 비밥보다 더 자주 끊어 들릴 수 있다. 청취로 확인할 부분이다
  - 프레이즈 중앙값 22는 여전히 데이터 16보다 길다. 정정(#1627 리뷰): 처음에는 "N = 24라 그 아래로 내려가지 않는 것이 당연하다"고 적었는데 틀렸다. N은 프레이즈 길이의 상한이지 하한이 아니다. 자연스러운 쉼만으로도 중앙값은 16 아래로 내려갈 수 있다. 22는 장치가 긴 프레이즈를 잘랐지만 짧은 프레이즈가 충분히 많지는 않았다는 뜻이다
  - 프레이즈 끝 코드톤이 0.38에서 0.46으로 올랐다. 착지는 바꾸지 않았다. 프레이즈가 끊기는 위치가 달라져서 생긴 부수 효과일 수 있다. 코드 표기가 있는 실제 기준이 없어 좋아졌다고 말하지 않는다
  - A는 #1620과 같은 구성이지만 다시 돌렸다. 값이 거의 같다(5.27 vs 5.30음/s, 쉼 4.5% 동일). 실행 간 재현성은 괜찮아 보인다
- 사전 규칙대로 FL 문서에 `--breath 24`(`fl_live.py`)를 **선택지**로 적었다. 기본값은 꺼짐이다
- 청취용: `--solo-line --comp --phrase-breath 24`, ii–V–I와 블루스 seed 42를 피아노로 렌더해 청취 페이지 B1·B2에 올렸다. 컴핑은 #1623 수정 후 규칙(시간이 겹칠 때만 뺀다)이다
- 다음 후보(협업 리뷰 대상)

  - 쉼 길이와 N은 다시 고르지 않는다. 청취 결과를 받은 뒤 새로 등록한다

## 리뷰 반영 (2026-10-02, 아스트라 공동 리뷰 2)
- **H1: 컴핑 경로에서 숨 쉬기가 적용되지 않았다**
  - `solo_with_comp_tokens`가 `line_filter`를 받기만 하고 호출하지 않았다. 구현할 때 문자열 치환이 맞지 않았는데, 그걸 확인하지 않았다
  - FL 기본값이 `--comp` 켬이라 `fl_live.py --breath`는 효과가 없었다
  - 처음 올린 청취용 B1·B2도 숨 쉬기가 빠진 소리였다(보고서 `dropped_notes: 0`)
  - 수정
    - 필터는 블록마다 맨 위 선율을 뽑은 직후 **한 번만** 적용한다. 그 뒤에 컴핑 충돌을 판정한다
    - 재인코딩이 실패해도 필터를 다시 호출하지 않는다(상태가 두 번 바뀌지 않게)
    - 회귀 테스트를 추가했다. 수정 전 코드에서는 실패한다
  - **판정에는 영향이 없다.** A/B 12회는 `--comp` 없이 돌렸다
  - 재렌더한 B1·B2: 뺀 음이 ii–V–I 10개, 블루스 12개다. 솔로 음은 측정에 쓴 B seed 42 실행과 같다(차집합 0)
- **M2: 판정 전 조건을 더 확인한다**
  - 디코딩: T 1.0, 문맥 carry 0, history 끔, pattern cache 끔
  - 숨 쉬기 설정은 `max_notes`와 `rest_s`(0.4)를 모두 맞춰 본다
  - seed와 체크포인트가 기록되기 전의 #1620 실행은 "legacy"로 따로 표시한다. 이 실행들은 디렉터리 이름으로만 확인한다
  - 다시 계산해도 판정은 같다
- **한계(남은 일):** 숨 쉬기 상태는 생성 순서를 따른다
  - 블록이 폐기되거나 fallback이 나면 실제로 재생된 음 수와 어긋난다
  - 이번 A/B는 fallback이 0이어서 영향이 없었다
  - "최종 재생음 기준 제한"이라고 보장하지 않는다
  - 채택 상태를 반영하려면 선행 생성과 동기화하는 작은 설계가 따로 필요하다. 그 smoke 테스트에는 폐기 → fallback → 다음 채택 경로를 넣는다
