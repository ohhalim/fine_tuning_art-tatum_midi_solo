# Aria MLX 생성·토큰 스트림·스케줄러 가상 시각 연결 (#1743) — 사전 등록

기반 점검을 세 번 했다.
- MLX KV 이어 생성이 처음부터 계산한 것과 같다(#1737)
- 생성 중간 되돌리기가 안전하다(#1739)
- 송출 계약은 상태기계로 구현하고 회귀 22개로 고정했다(#1741)

이 단위는 셋을 한 루프로 연결해 본다. 가상 시각으로 돌리고 실제 MIDI는 내보내지 않는다. 소리나 코드 제어가 나아지는지는 보지 않는다.

## 질문

1. 반 마디 블록마다 확정할 음이 제때 만들어지는가? 블록 생성 시간의 중앙값, p99, max는? 샘플 수와 cold/warm을 함께 적는다
2. 코드 입력을 흉내 내 미확정을 버리고 다시 생성하면 시간이 얼마나 걸리는가? 제어 토큰은 넣지 않고, 되돌리기만 흉내 낸다
3. 연결된 상태에서도 계약이 지켜지는가?

## 루프 (`scripts/aria_mlx_stream_loop.py`)

- 128 BPM 기준으로 블록 B = 반 마디 937.5 ms, 1박 = 468.75 ms. 48블록(약 45초)
- 블록 k의 가상 시각 now = t0 + k·B. t0은 prompt 마지막 완결 음의 onset이다
  1. 코드 입력 블록(k = 8, 16, 24, 32, 40, 4마디마다)이면 `rollback_to_committed()`
  2. 마지막 완결 음이 확정 지평 H = now + B + 1박에 닿을 때까지 생성한다. 이 시간이 **지평까지 시간**이다
     - 마감은 1박이다. now + 1박 전의 음은 앞 블록에서 이미 확정됐기 때문이다
  3. 이어서 한 블록 분량(H + B까지)을 추측으로 더 생성한다. 블록당 최대 64토큰
  4. `commit_until(H)` → 스케줄러에 예약 → 가상 시각 now까지 tick
- 샘플링은 #1726 샘플러다(단계마다 Exp(1) 노이즈 하나, temperature 1, min_p 없음). 형식 마스크(`aria_grammar_mask`)를 건다
  - 운영 조건으로 `<D>`·`<E>`도 막는다. 실시간 파트너는 연주를 끝내지 않기 때문이다
- 처음 KV는 비어 있으므로 토큰 스트림을 전체 reset 상태로 시작해 prompt를 prefill한다
- 가중치와 캐시는 float32, 캐시 용량 4,096. 범위를 넘으면 forward 전에 거절하고 멈춘다(문맥 자르기는 구현하지 않았다)

## 검사 (실행 전 고정)

| 검사 | 기준 |
|---|---|
| 48블록 모두 실행 | 중간에 멈추지 않음 |
| 모든 블록이 지평에 도달 | 블록당 64토큰 안에 H에 닿음 |
| 확정 구간 불변 | 블록마다 확정 토큰열이 이전 확정 토큰열을 앞부분으로 포함 |
| KV가 스트림을 따라감 | 블록 끝마다 `토큰 수 − kv_valid_length` ∈ {0, 1} |
| 확정 토큰 형식 유효 | `aria_token_validity` 유효, 음 중간에서 끝나지 않음 |
| note-on마다 note-off 하나 | 중복 note-on 없음, note-on과 note-off ID 집합이 같음 |
| 정지 뒤 울리는 음 없음 | `stop()` 뒤 sounding 비어 있음 |

**보고만 하는 것 (합격선 없음)**
- cold 첫 블록
- warm 블록(코드 입력 블록과 첫 블록 제외)의 지평까지 시간, 추측 포함 블록 시간
- 코드 입력 블록의 지평까지 시간
- 각각 n, 중앙값, p99(nearest rank), max
- 1박·반 마디 마감을 넘은 블록 수
- n이 100보다 작으면 p99는 가장 큰 관측값 중 하나다. 가상 시각이라 생성 시간만 실측이고, 키 입력에서 소리까지의 지연이 아니다

## 하지 않는 것

실제 MIDI 포트·타이머, 제어 토큰 주입, 착지 바이어스, 재순위, CFG, 양자화, 학습, 다운로드, 소리·제어 개선 주장.
