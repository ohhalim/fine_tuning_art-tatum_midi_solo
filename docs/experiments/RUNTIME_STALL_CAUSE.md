# 연속 런타임 드문 멈춤 원인 — 사전 등록

작성 2026-09-27. 이슈 #1490, 브랜치 `exp/issue-1490-runtime-stall-cause`.
선행: `TATUM_REALTIME_TEMPO.md`(R1e: Tatum 240 BPM에서 81–131 ms 멈춤, 13회 중 1회).

`quality_claimed: false` · 가상 CoreMIDI 포트 · CPU · 청취 없음

**이 절은 실행 전에 작성했다.**

## 계측 (`--stall-trace`, opt-in)
- **GC:** `gc.callbacks`로 각 수집의 시작·끝 시각(`perf_counter_ns`)과 세대를 기록한다
- **프로세스 내부 heartbeat:** 2 ms마다 깨는 데몬 스레드. 예정보다 5 ms 넘게 늦게 깬 구간을 기록한다. GIL이나 프로세스 전체가 멈추면 여기에 잡힌다
- **외부 heartbeat:** 같은 방식의 **별도 프로세스**다. GIL을 공유하지 않는다. macOS의 `perf_counter_ns`는 시스템 전역 시계(mach_absolute_time)라 시각을 비교할 수 있다. 시스템 수준 정지는 여기에도 잡힌다
- **늦은 이벤트:** 스케줄러 송신 기록 중 지각 > 10 ms인 이벤트다. 늦은 구간 [목표 시각, 송신 시작]과 겹치는 계측 구간으로 분류한다

## 분류 규칙 (이벤트마다, 우선순위 순)
1. 1 ms 이상 GC 구간과 겹치면 → **GC**
2. 외부 heartbeat 지연과 겹치면 → **시스템**
3. 내부 heartbeat 지연과만 겹치면 → **프로세스 내부**(GIL 등)
4. 어디에도 겹치지 않으면 → **미설명**. 스케줄러 스레드만 늦은 경우다
- 참고로 그 순간 생성 중이었는지(`producer_busy`)도 기록한다

## S1 — 판정
- 조건: Tatum u518, 240 BPM, 16마디, spin 5 ms, seed 60–89(30회)
- 1차 표본: 지각 > 10 ms 이벤트 전체. 2차 표본: > 20 ms(미스)
- **판정: 1차 표본이 10개 이상이고 한 범주가 그중 2/3 이상이면 그 범주를 주원인으로 기록한다.** 표본이 10개 미만이거나 2/3를 넘는 범주가 없으면 "미확정"이다
- 계측 자체의 영향을 보기 위해, 같은 조건에서 `--stall-trace` 끔 10회의 지각 분포와 비교한다(참고값)
- 우연한 겹침을 가늠하기 위해 각 계측 구간의 시간 점유율(기저율)을 함께 보고한다. 분류 규칙 자체는 바꾸지 않는다(스모크 실행에서 외부 heartbeat도 5–15 ms 늦잠이 흔했다. 20초에 25회, 최대 14.7 ms)
- 조치(S2)는 주원인이 확정됐을 때만 하며, 별도로 등록한다

## S1 결과 — 주원인: 시스템 수준 (사전 규칙 충족)
`outputs/runtime_stall/s1_traced/`(30회), `s1_untraced/`(10회). 요약: `runtime_stall/s1_summary.json`.

| 범주 | 지각 > 10 ms 이벤트 | 비율 |
|---|---|---|
| **시스템** (외부 heartbeat도 늦음) | **48** | **94%** |
| 미설명 | 3 | 6% |
| GC | 0 | 0% |
| 프로세스 내부 | 0 | 0% |

- 표본 51개(≥ 10) 중 한 범주가 2/3 이상 → **판정 확정: 시스템 수준**
- 우연한 겹침으로는 설명되지 않는다. 외부 heartbeat 지연이 시간에서 차지하는 비율은 평균 **2.2%**인데, 늦은 이벤트의 94%가 그 구간에 들어갔다
- 늦은 이벤트의 **94%는 생성이 쉬고 있을 때** 났다(`producer_busy` 6%). CPU가 한가할 때 OS가 스레드를 늦게 깨우는 쪽으로 보인다(타이머 병합, 전원 관리 등. 추정)
- GC: 최대 정지 14.6 ms가 있었지만 늦은 이벤트와 겹친 적은 없다. 1 ms 이상 GC는 30회 동안 30번이었다
- 2차 표본(> 20 ms)은 계측 30회에서 **0건**이다. 큰 멈춤의 원인은 직접 관측하지 못했다(한계)

| | 실행 | 지각 p50 중앙값 | p99 중앙값 | 최대 | 10 ms 초과/실행 | 미스가 난 실행 |
|---|---|---|---|---|---|---|
| 계측 켬 | 30 | 0.063 | 6.3 | 16.3 | 1.7 | 0 |
| 계측 끔 | 10 | 0.057 | 4.0 | **86.8** | 0.5 | 1 |

계측(2 ms heartbeat 스레드와 외부 프로세스)은 작은 지각을 늘렸다. 반면 계측을 켠 쪽에서는 큰 멈춤이 없었다. 주기적인 활동이 깊은 유휴를 막는다는 해석과 맞지만 검증하지 않았다.

## S2 — 스케줄러 스레드 QoS 상향 (실행 전 등록)
- 조치: macOS `pthread_set_qos_class_self_np(QOS_CLASS_USER_INTERACTIVE)`를 스케줄러 스레드(메인 스레드)에 적용한다. 옵션은 `--thread-qos user-interactive`, 기본값은 변경 전까지 `default`다
- 조건: Tatum u518, 240 BPM, 16마디, spin 5 ms, 계측 끔. 팔 두 개(default vs user-interactive), 각 20회(seed 100–119, 같은 seed 사용), 교대 실행
- **채택 규칙:** 다음을 모두 만족하면 기본값을 user-interactive로 바꾼다
  1. 10 ms 초과 지각(실행당 평균)이 default 대비 50% 이상 감소
  2. fallback 0 유지
  3. 생성 p95 중앙값이 1.1배 이하
- 20 ms 넘는 미스가 난 실행 수는 두 팔 모두 보고한다. 드물어서 판정에는 쓰지 않는다

## S2 결과 — QoS user-interactive 채택
`outputs/runtime_stall/s2/{default,user-interactive}/`, 비교: `runtime_stall/s2_compare.json`. Tatum u518, 240 BPM, seed 100–119, 교대 실행, 계측 끔.

| | default (기존) | **user-interactive** |
|---|---|---|
| QoS 적용 확인 | — | 20/20 (`thread_qos.applied`) |
| 10 ms 초과 지각 / 실행 | 0.40 (합 8) | **0.10 (합 2), −75%** |
| 지각 p50 중앙값 ms | 0.059 | 0.061 |
| 지각 p99 중앙값 ms | 3.63 | 2.79 |
| 최대 지각 ms | 36.1 | **10.1** |
| 20 ms 넘는 미스가 난 실행 | 2 / 20 | **0 / 20** |
| fallback | 0 | 0 |
| 생성 p95 중앙값 ms | 751 | 756 (1.006배) |

- **채택 규칙 세 가지를 모두 충족한다**(−75% ≥ 50%, fallback 0, 생성 p95 1.006배 ≤ 1.1배) → 기본값을 **`user-interactive`**로 바꿨다
- 한계: 사건 수가 적다(8 vs 2). 큰 멈춤(> 20 ms)의 감소(2 → 0)는 판정에 쓰지 않은 보조 관찰이다. 단일 템포(240 BPM), 가상 포트, DAW 부하 없음 조건이다
- QoS 상향은 macOS 전용이다. 다른 OS에서는 `applied: false`로 기록되고 동작은 바뀌지 않는다
