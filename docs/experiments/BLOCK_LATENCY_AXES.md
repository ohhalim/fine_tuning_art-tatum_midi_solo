# 블록 계약 스케줄 대기와 갱신 주기 정리 (#1770)

작성 2026-10-16. #1766 따라가기 F4입니다. 문서 작업만 했고, 계약이나 코드는 바꾸지 않았습니다.

목적: 우리 블록 계약을 ReaLJam·StreamMusicGen과 같은 축으로 다시 써서, "사람이 코드를 바꾸면 그 변화를 반영할 수 있는 가장 이른 AI 음이 언제인가"를 한 표로 비교합니다. 들리는 반응이나 음악적 반응을 잰 문서는 아닙니다. 바꿀 수 있는 손잡이와 비용은 질문으로 남깁니다.

## 1. 세 가지 축

| 축 | 뜻 | 왜 중요한가 |
|---|---|---|
| **결정 간격** | AI가 어떤 음을 정할 때 쓴 마지막 사람 입력과, 그 음이 실제로 울리는 시각 사이의 간격 | 길수록 AI가 사람의 미래를 더 많이 짐작해야 합니다. StreamMusicGen의 t_f(미래 가시성)와 같은 축입니다. 그 논문은 이 간격이 줄수록 일관성이 좋아진다고 보고합니다 [원문 초록] |
| **갱신 주기** | AI가 사람 입력을 새로 반영해 계획을 다시 세우는 간격 | StreamMusicGen의 k(청크 길이)와 같은 축입니다. 길수록 처리량은 좋지만 반응이 느려집니다 [원문 초록] |
| **스케줄 대기** (처음 이름: 반응 지연) | 사람이 코드를 바꾼 순간부터, 그 변화를 반영할 수 있는 **가장 이른 스케줄 창**까지 | 결정 간격과 갱신 주기에서 나오는 구조적 하한입니다. 소리로 들리는 반응이나 음악적 반응을 잰 값이 아닙니다. 그 창에서 AI가 쉬면 실제 반응은 더 늦습니다(아스트라 교정) |

- StreamMusicGen의 t_f 부호는 "최신 입력 시각 − 출력 시각"으로 읽었습니다. 실시간에서는 0 이하이고, 0에 가까울수록 좋습니다 [판단, 초록 문장 해석]
- 아래 숫자는 모두 **생성 쪽 시간 구조**입니다. 키 입력, MIDI 전송, 신스, 오디오 버퍼 지연은 따로 더해집니다

## 2. 우리 계약 [코드 `scripts/block_contract.py`, `scripts/rt_producer.py`]

- 박 b = 468.75 ms, 블록 B = 반 마디 = 2박 = 937.5 ms (128 BPM, 4/4)
- 블록 k 시작 s_k = t0 + k·B에서 그때까지 관측한 사람 입력으로 조건을 만듭니다
- 이 블록이 확정하는 음의 시작 시각 창은 [s_k + b, s_k + B + b)입니다(확정 지평 h_k = s_k + B + b)
- 마감은 s_k + b입니다. 그 전에 확정·예약을 끝내야 합니다
- 확정 뒤에 다음 블록 분량을 추측 생성해 둡니다. 조건이 바뀌면 추측분을 버리고 다시 만듭니다(`must_regenerate`, 제안 규칙)

세 축으로 쓰면

| 축 | 박 단위 | 128 BPM | 90 BPM | 130 BPM |
|---|---|---|---|---|
| 결정 간격 | 1–3박 | 0.47–1.41 s | 0.67–2.00 s | 0.46–1.38 s |
| 갱신 주기 | 2박 | 0.94 s | 1.33 s | 0.92 s |
| 스케줄 대기 | 1박 초과 ~ 3박 이하 | 0.47–1.41 s | 0.67–2.00 s | 0.46–1.38 s |

- 이 표는 k ≥ 1 블록의 정상 상태와 마감 준수를 전제합니다. k = 0은 `block_contract.py`에서 t0 − 1000 ms 이하 관측으로 만드는 cold prebuffer라 제외합니다(아스트라 LOW)
- 평균을 말한다면 약 2박이지만, 입력 도착 위상이 블록 안에서 고르게 분포한다는 가정이고 실측이 아닙니다
- 스케줄 대기: 코드가 시각 c에 바뀌면 다음 블록 시작 s_k ≥ c까지 기다리고(0 ~ B), 바뀔 수 있는 가장 이른 음은 s_k + b입니다. 그래서 (b, B + b]입니다. 그 창에 AI 음이 없으면 실제로 들리는 반응은 더 늦습니다
- 이 구조가 성립하려면 다시 만드는 시간이 b보다 짧아야 합니다. #1743 Aria MLX 측정: 코드 입력 블록 재생성 0.08–0.24 s(n=5), 모두 1박(0.469 s) 안 [실험]
- 90–130 BPM은 #1762 사용자 기준입니다. 박 단위 값은 템포와 무관하고, 초 단위 값은 60/BPM에 비례합니다. 생성 시간이 템포와 무관한지는 단정할 수 없습니다. 템포가 바뀌면 박당 토큰 밀도와 문맥 자르기가 달라질 수 있고, 이것은 재지 않았습니다(아스트라 교정)

## 3. 다른 시스템과 비교

### 3.1 ReaLJam [코드 `agent_interface.generate_live`, 프런트엔드] + [실험 #1768]

- 프레임 = 16분음표(박당 4)
- 요청 프레임은 보낼 때의 현재 프레임 + 1입니다(`frontend/play_from_midi_input.js` 247행)
- 다음 요청 시점은 조건부입니다(263–269행). 응답을 받았을 때 아직 같은 프레임이면 한 프레임 뒤 `setTimeout`으로, 프레임이 넘어갔으면 바로 다시 요청합니다(아스트라 교정). 그래서 호출 벤치 숫자는 갱신 간격이 아닙니다
- **첫 수정 가능 프레임(코드 식):** `generate_live`에서 `commit_frames = len(chord_tokens) − lookahead + commitahead − frame`이고, 앞 호출이 요청 프레임 f_prev에서 lookahead만큼 만들었으면 `len = f_prev + lookahead`입니다. 그래서 첫 수정 가능 프레임 F = frame + commit_frames = **f_prev + commitahead**입니다. 요청이 늦어 이 값이 현재 요청 프레임보다 작으면 `commit_frames`가 0으로 잘려 F = frame이 됩니다
- 새로 정해지는 코드는 [F, frame + lookahead) 프레임입니다. 응답이 제때 오면 그 **절대 프레임**에 재생되므로, 호출 시간은 대기에 더해지지 않습니다. 응답이 F 시작보다 늦으면 이미 지난 프레임에는 반영되지 못합니다(마감 초과)
- **작은 예시(8:4, 정상 상태, 응답이 한 프레임 안에 옴):** 앞 요청이 프레임 99에 보내져 f_prev = 100. 다음 요청은 프레임 100에 보내져 frame = 101, `len = 108`, `commit_frames = 108 − 8 + 4 − 101 = 3`, F = 104 = f_prev + 4. 사람 입력이 프레임 100 안, 이 요청 직전에 들어오면 프레임 104부터 바뀔 수 있어 대기는 3–4프레임입니다. 요청 직후에 들어오면 다음 요청(F = 105)을 기다려 4–5프레임입니다

| 설정 | 첫 수정 가능 프레임 | 스케줄 대기(정상 상태 예시, 미측정) | 결정 간격(새로 정한 코드가 울리기까지) | 호출 지연(측정) |
|---|---|---|---|---|
| 화면 기본값 lookahead 16·commit 16(4박·4박) | f_prev + 16 | 약 15–17프레임 = 3.75–4.25박(80 BPM 2.8–3.2 s) | 약 15–16프레임 = 3.75–4박 | MLX 중앙값 139–156 ms |
| lookahead 8·commit 4(2박·1박) | f_prev + 4 | 약 3–5프레임 = 0.75–1.25박(80 BPM 0.56–0.94 s, 128 BPM 0.35–0.59 s) | 약 3–8프레임 = 0.75–2박 | MLX 중앙값 97–116 ms |

- 위 대기는 코드 식과 정상 상태 가정(요청이 프레임마다, 응답이 제때)으로 계산한 값입니다. **실제 제어 지연은 재지 않았습니다**
- 128 BPM에서 MLX 8:4의 p95(173–175 ms)는 한 프레임(117 ms)보다 길어서, 호출 사이에 프레임을 건너뜁니다. 그러면 commit 구간이 줄고 새로 정할 프레임이 늘어 호출이 더 느려집니다. 이 상호작용은 재지 않았습니다 [판단]
- ReaLJam은 사람이 멜로디, AI가 코드입니다. AI 출력이 박당 최대 4개 결정(코드 기호)이라 우리 솔로보다 결정 수가 적습니다

## 5. 홀수 박자 (#1762)

- 지금 상수는 `BEAT = 468.75`, `BLOCK = 937.5`(ms)로 128 BPM 4/4에 고정돼 있습니다 [코드]
- 7/8 같은 박자에는 "반 마디"가 박의 정수배로 떨어지지 않습니다(예: 2+2+3). 블록 경계를 박 단위로 둘지, 마디 안 그룹(2·2·3) 단위로 둘지 정해야 합니다
- 템포 범위 90–130을 받으려면 상수를 템포에서 계산하도록 바꿔야 합니다. 학습 입력 내보내기(#1756)도 같은 격자를 써야 합니다
- 이 문서에서는 정하지 않습니다
- **아스트라 권고(2026-10-16):** 연산 블록과 음악 마디를 분리합니다. 4분음표 기준 BPM, 박자표(time signature), 마디 안 그룹(예: 7/8 = 3+2+2)을 각각 별도 데이터로 둡니다. 블록 길이는 연산 단위로 정하고, 마디·그룹은 음악 정보로 따로 들고 다니는 설계입니다
