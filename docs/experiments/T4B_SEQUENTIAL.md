# T4b: 미리 정한 코드 진행 위에서 반마디씩 순차 생성 (사전 등록, 탐색)

작성 2026-10-08. 아스트라 #207 결정, #209 계약 검토. 새 학습·마스크·반복 패널티·캐시 구현 없음. `musical_quality_verified: false`.

## 질문 (하나)
사용자가 DAW에서 미리 정한 코드 진행을 주는 모드에서, Aria가 반마디마다 그 블록의 코드에 맞춰 이어 칠 때 두 가지를 묻는다.
- 바뀐 코드가 두 전환 방향(maj7 → m7, m7 → maj7)에서 반영되는가
- 블록 예산 안에 계산이 끝나는가

- 즉흥 키보드 입력에 바로 반응하는 모드는 범위가 아니다. 최종 목표를 포기하는 것이 아니라, 알려진 반주 위의 솔로부터 검증하는 것이다
- 사용자 청취나 기준 곡 제출을 시작 조건으로 두지 않는다

## 고정
- **맥락:** T4a의 디코드 프라이머 P2, P3, TA, TB. 오프라인 녹음 자료이고 지속음 end를 포함한다. 라이브 입력 검증이 아니다
- **근음:** T4a의 임의 proxy(P2 B, P3 G, TA C, TB G). 곡의 화성 정답이 아니다
- **블록:** T_0 = T4a의 코드 시각, T_j = T_0 + j × 0.9375초(j = 0…3)
- **계획 코드(입력):** 블록마다 onset T_j, 길이 0.9375초, 근음 C2–B2 + 3·7음 C3–B3, velocity 60
  - seed 1: maj7, m7, maj7, m7
  - seed 2: m7, maj7, m7, maj7
  - 두 순서를 seed에 엇갈려 배치해 순서 혼입을 기록한다
- **샘플러:** 공식 `sample_batch`, 배치 1, temp 0.98, min_p 0(실험 조건), 48토큰, force_end 끔. 블록마다 `torch.manual_seed(1000 × seed + j)`
- 4 맥락 × 2 seed × 4블록 = 32블록

## 시간축과 출처 계약 (#209)
- **블록 j 문맥** = 맥락 음 + 블록 0…j−1의 채택 생성 음 + 계획 코드 0…j
  - 미래 코드(j+1 이후)는 모델에 넣지 않는다. Aria 토큰은 시간순이라 미래 코드를 넣으면 생성이 그 뒤로 밀린다
  - 호스트는 진행 전체를 알고, 모델에는 현재 목표 블록의 코드까지만 보인다. "미래 코드 조건화"가 아니라 "미리 계산하기 위한 lookahead"다
  - T_j의 코드는 계산 시각 T_j − 0.9375에 이미 계획 정보로 쓸 수 있다
- **생성 음:** 출력 음에서 문맥 음을 (pitch, onset 10 ms) 다중집합으로 뺀 나머지. 원 sampled 토큰을 함께 저장한다
- **채택:** onset이 [T_j, T_j + 0.9375)인 생성 음
  - end = min(원래 end, 블록 끝). end ≤ onset이면 뺀다
  - 원래 생성 음은 따로 보존한다. 잘린 음 수와 잃은 길이를 기록한다. 블록 경계에서 프레이즈가 끊기는 영향을 명시한다
  - 블록을 넘는 지속음을 다음 블록으로 넘기는 처리는 이번 범위가 아니다
- **블록 안 같은 pitch 겹침:** 측정만 하고 고치지 않는다
- **문맥 보존 검사:** 토큰 접두사를 글자 그대로 비교하지 않는다. 문맥 MIDI를 토크나이저로 왕복시킨 뒤 맥락 + 채택 음 + 계획 코드의 (pitch, onset, end 10 ms 반올림, velocity) 다중집합이 같은지 본다
- 계획 코드 음은 생성 결과, 평가, 재생용 블록에 넣지 않는다(출처 "guide"). 같은 시각에 계획 코드와 같은 pitch를 모델이 생성한 경우는 개수를 센다

## 시간 시뮬레이션 (#209)
- 작업자 하나가 순차로 계산한다
- 비용 cost_j = 문맥 MIDI 작성 + 토큰화 + 샘플링 + detokenize + 채택 필터. 모델 로딩은 따로 잰다
- 시뮬레이션 시계(음악 시간):
  - actual_start_j = max(T_j − 0.9375, actual_ready_{j−1})
  - actual_ready_j = actual_start_j + cost_j
  - miss = actual_ready_j > T_j − 0.05
- 블록 0은 명목 사전 계산 시작(T_0 − 0.9375)에서 시작한다
- 서비스 비용과 누적 지연을 따로 보고한다
- miss 뒤 블록들은 분석용 tentative chain이다. 재생 fallback이 없으므로, miss가 있으면 전체 실시간 통과라고 하지 않는다

## smoke → 본 실행
- **smoke:** P2 seed 1, 4블록. 통과 조건은 세 가지다
  1. 모든 블록에서 생성 첫 onset ≥ T_j(정렬)
  2. 문맥 보존(빠짐·추가 0)
  3. 블록마다 채택 음 ≥ 1
- 실패하면 원인만 보고하고 본 실행을 멈춘다
- smoke 뒤에는 버그 수정 외에 설정을 바꾸지 않는다. 본 실행은 32블록 전부를 다시 계산한다. seed가 결정적이라 P2 seed 1은 smoke와 같은 결과가 나와야 하고, 다르면 기록한다. smoke를 근거로 같은 seed의 확증을 주장하지 않는다

## 보고
- 블록별: 채택 음 수, 재타격 / 같은 pc 다른 옥타브 / 그 밖, 재타격 제외 P·Q 구별 음 수(그 블록 계획 코드 기준), 최고음 위 새 음
- 전환 방향별 반영 여부, seed 교차로 본 순서 효과
- 연결부: 블록 경계 앞뒤 채택 음의 간격과 음정. 성부를 추정한 것이라 한계가 있다
- 반복: 4블록이 3.75초라 LOOP_DIAG의 4초 루프 정의는 해당되지 않는다. 블록 안 같은 이벤트 반복 수만 센다. 이것만으로 긴 반복이 없어졌다고 하지 않는다
- block-ready 분포, miss, empty, drop, clip, 겹침 수
- 판정은 탐색이다. 품질이나 인과 주장은 하지 않는다

- 시간: 4블록 모두 마감(T − 0.05) 안에 준비됐다. 비용은 0.634–0.698초다
- 채택 음: 4블록 모두 1개 이상이다
- **실패 1, 문맥 보존(같은 pitch 겹침):** 빠짐과 추가가 같은 수로 블록마다 늘었다
  - pitch와 onset은 블록 0에서 모두 보존됐다. 빠짐과 추가는 길이(end)가 달라서 생긴다
  - 원인: 프라이머 끝의 B2(7.65–8.71초)가 아직 울리는 동안 계획 코드 근음 B2(8.11초)를 새로 친다. MIDI는 같은 pitch를 동시에 둘 담지 못한다. 토크나이저 왕복에서 앞 음이 뒤 음 onset에서 끝나고, 길이가 바뀐다
  - 블록이 쌓일수록 계획 코드 근음과 맥락·생성 음의 같은 pitch 겹침이 늘어서 숫자가 커진다
- **실패 2, 정렬 판정(10 ms 격자):** 블록 2의 첫 생성 onset이 T보다 5 ms 이르다
  - 원인: T_j = t_c + j × 0.9375가 Aria 토큰의 10 ms 격자 위에 있지 않다. 예를 들어 T_2 = 9.985초다. 계획 코드와 생성 음 모두 9.98초로 반올림된다
  - 그 결과 코드와 동시에 친 생성 음 2개가 채택 규칙(onset ≥ T − 1 ms)에서 블록 밖으로 빠졌다. 모델이 앞서 생성한 것이 아니라 격자 반올림이다
- 3블록 이후(블록 3) pitch+onset에서도 빠짐·추가 3이 생겼다. 격자 밖 시각의 반올림 차이로 보이지만, 수정 뒤 smoke에서 다시 확인한다

### 수정 제안 (아스트라 검토 대기, 본 실행 전)
- 블록 시각과 계획 코드 길이를 10 ms 격자에 맞춘다(T_j를 0.01초 단위로 반올림). 채택 창도 같은 격자로 정한다
- 같은 pitch 겹침은 MIDI가 표현하지 못한다. 문맥을 쓰기 전에 "뒤에 같은 pitch가 시작되면 앞 음은 그 onset에서 끝난다"를 **명시 규칙**으로 적용하고, 그 수를 기록한다. 토크나이저가 어차피 하는 일을 숨기지 않고 드러내는 것이다. 그 뒤 보존 검사는 이 규칙을 적용한 문맥을 기준으로 한다

### 계약 v2 (아스트라 #210, smoke 실패 뒤 · 본 실행 전)
- **절대 격자:** q_j = T_0 + j × 0.9375초를 10 ms 단위로 반올림(정수 ms, half up)한 값. 누적하지 않아서 드리프트가 없다. 블록 끝 = q_{j+1}, 계획 코드 길이 = q_{j+1} − q_j
  - 채택 창은 [q_j, q_{j+1})다. 정확히 경계 위의 onset은 다음 블록에 속한다
  - 마감은 원래 템포 시계 T_j로 잰다. 격자 오차(q_j − T_j)는 따로 기록한다
- MIDI는 1 tick = 1 ms(500 tick/beat, 120 BPM)로 쓴다. 10 ms 격자가 정수 tick에 정확히 맞아서, 토크나이저 반올림이 끼지 않는다
  - 토크나이저 `_find_closest_int`의 동점 처리는 탐색 순서에 따라 정해진다. 그래서 동점이 아예 생기지 않게 격자 위 시각만 쓴다
- **정정:** 처음 "MIDI는 같은 pitch를 동시에 담지 못한다"고 쓴 것은 틀렸다. 겹친 note-on 자체는 저장할 수 있다. 이번 경로의 파서(ariautils)는 note-off 하나로 그 pitch의 열린 note-on을 모두 닫는다. 그래서 같은 채널·같은 pitch 겹침이 모호해지고 정규화된다
- **같은 pitch 정규화(모델 문맥에만):** `normalize_context`
  - 같은 pitch, 같은 onset이면 출처 우선순위(guide > history > generated)로 하나만 남긴다. 나머지는 문맥에서만 빼고 기록한다
  - 같은 pitch가 다음 onset까지 울리면 그 onset에서 끝낸다
  - end ≤ onset은 뺀다
  - 출처 쌍별(history←guide, guide←generated 등) 수정 수와 잃은 길이를 기록한다
  - 채택·재생용 원본은 소급해 고치지 않는다. 계획 코드 때문에 지속음이 잘리는 것은 무손실 처리가 아니다
- 결과는 둘로 나눠 본다: 원본 보존(채택 목록은 그대로), 정규화한 문맥의 토크나이저 왕복 보존
- 회귀 테스트(`tests/test_t4b_contract.py`, 6개)
  - 40블록(37.5초) 절대 격자에 드리프트·겹침 없음
  - 경계 1 tick 앞뒤 onset의 블록 소속
  - 프라이머 B2 + 계획 코드 B2 재현
  - 같은 시각 같은 pitch의 우선순위(guide 대 generated, generated 대 generated)
  - 원본 불변
