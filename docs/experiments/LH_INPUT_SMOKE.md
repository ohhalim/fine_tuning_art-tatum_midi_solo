## 1. 질문 (하나)

- 성공 의미는 여기까지입니다. 왼손이 더 좋은 솔로를 만든다는 검증이나 사용자 청취를 대신하지 않습니다

## 3. 입력 규칙 (실행 전 고정)

- 세션 시계: producer의 `start`(음악 기준 t0, 벽시계 W)를 feeder가 파일로 받아, 음악 시각 m의 음을 벽시계 W + (m − t0)에 보냅니다
- 수신 시각 → 음악 시각: m = t0 + (수신 ns − W) / 1e6
- 블록 k 시작 s_k = t0 + k·B에서 snapshot: **onset < s_k**인 음만. off는 snapshot 전에 실제로 받은 것만 쓰고, 아직 안 뗀 음은 s_k에서 가상 종료(#1773 held 규칙)
- 같은 음높이를 다시 치면(앞 음이 안 떼진 채) 앞 음을 새 onset에서 끝냅니다. velocity 0 note_on은 note_off입니다. 받은 적 없는 음의 off는 무시하고 기록합니다
- CC64(서스테인)는 지원하지 않습니다. 받으면 무시하고 개수를 기록합니다
- 입력 끝: feeder가 목록을 다 보내면 끝. 안 뗀 음은 snapshot 규칙대로 가상 종료
- 관측 창 7.5초, crop, 병합 순서는 #1773 그대로(`lh_context.window_notes`, `merge`)

## 4. 생성 규칙 (실행 전 고정)

- 블록 0(cold)은 왼손 없이 #1747 producer와 같게 만듭니다
- 블록 k ≥ 1: 오른손 추측분을 버리고(`rollback_to_committed`), 확정 오른손 + snapshot 왼손으로 N을 만듭니다. P_reuse = min(공통 앞부분(KV에 있는 모델 입력, N), KV 유효 끝), crop이 바뀌면 0, S = 0이면 마지막 1토큰. N[P_reuse:]를 계산한 뒤 오른손을 지평(h_k = s_k + B + 1박)까지 생성하고 추측분 한 블록을 더 생성합니다(`fill_block`, 블록당 최대 64토큰)
- 생성 길이는 음악 지평 도달로 정합니다. n개로 자르지 않습니다
- 샘플러·형식 마스크·seed는 #1747 producer와 같습니다(#1726 샘플러, `<D>`·`<E>` 차단)

## 5. 마감과 안전 (실행 전 고정)

- 마감 = W + (k·B + 1박). 블록 k의 확정·예약(on_ready)이 마감 뒤면 그 결과를 송출하지 않고 `abort`(이유 `deadline_miss`)를 보낸 뒤 실험을 멈춥니다
- 송출기는 `abort`를 비정상 종료로 처리합니다: 미송출 note-on 취소, 울리는 소유음 note-off, 포트 닫기(#1747 종료 경로)
- 늦은 결과를 몰아서 내거나, 조용히 추측분으로 바꾸거나, 다음 블록으로 넘기지 않습니다. crop 비용도 같은 마감으로 셉니다

### 10.3 사후 발견(사전 등록 검사 밖): 확정 지평 앞 음의 지각 송출

### 10.4 실행 간 차이: 2 ms 지터가 생성 경로를 바꿈

1차 실행과 재실행은 같은 seed인데, 블록 2부터 생성 토큰 수가 달라졌습니다(48 대 42).
- 1차 실행에서는 첫 왼손 음이 예정보다 약 2.4 ms 늦게 기록됐습니다(feeder 지연 1.1 ms + 전달 2.3 ms). 재실행 세 번은 0.2 ms 이하였습니다
- 그 음은 블록 2에서 held라 s₂에서 가상 종료됩니다. 길이가 934.1 ms 대 936.3 ms로, 10 ms 격자에서 930 대 940으로 양자화가 갈렸습니다
- 확인한 범위에서 블록 2 문맥의 다른 왼손 값(onset·길이·세기)은 두 실행이 같았습니다. N 자체는 저장하지 않아 토큰 단위로는 대조하지 못했습니다
- 실제 연주에서는 이 정도 지터를 없앨 수 없습니다. 같은 연주라도 실행마다 생성과 마감 결과가 달라질 수 있으므로, 한 실행의 마감 결과를 일반화하지 않습니다

### 10.5 다음 후보(이번 단위에서 채택하지 않음)

1. **확정 지평 강제(계약 집행, 제품 tradeoff 아님):** rollback 뒤 onset 하한을 max(마지막 확정 음, h_{k−1})로 겁니다. h_{k−1}이 다음 segment면 `<T>`부터 강제합니다. 송출기는 예정 시각이 지난 note-on을 보내지 않고 기록만 하는 방어선을 둡니다. 이미 확정된 구간에 음을 끼워 넣지 않는다는 기존 계약을 생성과 송출에서 집행하는 것입니다
2. **촘촘한 블록의 생성 예산(제품 tradeoff):** 반응 지연을 2박으로 늘리기, 블록당 밀도 제한, 추측분 유지 등입니다. 원하는 긴 릭과 반응성을 깎는 선택이라 비용 숫자만으로 정하지 않습니다(아스트라 #1794·#1796 권고)
3. B의 crop과 C의 지연 주입을 실제로 거치려면, 블록 4 이전에 멈추지 않는 조건이 필요합니다. 1이 들어간 뒤 같은 세 시나리오를 새 사전 등록으로 다시 볼지 정합니다

### 10.6 리뷰에서 나온 결함(이번 실행 결과에는 영향 없음)

- **지평 미도달 블록 송출(#1802):** `fill_block`은 토큰 상한 64를 다 쓰면 지평에 못 미쳐도 `on_ready`를 부르고, producer의 `on_ready`는 시각만 검사합니다. 이번 세 실행에서 정상 반환한 블록은 모두 지평에 도달했고(`every_block_reached_horizon` 참), 마감으로 중단한 블록은 도달 여부가 기록되지 않았습니다(Abort 시 `reached=None`, 집계에서 빠짐). 이 실행에서 미도달 상태로 송출된 블록은 확인되지 않았습니다. 실제 미도달 발생 여부는 추정하지 않습니다
- **crop 위치 선택에 왼손 길이 미반영(#1803):** 자를 위치를 오른손 세션만으로 고르고 병합 뒤 용량을 다시 확인하지 않습니다. 이번 실행은 crop이 0회라 발동하지 않았습니다
- **보고 보완(#1802에 포함):** 중단 블록의 샘플 수와 snapshot, context, suffix, ready 절대 시각을 보존합니다. 송출기는 note_id와 블록 번호를 직접 기록합니다(#1798)
- 이 결과는 실패 기록입니다. #1798, #1802, #1803을 닫기 전에는 실사용이나 기본 경로 확대 근거로 쓰지 않습니다. 강제 crop과 느린 producer가 실제로 도달하도록 하는 fault 위치는 다음 실행 전에 따로 고정합니다
