# 블록당 후보 선택 (S, 오프라인, 사전 등록)

작성 2026-10-03. 이슈 #1637. 아스트라와 심층 토의 2에서 합의했다. 판정 규칙은 실행 전에 고정했다. `musical_quality_verified: false`.

## 근거
- 런타임에서 화성 조건이 약하다: 화성이 달라도 출력이 같은 비율 10–37.5%(#1636), matched Δshuf .014–.021(#1634)
- 재학습(A)으로는 조건 반응이 늘어난 것이 확인되지 않았다
- 그래서 모델은 그대로 두고 디코딩을 바꾼다. 같은 primer에서 후보 N개를 만들고 고정 규칙으로 하나를 고른다
- 음을 고치거나 걸러 내지 않는다. 후보는 전부 모델 출력이다

## 실행 (`scripts/candidate_select_eval.py`)
- 체크포인트: bebop. 런타임 기본 블록 호출(현재 런타임 guide, 반마디 0.9375초, 128 BPM, T 1.0, top-k 32, top-p .95, gen 96 / max seq 192)
- **holdout 진행**(앞선 실험에 쓰지 않음): ii–V–I F(Gm7 C7 Fmaj7), 리듬 체인지 A(Bbmaj7 G7 Cm7 F7), A 단조(Bm7b5 E7 Am7). 각 진행의 고유 코드마다 seed 40개
- 후보 N = 3(seed s, s+1000, s+2000)
  - **A:** 후보 0. 지금 런타임이 치는 것이다
  - **B:** 무작위로 고른 1개(고정 RNG)
  - **C:** 고정 ranker. 유효하고 솔로 음이 3개 이상인 후보 중 fit − clash(코드 pc 기준, 길이 가중)가 가장 큰 것. 같으면 번호가 낮은 쪽. 해당 후보가 없으면 후보 0
- 원시 후보, 점수, 선택 결과를 `raw.json`에 보존한다

## 독립 검사 (ranker가 직접 최적화하지 않는 것)
- 초당 음 수, 빈 블록 비율, 한 음 블록 비율, 같은 음 반복 비율, 도약(> 7반음) 비율
- 박 위 clash: 박(0, 1박) ±30 ms에 시작한 음 중 반음 충돌인 비율. ranker는 길이 가중 전체 clash만 본다. 박 위치는 보지 않는다
- 첫 음정 3개의 다양성: 블록마다 고유한 시작 음정열의 비율. 선택 때문에 단조로워지는지 본다

## 판정 (실행 전 고정): "런타임 예산 검증 단위로 진행"
1. ranker 이득(C − B, fit − clash) ≥ 0.05. 이 정도 차이가 아니면 런타임 비용을 쓸 가치가 없다(기대되는 방향이라 크기만 본다)
2. C 초당 음 수가 A의 ±20% 안
3. C 같은 음 반복 ≤ A + 0.05
4. C 빈 블록 ≤ A
5. C 도약 비율 ≤ A + 0.05
6. C 시작 음정 다양성 ≥ B × 0.9
7. C 박 위 clash < B
- 통과해도 품질 보증이 아니다. fit/clash의 절대 임계값은 검증되지 않았다. 다음 단위는 런타임 예산 검증이다: N개 생성 + 순위 + 전송 준비의 block-ready p95/p99, miss, fallback, 유효 후보가 0개이거나 시간을 넘길 때의 정책
- 미달이면 기록한다. ranker나 N은 다시 고르지 않는다
