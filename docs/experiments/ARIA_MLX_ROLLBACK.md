# Aria MLX 생성 중간 되돌리기·첫 호출 비용·송출 계약 (#1739) — 사전 등록

#1737에서 로컬 Aria MLX의 KV 캐시 이어 생성이, 시험한 토큰열에서 처음부터 계산한 것과 같다는 것을 확인했다(토큰당 약 11 ms). 남은 것은 세 가지다.
- 되돌리기는 prompt 끝으로만 시험했다
- 새 길이를 처음 계산할 때 튀는 값(0.18~0.85초)이 있었다
- 실시간에서 무엇을 확정으로 내보내고 무엇을 버릴지 규칙이 없다

이 문서는 그 셋을 다루는 기반 점검이다(아스트라 #1738 재리뷰 합의). 소리나 코드 제어를 개선하는 실험이 아니다.

## 질문

1. 생성 중간 위치로 되돌려 짧거나 긴 다른 토큰열을 이어 넣어도, 처음부터 계산한 것과 같은가?
2. 되돌린 뒤 캐시에 남아 있는 취소된 토큰이 이후 계산에 보이지 않는가?
3. 처음 쓰는 길이의 첫 호출 비용은 얼마인가? 같은 길이의 두 번째 호출(warm)과 나눠 잰다
4. 확정 송출, 미확정 생성, 울리는 음의 note-off 책임을 어떤 규칙으로 정하나?

## 고정 조건

#1737과 같다. 로컬 `t3_aria`(커밋 c2f67bc, mlx 0.25.2, 로컬 `max_kv_pos` 패치), `model-gen.safetensors`, float32 가중치·캐시. 토큰열은 #1731 마스크 생성의 A(prompt 0 + base seed 1), B(prompt 0 + base seed 2), 각 614토큰. 캐시 용량은 모든 검사가 쓰는 최대 위치 + 1로 미리 계산하고, 범위 밖 호출은 forward 전에 거절한다.

## 검사와 기준 (실행 전 고정)

**R 되돌리기 (`scripts/aria_mlx_rollback_smoke.py`)**
- 캐시에 A 전체(위치 0~613)를 채운다
- 되돌릴 위치 R ∈ {P+64, P+256, P+448}(P = prompt 길이 102), 대체 길이 k ∈ {8, 128}, 6가지 조합이다
- R부터 B의 생성 토큰 k개를 한 번에(chunk) 써 넣는다. 이어서 저장된 B 토큰 16개를 하나씩 decode한다
- 같은 토큰열 `A[:R] + 대체 + 이어진 16토큰`을 새 캐시에 한 번에 넣은 결과와 비교한다
- **기준:** 써 넣은 모든 위치에서 top-1이 같고, 최대 |logit 차| ≤ 1e-3
- 새 끝 뒤에 A의 옛 토큰이 남아 있는 조합(5개)은 "취소된 토큰이 보이지 않는다"는 검사도 된다. 조합마다 남은 칸 수를 기록한다. R = P+448, k = 128 조합은 옛 칸이 남지 않는다

**F 첫 호출 비용**
- 프로세스가 시작한 뒤 다른 forward보다 먼저 잰다
- 처음 쓰는 prefill 길이 96, 160, 224, 288, 352, 416, 480, 544마다 첫 호출과 같은 길이의 두 번째 호출 시간을 잰다
- 첫 길이(96)의 첫 호출은 프로세스 첫 forward라 따로 표시한다
- 256토큰 prefill 뒤의 첫 한 토큰 decode와 그다음 decode도 잰다
- 보고만 하고 합격선은 두지 않는다

## 실시간 송출 계약 (설계. 이번 단위에서는 구현하지 않는다)

용어
- **확정 구간:** 런타임이 MIDI 스케줄러에 넘긴 토큰. 이미 울렸거나 울릴 예정이다
- **미확정 구간:** 생성했지만 아직 넘기지 않은 토큰
- **위치 세 개** (모두 토큰 인덱스, 끝은 미포함. 아스트라 #1740 LOW)
  - `committed_end`: 확정 구간의 끝. 이 앞의 토큰은 스케줄러에 넘어갔다
  - `kv_valid_length`: KV 캐시에서 유효한 길이. 위치 0 ~ `kv_valid_length − 1`이 현재 토큰열과 일치한다
  - `next_write_pos`: 다음에 KV에 써 넣을 위치. 보통 `kv_valid_length`와 같다
  - 샘플링한 마지막 토큰은 다음 forward에서 써 넣기 전까지 KV에 없다. 그래서 그 순간 토큰열 길이는 `kv_valid_length + 1`이다. 다음 단위에서 이 경우를 명시적으로 다룬다
- **세대(generation):** 정지·재시작할 때마다 1씩 올리는 번호. 예약한 모든 MIDI 이벤트에 붙인다

규칙
1. **확정 단위는 완결된 음이다.** 피아노 음 토큰, onset, dur 세 개가 다 있어야 확정한다. 음 중간(note-on만 확정되고 dur는 미확정)에서 끊지 않는다. 그래야 확정한 모든 음의 note-off 시각이 정해져 있다
2. **확정 구간은 바꾸지 않는다.** 코드 입력이 와도 이미 넘긴 음은 고치지 않는다. 그래서 반응은 확정 지평(예: 1박) 뒤부터 나타난다. "첫 박 패치"처럼 확정된 음을 바꾸는 방식은 쓰지 않는다(아스트라 #1736 H2)
3. **입력이 오면 미확정 구간을 버린다.** `kv_valid_length`와 `next_write_pos`를 `committed_end`로 되돌리고, 그 뒤에 새 입력(제어 토큰 등)을 써 넣은 다음 다시 생성한다. 버린 칸은 `max_kv_pos`로 가려져 보이지 않는다(검사 R에서 확인)
4. **note-off는 스케줄러가 책임진다.** 확정한 음의 note-off는 확정할 때 정해진 시각에 스케줄러가 보낸다. 모델이나 캐시가 되돌려져도 영향을 받지 않는다. 버린 미확정 음은 보내지 않았으므로 짝 없는 note-off도 생기지 않는다
5. **되돌릴 때 문법 상태도 함께 되돌린다.** 확정 구간 끝의 문법 상태(음 사이/onset/dur, 구간의 마지막 onset, `<T>` 구간 번호)를 저장해 두고, 형식 마스크를 그 상태에서 다시 시작한다
6. **어댑터를 바꾸면 전체 reset이다.** 이전 어댑터로 계산한 KV는 새 어댑터에서 유효하지 않다. 문맥 전체를 새 어댑터로 다시 prefill하고, 미확정 구간은 모두 버린다. 확정 음의 note-off는 규칙 4대로 스케줄러가 계속 책임진다. 교체는 프레이즈 경계에서 한다. 이번 단위에서는 구현하지 않는다
7. **정지·오류는 확정 구간 불변(규칙 2)의 예외다.** 일반 되돌리기는 확정 구간을 그대로 두지만, 정지·오류에서는 확정됐어도 아직 실행되지 않은 미래 이벤트까지 취소한다(아스트라 #1740 MEDIUM). 예를 들어 t=10에 note-on을 예약한 상태에서 t=9에 정지하면, t=10에 음이 울리면 안 된다. 정지·오류 때 스케줄러는 순서대로 다음을 한다
   1. 새 예약을 막는다
   2. 세대 번호를 올린다. 이전 세대의 대기 중인 note-on·note-off를 모두 무효로 한다
   3. 지금 울리는 음 전체에 note-off를 보낸다(all-notes-off)
   4. 재시작한 뒤에도 이전 세대 번호가 붙은 늦은 callback은 실행하지 않는다
8. **캐시 용량을 넘기 전에 문맥을 줄인다.** 커서가 용량에 가까워지면 오래된 문맥을 잘라 처음부터 다시 prefill한다. 이때 F에서 잰 새 길이 첫 호출 비용이 생기므로, 자르는 길이를 몇 개로 고정해 미리 데워 둔다(warm-up)

## 하지 않는 것

착지 바이어스, 후보 재순위, CFG, 양자화, 새 학습, 다운로드, 런타임 구현, 키 입력부터 소리까지의 지연 주장, 소리·제어 개선 주장.

## 해석

- **확인한 것:** 시험한 토큰열에서, 생성 중간으로 되돌려 짧거나 긴 다른 토큰을 써 넣어도 처음부터 계산한 것과 허용 오차 안에서 같고 top-1이 일치한다. 되돌린 뒤 남은 옛 칸은 보이지 않는다. 그래서 송출 계약 규칙 3(입력이 오면 미확정 구간을 버리고 커서를 되돌린다)은 KV 쪽에서는 성립한다
- **확인하지 않은 것:** 송출 계약의 실제 구현(확정 단위, 스케줄러의 note-off 책임, 문법 상태 저장·복원), 정지·오류 시 미래 예약 취소와 세대 무효화, 어댑터 교체 reset, 블록 지연의 max·p99와 튀는 값의 원인, 키 입력부터 소리까지의 지연, bf16
- 소리나 코드 제어가 나아졌다는 주장은 하지 않는다. 이것은 기반 점검이다

## 계약 구현 (#1741)

`scripts/stream_contract.py`에 모델 없이 도는 상태기계 두 개를 만들었다. 시계는 가상 시각이다. MLX·모델 연결, 실제 MIDI 포트, 제어 토큰 주입, 어댑터 전환 구현은 하지 않았다.

| 상태기계 | 맡는 규칙 | 핵심 동작 |
|---|---|---|
| `TokenStream` | 1, 2, 3, 5, 6, 8 | `committed_end` / `kv_valid_length` / `next_write_pos`. 완결된 음만 지평 전까지 확정한다. `<T>`는 지평이 다음 구간에 닿아야 확정한다. 미확정을 버리면 위치와 문법 상태가 확정 끝으로 돌아간다. 샘플한 토큰은 KV에 쓰기 전까지 `tokens`에만 있다. 전체 reset은 확정 문맥 전체를 다시 prefill해야 한다고 표시한다 |
| `Scheduler` | 4, 7 | 확정 음을 세대 번호가 붙은 note-on/off로 예약한다. 정지하면 새 예약 차단, 세대 증가, 대기 이벤트 삭제, 울리는 음 note-off. 이전 세대의 늦은 callback은 재시작 뒤에도 무시한다. 같은 음높이가 겹쳐도 note-off는 음마다 따로 책임진다 |

**회귀 `tests/test_stream_contract.py` 16개 (모두 통과)**
- 아스트라 지정 4개: 예약 전 정지, note-on 직후 정지(note-off 한 번만), 늦은 callback(재시작 뒤에도 무시), 재시작 뒤 새 예약 정상
- 확정 단위: 완결된 음만 확정, 지평에서 멈춤, `<T>` 확정 조건
- 되돌리기: 확정 토큰 불변, 위치·문법 상태 복원, 확정 음의 note-off는 되돌리기와 무관
- 그 밖: 샘플 토큰이 KV에 쓰이기 전 상태, 잘못된 토큰 거절, 전체 reset, 정지 중 예약 거절, 정지 뒤 대기 목록 비움, 같은 음높이 겹침
- **변형 검사:** 규칙을 일부러 깨 봤다(정지 시 대기 이벤트를 남김, 세대 확인 제거, 미완결 음 확정 허용, 되돌리기에서 미확정을 남김). 넷 다 테스트가 실패로 잡았다. 처음에는 "정지 시 대기 이벤트를 남김"을 못 잡았다. 세대 확인이 이중으로 막아 동작은 맞았지만, 그 장치 하나만 지키는 테스트가 없었다. 그래서 대기 목록이 비는지 확인하는 테스트를 더했다

**아직 안 한 것:** MLX 생성 루프와 연결, 실제 MIDI 출력·타이머, 제어 토큰 주입, 어댑터 교체 시 실제 재prefill, 블록 지연의 max·p99 측정
