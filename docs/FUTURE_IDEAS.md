## 1. FL Studio 라이브 즉흥 (DJ 세트 안에서)

### 그림
- 사용자가 DJ를 하면서 틀던 곡이나, 전환해서 드롭하는 구간 위에서 모델이 즉흥 연주를 한다
- 입력은 사용자의 키보드다. 코드를 짚거나 멜로디 라인을 준다
- 출력 MIDI는 FL Studio로 들어가서 FL의 악기로 소리가 난다

### 진행 상황 (2026-10-01) ✅
- FL Studio와 실제로 연결했다: FL 자판 → MIDI Out → 런타임 → Serum #2. 사용자 청취 소감은 "무작위적"이다(`docs/phase1/FL_MVP_RECORD.md`)

### 이미 있는 것 ✅
- MIDI 입력 → 생성 → MIDI 출력 루프(`run_continuous_jazz.py`, 가상 포트 `ContinuousJazz`)
- 키보드 입력이 반 마디 블록마다 primer에 반영된다. 입력 도착부터 반영 블록 시작까지 약 0.5–1.3초다(128 BPM, 가상 포트)
- 어댑터 전환: 4마디마다 자동, 또는 키보드 Program Change로 Tatum ↔ 멜다우
- 128–240 BPM에서 fallback·미스 없이 동작한다(가상 포트, 무부하)
- 관련 자산: `flstudio-mcp`(외부 키보드 실시간 연결), `ableton-mcp`(git_box)

### 비어 있는 것
- ✅ **코드 진행이 실행할 때 `--chords`로 고정된다.** 곡 중간에 바꾸거나, 사용자가 짚는 코드를 실시간으로 인식하는 기능이 없다. DJ 세트에서는 곡마다 키와 진행이 바뀌므로 필수다
  - #1576(2026-10-01): opt-in `--live-chords`를 만들어 가상 포트에서 쟀다. 인식 6/6, 반영 지연 약 1.1–1.3초. 코드톤 개선 +0.078로 등록 기준(+0.08) 미달, 입력 블록 fallback 때문에 아직 합치지 않음(`docs/experiments/LIVE_CHORDS.md`)
- ✅ **템포가 런타임 자체 시계다.** 트랙이나 FL Studio의 템포를 따라가지 않는다. FL Studio에서 MIDI 클럭을 받아 맞추는 기능이 필요하다(⚠️ FL Studio의 클럭 송출·Link 지원 방식 확인 필요)
- ✅ 실물 키보드와 FL Studio 경로는 한 번도 검증하지 않았다(`docs/phase1/LATENCY_BUDGET.md`의 미측정 구간)
- ✅ 128 BPM보다 느린 템포는 재지 않았다. 90 BPM에서는 반 마디 블록 32개 중 4개가 fallback이었다
- ✅ 성능 코어를 모두 쓰는 부하에서는 fallback이 난다(#1534). FL Studio와 신스가 같이 돌 때 재측정이 필요하다

### 판단 💭
- 1번 목표인 "내가 실제로 연주에 쓴다"와 바로 이어진다. 두 아이디어 중 먼저 할 것이다
- 드롭 위 즉흥은 즉각적인 주고받기보다 "지금 코드와 템포에 맞는 선율"이 핵심이다. 그래서 0.9초 반영 지연보다 **템포 동기화와 실시간 코드 입력**이 더 중요할 수 있다
- 모델은 재즈 피아노 자료로 학습했다. EDM 드롭 위에서 재즈 솔로가 어울리는지는 예술적 판단이라, 직접 쳐 보고 정할 문제다

## 2. 웹 서비스

### 그림
- 사람들이 웹사이트에 들어와 MIDI 키보드나 컴퓨터 자판(Logic의 Musical Typing처럼)으로 연주한다
- 사용자가 준 멜로디나 코드에 맞춰 즉흥 연주가 나온다
- 스타일을 고를 수 있다
  - 재즈: 찰리 파커, 몽크, 키스 자렛 등
  - 클래식: 모차르트, 쇼팽, 리스트 등
- 많은 사람이 들어와도 안정적으로 돌도록 트래픽을 관리한다

### 이미 있는 것 ✅
- **base 1개 + 어댑터 교체 구조.** 스타일 카탈로그와 그대로 맞는다
  - 같은 base면 스왑은 LoRA가 건드린 12개 텐서 복사, 약 1 ms다
  - base가 다르면 전체 복사, 2–20 ms다
- 루프 안 지표(블록별 코드톤, 보이싱 다양성)를 이미 기록한다. 서비스 모니터링의 재료가 된다
- 생성이 늦으면 미리 만든 패턴으로 대체하는 fallback 구조가 있다. 과부하 때 소리가 끊기지 않게 버티는 설계와 같은 개념이다
- 모델이 작다
  - 13.4M 파라미터, 체크포인트 약 58 MB(fp32)
  - M1 Max CPU에서 반 마디 블록 생성 p50은 약 180 ms다

### 핵심 설계 결정: 추론을 어디서 돌릴 것인가 💭
| | 서버에서 추론 | 브라우저에서 추론 |
|---|---|---|
| 비용 | 동시 사용자마다 연속 생성이 필요하다(반 마디마다 수백 ms). 사용자 수에 비례해 서버가 필요하다 | 서버는 정적 파일만 준다. 트래픽이 늘어도 비용이 거의 늘지 않는다 |
| 안정성 | 자동 확장, 세션 제한, 대기열이 필요하다 | 사용자 기기 성능에 좌우된다(느린 폰이면 fallback이 늘어남) |
| 지연 | 네트워크 왕복이 더해진다 | 네트워크 지연이 없다 |
| 난점 | 운영 부담 | ⚠️ 상대 위치 어텐션(RPR)과 KV 캐시를 브라우저 런타임(ONNX Runtime Web / WebGPU 등)으로 옮길 수 있는지 확인 필요 |

- 💭 **작은 모델이 여기서는 장점이다.** jam_bot(360M)은 브라우저에서 돌리기 어렵지만, 13.4M은 양자화하면 수십 MB 이하로 받아서 돌릴 수 있는 크기다(⚠️ 실제 속도는 검증 전)
- 💭 "많은 사람이 들어와도 안정적"이라는 요구는 브라우저 추론을 택하면 대부분 정적 호스팅 문제로 바뀐다. 서버 추론을 택하면 동시 세션 수가 곧 비용과 안정성 문제가 된다

### 비어 있는 것
- 브라우저 입력: Web MIDI API는 브라우저마다 지원이 다르다(⚠️ Safari 지원 여부 확인 필요). 컴퓨터 자판 매핑도 필요하다
- 브라우저 소리: 사운드폰트 기반 WebAudio 신스가 필요하다
- **스타일 카탈로그의 자료와 권리**
  - ✅ 멜다우 16곡으로는 가능도 개선은 있었지만 들리는 스타일은 확인되지 않았다(블라인드 청취 지지 없음). 스타일 하나당 자료량이 관건이다
  - 💭 클래식은 base 자체가 재즈 자료로 학습돼 있어서, 어댑터만으로 부족할 수 있다(더 넓은 base 사전학습이 필요할 수 있음)
  - ⚠️ 공개 MIDI 데이터셋의 라이선스(비상업 조건 등)와 재즈 채보의 저작권은 서비스 전에 반드시 확인해야 한다
  - ⚠️ 실존 연주자 이름을 스타일 이름으로 내거는 것(퍼블리시티권, 상표)도 서비스 전에 확인해야 한다
- 실사용 트래픽 관리(세션 수 제한, 과부하 시 fallback 비율 모니터링, 기기 성능 감지)

## 3. 제안 순서 💭

1. **출력이 이어지게 만들기** (공통 선행 과제). A/B 청취 결과로 런타임 구조 문제인지 모델 한계인지 가른다
2. **FL Studio 라이브 루프**(아이디어 1)
   - 실물 키보드 → 런타임 → FL Studio 소리 확인
   - 실시간 코드 입력, 템포 동기화
   - 3분 연주 영상
3. **웹 데모 1인용**(아이디어 2의 첫 단계)
   - 브라우저 추론이 되는지부터 확인한다(모델 한 개, 자판 입력, 서버 없음)
   - 이것이 되면 트래픽 문제의 대부분이 사라진다
4. **스타일 카탈로그와 확장.** 자료·권리 확인 후 스타일을 하나씩 추가하고, 사용자가 늘면 모니터링을 붙인다

## 4. 열린 질문
- 라이브 즉흥에서 사용자 입력의 역할은? 코드를 알려 주는 것인가, 주고받는 대화 상대인가. 이 답에 따라 필요한 지연 목표가 달라진다
- 웹 서비스의 첫 사용자는 누구인가. 연주자, 일반 청취자, 교육 중 무엇인가
- 스타일을 "그 연주자처럼 들린다"로 약속할 수 있는가. 지금 근거는 가능도 수치뿐이고, 청취로는 확인되지 않았다
