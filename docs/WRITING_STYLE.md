# 커밋·PR·이슈 작성 규칙

반년 뒤의 나와 리뷰어가 읽는다고 생각하고 쓴다. 무엇을 바꿨는지는 diff에 이미 있다.
diff에 없는 것, 즉 왜 바꿨는지와 무엇을 확인했는지를 쓴다.

근거는 아래 자료다. 한국어 표기(어미, 줄 길이)는 공인된 기준이 없어서 이 저장소에서 정했다.

- 리눅스 커널 [submitting-patches](https://www.kernel.org/doc/html/latest/process/submitting-patches.html) "Describe your changes"
- Git [SubmittingPatches](https://git-scm.com/docs/SubmittingPatches)
- Google [Writing good CL descriptions](https://google.github.io/eng-practices/review/developer/cl-descriptions.html), [How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html)
- Go [Contribution Guide](https://go.dev/doc/contribute) 커밋 메시지 절
- Mozilla [Bug writing guidelines](https://bugzilla.mozilla.org/page.cgi?id=bug-writing.html)
- Claude Code 팀 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) (2026-10-15)

## 공통

기록은 해라체 평서문으로 쓴다("~한다", "~했다"). 리뷰 답글이나 질문처럼 사람에게 말을
거는 글만 존댓말로 쓴다.

문장으로 쓴다. 가운뎃점(·)으로 명사를 잇거나 "~의 ~의"로 쌓지 않는다. 화살표, 등호,
빗금을 문장 대신 쓰지 않는다. 수식과 변수 이름은 백틱으로 감싼다.

숫자는 주장을 뒷받침할 때만, 비교 기준과 같이 쓴다. 제목에는 넣지 않는다.

리뷰 메시지 ID나 문서 안의 검사 코드(C1, B2 같은 것)는 쓰지 않는다. 필요하면 "입력
무결성 검사"처럼 풀어 쓴다.

해당 없는 항목은 비워 두지 말고 지운다. "학습 없음", "청취 없음" 같은 문구를 매번
붙이지 않는다. 범위를 오해할 만할 때만 한 줄 쓴다.

굵은 글씨 라벨 목록(`**라벨:** 설명`), 이모지, 하위 제목만 담은 제목을 쓰지 않는다.

본 것과 짐작한 것을 나눈다. 확인하지 않은 것은 확인하지 않았다고 쓴다.

## 커밋

제목은 `type(scope): 명사구`로 쓰고 한글 30자 안팎에서 끊는다. "이 커밋을 적용하면
___"의 빈칸에 들어가는 말이어야 한다. 마침표는 찍지 않는다.

빈 줄을 두고 본문을 쓴다. 순서는 다음과 같다.

1. 지금 무엇이 문제인지 현재형으로 쓴다.
2. 이 커밋이 무엇을 바꾸는지 쓴다.
3. 왜 이 방식인지 쓴다. 버린 대안이 있으면 그것도 쓴다.

본문은 짧은 문단으로 쓰고 한글 36자(72열) 근처에서 줄을 바꾼다. Markdown은 쓰지 않는다.

실험 결과 수치는 본문에 나열하지 않는다. 결과는 실험 문서에 두고 본문에는 결론 한
문장만 쓴다. 본문이 길어지면 커밋을 나눠야 한다는 신호다.

꼬리말은 `Refs: #이슈`, 버그 수정이면 `Fixes: <커밋 해시> ("<제목>")`를 단다.

예전:

```
exp(realtime): 실제 cache 상태 연속 요청 재생의 사전 등록·스크립트·시험 추가

#1794 리뷰 권고 단위입니다. 실행 전 커밋입니다.

- 재사용 규칙: P_reuse = min(공통 앞부분, KV 유효 끝), crop이면 0, S=0이면 마지막 1토큰 재계산
- 사례: 긴 P 4쌍, crop 1쌍, S=0 1쌍 × fed/unfed. 매 재생 전 KV를 다른 곡 토큰으로 오염
- 시험 2개. 계약 변경·생성·학습·청취 없음
```

지금:

```
exp(realtime): 실제 KV 상태로 앞부분 재사용 재생 준비

앞부분 재사용이 전체 재계산과 같다는 것은 앞 요청 입력을 KV에
전부 넣은 상태에서만 확인했다. 실제 루프에서는 마지막으로 뽑은
토큰이 아직 KV에 없을 수 있어서 같은 결과가 나온다는 보장이 없다.

실제 루프와 같은 KV 상태를 만든 뒤 연속 요청을 재생하고 전체
재계산과 비교하는 스크립트를 추가한다. 잘못된 재사용을 일부러
넣은 두 경우가 실패로 잡히는지도 같이 본다. 실행 전에 판정
기준을 문서로 먼저 올린다.

Refs: #1795
```

## PR

제목은 `type(scope): 명사구 (#이슈)`로 쓴다.

본문 첫머리는 섹션 없이 두세 문단으로 쓴다. 왜 바꾸는지, 핵심 결정이 무엇인지, 리뷰어가
특히 볼 곳이 어디인지 쓴다. 파일 목록을 다시 읽어 주지 않는다.

그 아래에 다음을 한두 줄씩 쓴다.

- 테스트: 실제로 돌린 명령과 결과
- 위험: 깨질 수 있는 것
- 되돌리기: merge를 revert하는 것으로 끝나지 않을 때만

마지막 줄에 `Closes #이슈`를 쓴다.

리뷰 지적에는 하나도 빠짐없이 답한다. 고쳤으면 커밋을 적고, 안 고치면 이유를 한 줄로
쓴다. 반영 요약은 "지적 3건 중 2건 고침, 1건은 의도된 동작"처럼 개수로 시작한다.

## 이슈

제목은 열 단어 안팎으로 문제를 쓴다. 해결책을 쓰지 않는다.

버그 이슈 본문은 다음 순서로 쓴다.

1. 무엇을 했고 무엇을 봤는지 쓴다. 재현 방법, 정확한 수치, 출력을 넣는다.
2. 무엇을 기대했는지 쓴다.
3. 원인을 쓴다. 확인한 것과 짐작한 것을 나눈다.
4. 할 일을 쓴다.

실험 이슈 본문은 다음을 쓴다.

- 답할 질문 하나
- 실행 전에 정한 판정 기준
- 범위

할 일이 둘 이상이면 체크박스로 쓴다.
